# 技术六：高可用与容灾

## 技术定位

高可用与容灾保障平台在多基地推广过程中持续稳定运行，是智能运维平台能够真正落地的关键基础。

## 为什么采用

- 平台一旦中断，会影响监控、告警和工单响应
- 设备状态采集链路不能因为中心系统抖动而全部中断
- 项目分 3 期交付，需要控制升级风险

## 在项目中的具体场景

### 场景 1：核心服务多实例部署

监控、告警、权限、工单等核心服务采用集群部署，降低单点故障风险。

### 场景 2：边缘缓冲保障采集连续性

当中心平台暂时不可用时，边缘节点可本地缓存关键数据，待恢复后续传。

### 场景 3：备份恢复与演练

对核心业务数据和配置数据实施备份恢复策略，并安排阶段性演练。

## 决策要点

- 区分高可用和容灾，分别建设
- 优先保证核心链路，而不是追求所有模块同等投入
- 备份机制必须可恢复验证，不能只停留在方案层面
- 分期上线阶段采用灰度和回滚策略

## 项目贴合场景示例

在本项目中，高可用不是只写“多实例”，而是要写成“入口、服务、缓存、数据库、边缘侧”的全链路保障。

典型链路可写为：

`边缘节点/WEB端 -> Nginx/Keepalived -> Gateway -> Kubernetes 多副本服务 -> Redis Sentinel/MySQL 主从 -> 对象存储与备份系统`

项目内可写的具体场景包括：

- 监控、告警、工单服务部署为 `Kubernetes` 多副本
- 数据库采用 `MySQL 主从` 或 `MGR`，保障故障切换能力
- 缓存层采用 `Redis Sentinel`
- 关键指标接入 `Prometheus + Grafana` 做可观测性监控
- 发布阶段通过灰度发布和滚动升级控制风险

## 可写入论文主体内容

高可用与容灾设计是本项目能够在生产环境稳定运行的关键保障。由于平台承载设备接入、状态监控、告警处理和工单闭环等核心能力，一旦系统不可用，影响的不只是某个功能，而是整个运维体系的响应效率。基于这一风险判断，我在架构层面采取了多项协同措施：入口层通过 `Nginx/Keepalived` 保证访问高可用，核心服务通过 `Kubernetes` 多副本部署避免单点故障，关键链路通过消息队列实现异步解耦，缓存层采用 `Redis Sentinel`，数据库层采用 `MySQL 主从` 或 `MGR`，同时边缘节点支持本地缓存和恢复后补传，提升现场异常情况下的数据韧性。通过这些设计，我将稳定性要求从单一模块能力，提升为覆盖端、边、云全链路的系统性能力，从而保障平台能够长期支撑集团设备运维业务。
