# 技术一：微服务与服务治理

## 技术定位

平台覆盖设备接入、监控告警、工单管理、权限控制、统计分析等多个模块，采用微服务架构有利于按业务域拆分系统能力。

## 为什么采用

- 功能域较多，单体系统后期维护压力大
- 分 3 期交付，需要支持模块化演进
- 22 人团队适合按服务拆分协作开发
- 高并发场景下，部分服务需要独立扩缩容

## 在项目中的具体场景

### 场景 1：监控与工单解耦

监控告警服务负责异常识别，工单服务负责闭环流转。二者拆分后便于独立演进，避免工单逻辑影响监控链路。

### 场景 2：权限服务独立

多基地、多角色访问控制较复杂，因此将认证授权能力沉淀为统一权限服务，供各业务模块复用。

### 场景 3：统计分析服务独立

可视化看板依赖统计分析，但统计分析计算量较大，单独拆分后可以避免拖慢在线业务。

## 决策要点

- 按业务域拆分，而不是盲目细粒度拆分
- 服务间调用只保留必要接口
- 对高频异步场景配合消息队列使用
- 对公共能力如认证、日志、配置进行统一治理

## 项目贴合场景示例

在本项目中，可将平台拆分为设备接入服务、设备主数据服务、监控服务、告警服务、工单服务、权限服务、报表分析服务等微服务，并通过 `Nacos` 统一做服务注册与配置管理。

典型调用链可写为：

`边缘节点/WEB端/移动端 -> Gateway -> 监控服务 -> 告警服务 -> 工单服务 -> 通知服务`

或者：

`边缘节点 -> Gateway -> 设备接入服务 -> Kafka/RocketMQ -> 监控服务/规则服务/时序存储服务`

在论文里，这样写会更贴合项目：

- 监控服务只负责状态聚合与实时看板
- 告警服务只负责规则判定与告警分发
- 工单服务只负责流程流转与闭环管理
- 权限服务提供统一认证鉴权能力
- 报表服务负责离线统计和驾驶舱展示

## 可写入论文主体内容

在平台总体架构设计阶段，我没有采用传统单体系统，而是选择了基于 `Spring Boot + Spring Cloud Alibaba` 的微服务架构。这样做的主要原因在于，平台同时覆盖设备接入、监控告警、工单管理、权限控制和统计分析等多个模块，若全部耦合在一个系统中，不仅难以支撑22人团队并行开发，也不利于分3期逐步交付。基于这一判断，我将平台拆分为设备接入、监控告警、工单、权限、分析等核心服务，并通过 `Nacos` 统一管理注册中心和配置中心，通过 `Gateway` 统一承接外部流量，通过 `OpenFeign` 和异步消息机制实现服务协同。对于高频交互场景，我要求同步调用只保留在必要链路上，而把状态上报、告警分发、统计分析等场景改为事件驱动方式。这样设计既提升了系统扩展性，也使后续模块独立上线、独立扩容和独立优化成为可能，较好支撑了项目从建设到持续优化的演进过程。
