# 技术二：消息队列与异步削峰

## 技术定位

设备状态上报、告警分发、工单联动等场景都存在异步处理需求，消息队列用于系统解耦、削峰和缓冲。

## 为什么采用

- 900 余台设备持续上报数据，存在瞬时高峰
- 采集、告警、工单等链路耦合过紧会降低稳定性
- 异常事件需要通知多个下游模块

## 在项目中的具体场景

### 场景 1：设备状态异步上报

边缘节点将采集数据异步发送到平台，中心系统通过消息队列缓冲高峰流量。

### 场景 2：告警事件分发

告警中心识别异常后，把事件发送到通知服务、工单服务、分析服务等多个模块。

### 场景 3：统计分析异步处理

部分统计任务不要求实时返回，采用异步消费方式降低在线服务压力。

## 决策要点

- 消息队列不直接替代数据库
- 对关键消息设计重试和幂等机制
- 对重要链路增加失败补偿和监控告警
- 对消息主题按业务分类，避免混乱

## 项目贴合场景示例

在本项目中，设备上报链路和告警联动链路都适合写成“接入层异步化”。

典型链路可写为：

`边缘节点 -> MQTT Broker/接入服务 -> Kafka/RocketMQ Topic(device.telemetry.raw) -> 监控服务 -> 规则引擎服务`

告警联动链路可写为：

`规则引擎服务 -> Topic(alarm.event) -> 通知服务 / 工单服务 / 分析服务`

这样写能和项目高度贴合：

- 设备状态上报走异步链路，防止瞬时高峰压垮中心平台
- 告警事件一经产生，同时驱动通知、派单、统计多个下游模块
- 对关键消息设置死信队列和重试机制，保障复杂场景下的可靠投递

## 可写入论文主体内容

在本项目中，消息队列并不是可有可无的中间件，而是保障平台稳定性和扩展性的关键基础设施。由于3个基地、900余台设备会持续上报状态数据，如果采集、告警、工单和分析全部采用同步调用方式，任何一个环节的阻塞都可能引发链路级连故障。针对这一问题，我在架构中引入 `Kafka` 或 `RocketMQ`，将设备状态上报、告警事件分发以及部分统计任务处理改为异步模式。例如，边缘节点先通过 `MQTT` 或接入服务把数据送入消息队列，再由监控服务、规则服务和分析服务按消费组独立处理，从而实现削峰填谷和系统解耦。与此同时，我还要求团队在关键消息处理环节中加入重试、死信队列、幂等消费和失败补偿机制，确保异步架构在提升性能的同时不牺牲业务可靠性。这一设计有效缓解了高峰期处理压力，也为后续功能扩展预留了空间。
