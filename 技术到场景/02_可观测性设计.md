# 技术二：可观测性设计

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

可观测性解决的核心问题是：系统出了问题，能不能快速定位到根因。它不是"能监控到异常就够了"，而是要让系统的行为可以从外部输出（指标、日志、链路）中被完整理解和还原。

可观测性的三个支柱：

- **指标（Metrics）**：系统"现在怎么样"——连续采样的数值型数据，回答"健康还是不健康"
- **日志（Logs）**：系统"发生了什么"——离散的事件记录，回答"具体出了什么事"
- **链路追踪（Traces）**：系统"请求经过了哪"——一次请求在多个服务间的完整路径，回答"卡在了哪里"

三者缺一不可：指标告诉你"有问题"，日志告诉你"是什么问题"，链路告诉你"问题在哪一环"。

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 可观测性设计
- 自动化运维及其应用
- 高可用与可靠性设计
- 分布式系统故障诊断
- 性能优化与监控
- SRE 实践

### 1.3 从项目角度看

本项目服务于 3 个生产基地、24 台边缘节点、900 余台设备，中心侧采用微服务架构，覆盖接入、监控、告警、工单、权限和分析等多个服务域。系统链路长：

`设备 → 边缘采集代理 → MQTT → 中心接入服务 → Kafka → 规则引擎/监控/分析 → 告警/工单/通知`

一旦出现"告警延迟""工单未生成""数据丢失"等问题，故障可能出现在链路中的任何一环。如果没有统一可观测体系，排障只能靠逐个服务人工猜测，效率极低。

## 2. 技术分析

### 2.1 技术点一：指标监控体系

#### 技术解释

指标监控是可观测性的第一层基础。它通过持续采集数值型时间序列数据，建立系统的实时运行画像。核心不是"采集了哪些指标"，而是指标体系怎么分层设计、怎么存储查询、怎么驱动告警。

指标体系通常分为四层：

- **基础设施层**：CPU、内存、磁盘、网络
- **中间件层**：Kafka 消费延迟、MQTT 连接数、Redis 命中率
- **服务层**：请求 QPS、响应时间 P99、错误率
- **业务层**：设备在线率、告警生成速率、工单处理时长

#### 项目中的具体场景

本项目中，指标监控采用 Prometheus + Grafana 架构。Prometheus Server 作为中心采集端，通过 Pull 模式定期拉取各服务暴露的指标端点。边缘节点因为网络条件限制，采用 Pushgateway 中转上报。

四层指标的具体设计：

| 层级 | 关键指标 | 采集方式 | 告警阈值示例 |
| --- | --- | --- | --- |
| 基础设施 | CPU 使用率、内存使用率、磁盘使用率、网络丢包率 | node_exporter | CPU > 80% 持续 5 分钟 |
| 中间件 | Kafka 消费组 Lag、MQTT 活跃连接数、Redis 命中率 | JMX exporter / 内置指标 | Kafka Lag > 10000 持续 3 分钟 |
| 服务 | 请求 QPS、响应时间 P99、错误率、线程池使用率 | 应用内置 Metrics SDK | P99 > 500ms 或错误率 > 1% |
| 业务 | 设备在线率、告警生成速率、工单平均处理时长、数据上报成功率 | 业务自定义指标 | 设备在线率 < 95% |

Prometheus 的存储采用本地 TSDB 保留 15 天热数据，同时通过 Remote Write 将长期数据写入中心 InfluxDB（详见 [06_数据架构与大数据处理.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/技术到场景/06_数据架构与大数据处理.md)）。Grafana 按角色分层设计看板：

- **运维人员看板**：基础设施和服务层指标，关注系统健康
- **值班人员看板**：告警趋势、设备在线率、消息积压，关注业务连续性
- **管理层看板**：OEE、故障率、响应时效，关注运营效率

告警规则通过 Prometheus Alertmanager 配置，按严重程度分为三级：

| 级别 | 条件 | 通知方式 | 示例 |
| --- | --- | --- | --- |
| P0 紧急 | 影响核心业务链路 | 电话 + 短信 + 企业微信 | 中心接入服务宕机、Kafka 集群异常 |
| P1 严重 | 影响部分功能 | 短信 + 企业微信 | 单基地设备在线率骤降、消息积压持续增长 |
| P2 警告 | 需要关注但不紧急 | 企业微信 | 磁盘使用率偏高、单台边缘节点离线 |

#### 架构师决策点

我没有让每个服务自己做告警判断。原因是如果每个服务各自配告警阈值和通知方式，会出现两个问题：一是告警规则分散在各处，修改和审计困难；二是无法做跨服务的关联告警（比如"消息积压 + 规则引擎 CPU 高"组合出现时，可能指向规则引擎性能瓶颈，而不是消息队列问题）。统一 Prometheus + Alertmanager 后，告警规则集中管理，也便于后续做告警收敛和关联分析。

### 2.2 技术点二：日志集中管理

#### 技术解释

日志是离散的事件记录，回答"具体发生了什么事"。指标只能告诉你"P99 延迟升高了"，但日志能告诉你"是哪个请求、传了什么参数、在哪一行代码报了什么错"。

日志集中管理的核心设计点：

- **结构化日志**：不是写纯文本，而是用 JSON 等结构化格式，包含时间戳、服务名、日志级别、请求 ID、业务字段等
- **统一采集**：各服务的日志通过采集代理统一发送到中心日志平台
- **索引与检索**：支持按字段快速检索，而不是全文 grep
- **保留策略**：热日志保留 7 天可实时检索，温日志保留 30 天可离线查询，冷日志归档到对象存储

#### 项目中的具体场景

本项目中，各服务统一采用结构化日志格式：

```json
{
  "timestamp": "2025-03-12T09:30:05.123+08:00",
  "level": "ERROR",
  "service": "rule-engine",
  "traceId": "abc-123-def",
  "deviceId": "CNC-018",
  "baseId": "B01",
  "message": "threshold rule evaluation failed",
  "error": "connection timeout to InfluxDB",
  "duration_ms": 5023
}
```

关键字段说明：

- `traceId`：链路追踪 ID，可以把一条日志和完整请求链路关联起来
- `deviceId`、`baseId`：业务维度字段，支持按设备和基地检索
- `duration_ms`：耗时字段，支持性能分析

日志采集链路：

`应用服务 → 文件/Stdout → 日志采集代理（Filebeat/Fluentd）→ Kafka → 日志消费服务 → Elasticsearch → Kibana`

日志平台的核心能力：

| 能力 | 用途 | 示例 |
| --- | --- | --- |
| 关键字检索 | 快速定位错误 | 搜索 `level:ERROR AND service:rule-engine` |
| 请求追踪 | 还原一次完整请求 | 按 `traceId:abc-123-def` 查看全链路日志 |
| 设备维度查询 | 按设备排查问题 | 按 `deviceId:CNC-018` 查看该设备所有日志 |
| 基地维度统计 | 按基地分析趋势 | 统计各基地最近 1 小时的 ERROR 日志数量 |
| 日志告警 | 基于日志模式触发告警 | ERROR 日志 5 分钟内超过 100 条触发 P1 告警 |

#### 架构师决策点

我没有让各服务直接写入 Elasticsearch。原因是：一、如果 Elasticsearch 短时不可用，日志会丢失，而业务服务不应该被日志系统阻塞；二、高峰期日志量大，直接写入可能打爆 ES 集群。因此在中间加了一层 Kafka 作为日志缓冲：服务异步写入 Kafka，日志消费服务按 ES 集群的承载能力控制写入速率。这样既保证日志不丢（Kafka 持久化），也避免日志系统影响业务服务。

同时，我要求所有服务必须输出 `traceId`。这个字段是连接日志和链路追踪的桥梁——当链路追踪发现某个 span 耗时异常时，可以通过 `traceId` 直接检索到该 span 对应的详细日志，快速定位根因。

### 2.3 技术点三：分布式链路追踪

#### 技术解释

链路追踪解决的是"一次请求在多个服务之间经历了什么"的问题。在微服务架构中，一个业务事件可能经过接入服务 → Kafka → 规则引擎 → 告警服务 → 工单服务 → 通知服务，如果某个环节延迟或失败，单看每个服务的日志和指标无法还原完整链路。

链路追踪的核心概念：

- **Trace**：一次完整请求的全链路，由唯一的 traceId 标识
- **Span**：链路中的一个操作单元（如一次服务调用、一次数据库查询），包含开始时间、耗时、状态
- **Context Propagation**：traceId 在服务间的传递机制（通常通过 HTTP Header 或消息 Header）
- **采样率**：不是每条请求都记录链路，按比例采样以控制存储和性能开销

#### 项目中的具体场景

本项目中，一条典型业务链路的 span 结构：

```
Trace: abc-123-def
├── Span 1: 接入服务接收 MQTT 数据 (15ms)
│   ├── Span 1.1: 数据校验 (2ms)
│   ├── Span 1.2: 幂等去重查询 Redis (5ms)
│   └── Span 1.3: 写入 Kafka (8ms)
├── Span 2: Kafka 消费延迟 (50ms, 等待消费)
├── Span 3: 规则引擎处理 (120ms)
│   ├── Span 3.1: 加载规则快照 (5ms)
│   ├── Span 3.2: 阈值规则判定 (10ms)
│   ├── Span 3.3: 组合规则判定 (30ms)
│   └── Span 3.4: 时间窗口规则判定 (75ms)
├── Span 4: 告警事件写入 Kafka (10ms)
└── Span 5: 通知服务发送告警 (200ms)
    ├── Span 5.1: 查询通知模板 (10ms)
    ├── Span 5.2: 调用短信网关 (180ms)
    └── Span 5.3: 写入通知记录 (10ms)
```

通过这个 span 树，可以清晰看到：整条链路耗时约 395ms，其中通知服务调用短信网关耗时 180ms 是最大瓶颈，规则引擎中时间窗口规则判定耗时 75ms 次之。

链路追踪在本项目中的三个典型使用场景：

| 场景 | 问题 | 排查方式 |
| --- | --- | --- |
| 告警延迟 | 设备异常后告警通知慢了 2 分钟 | 按 traceId 查看完整链路，定位到 Kafka 消费 Lag 导致等待 |
| 工单未生成 | 告警已生成但工单服务没有创建工单 | 查看 span 发现告警事件写入 Kafka 成功，但工单服务消费时因参数校验失败静默丢弃 |
| 数据丢失 | 某设备的数据偶尔缺失 | 按 deviceId 和时间范围检索 trace，发现边缘节点 MQTT 断连重连时丢失了中间几条数据 |

链路追踪的 Context Propagation 设计：

- 服务间 HTTP 调用：通过 `traceparent` Header 传递
- Kafka 消息：通过消息 Header 中的 `traceId` 字段传递
- MQTT 上报：边缘节点在数据 payload 中携带 `traceId`，接入服务提取后注入后续链路

#### 架构师决策点

我没有采用 100% 全量采样。原因是本项目 900 台设备、秒级采集，每秒产生的链路数据量极大，全量采集会带来巨大的存储和性能开销。我采用的策略是：

- **错误请求**：100% 采样，任何报错的链路必须完整记录
- **慢请求**：响应时间超过阈值的 100% 采样
- **正常请求**：按 10% 比例采样，足够支撑趋势分析和抽样排查

同时，业务关键链路（告警生成、工单创建）通过配置强制 100% 采样，因为这些链路的异常直接影响业务闭环。

### 2.4 技术点四：告警收敛与降噪

#### 技术解释

可观测体系不能只是"发现很多报警"，还必须具备降噪和分级能力。工业场景中，一次网络波动可能导致几百台设备同时离线告警，如果不做收敛，值班人员会被海量告警淹没，反而抓不住真正的故障点。

告警收敛的常用策略：

- **按时间窗口聚合**：同一类型告警在 N 分钟内只发一次汇总通知
- **按源头合并**：同一根因触发的多条告警合并为一条（如"边缘节点 EDGE-03 离线"导致该节点下 40 台设备离线告警，合并为一条）
- **按严重程度分级**：P0 电话、P1 短信、P2 企业微信
- **静默与维护窗口**：计划维护期间自动静默相关告警

#### 项目中的具体场景

本项目中的告警收敛设计：

| 告警场景 | 原始告警量 | 收敛策略 | 收敛后 |
| --- | --- | --- | --- |
| 边缘节点离线 | 该节点下 40 台设备各一条离线告警 | 按源头合并：识别为"边缘节点离线"，设备离线作为附属信息 | 1 条汇总告警 + 40 台设备列表 |
| 网络波动 | 3 个基地数百台设备上报异常 | 按时间窗口聚合：5 分钟内同类告警合并 | 1 条"网络波动影响汇总" |
| 规则引擎异常 | 同一规则对多台设备反复触发 | 按规则 + 时间窗口去重 | 每 10 分钟一条汇总 |

告警通知路由：

```
告警事件 → Alertmanager → 路由规则匹配
  ├── P0 紧急 → 电话 + 短信 + 企业微信群 @值班人
  ├── P1 严重 → 短信 + 企业微信群
  ├── P2 警告 → 企业微信群
  └── 信息类 → 仅记录，不通知
```

告警与工单联动：

- P0/P1 告警自动创建工单，工单优先级与告警级别对应
- 告警恢复后自动更新工单状态
- 同一设备 24 小时内重复触发同一告警，工单自动升级

#### 架构师决策点

我没有简单地按"设备 → 基地 → 集团"逐级聚合告警。因为实际场景中，一个边缘节点离线可能导致该节点下所有设备离线，如果按设备维度聚合，需要先知道设备属于哪个节点，再判断是否为同一根因。因此我采用"先识别根因实体，再聚合关联告警"的策略：系统先判断是边缘节点离线还是单台设备异常，如果是节点离线，则自动将该节点下所有设备的离线告警合并为一条节点级告警。

### 2.5 技术点五：三支柱关联与统一观测平台

#### 技术解释

指标、日志、链路追踪三者不是独立存在的，真正的可观测性价值在于三者的关联：

- **指标 → 日志**：指标发现异常后，通过时间范围和服务名快速检索相关日志
- **日志 → 链路**：日志中的 traceId 可以直接跳转到链路追踪视图
- **链路 → 日志**：链路中某个 span 异常时，可以通过 traceId 查看该 span 的详细日志

这种关联能力让排障从"逐个系统切换查看"变成"从一个入口穿透到所有相关信息"。

#### 项目中的具体场景

本项目中的统一流程示例：

**场景：某基地设备告警延迟**

1. **指标层发现问题**：Grafana 看板显示 B01 基地的"告警生成到通知送达"延迟从 3 秒升高到 2 分钟
2. **指标定位范围**：拆解各环节延迟，发现规则引擎处理耗时正常，但通知服务调用短信网关超时
3. **链路追踪验证**：找到一条延迟告警的 traceId，查看 span 树确认通知服务的短信网关调用 span 耗时 120 秒
4. **日志定位根因**：用 traceId 检索通知服务日志，发现短信网关返回 `rate limit exceeded`，是短信服务商限流导致
5. **处置**：临时切换备用短信通道，同时调整告警通知的短信发送频率

这个流程体现了三支柱关联的价值：指标发现 → 链路定位 → 日志定因，整个排障过程在 10 分钟内完成。

统一观测平台的集成设计：

| 入口 | 可跳转到 | 用途 |
| --- | --- | --- |
| Grafana 指标面板 | Loki 日志（按服务名+时间范围） | 从异常指标直接看相关日志 |
| Grafana 日志面板 | Jaeger 链路（按 traceId） | 从错误日志直接看请求链路 |
| Jaeger 链路详情 | Loki 日志（按 traceId） | 从异常 span 直接看详细日志 |
| 告警通知 | Grafana 面板 + 相关日志 | 值班人员从告警直接进入排障视图 |

#### 架构师决策点

我没有把指标、日志、链路追踪作为三个独立系统来建设。如果三者之间没有关联，运维人员需要在 Grafana、Kibana、Jaeger 三个系统之间反复切换，排障效率反而不如以前看单机日志。因此我要求三个系统之间必须打通关联：指标和日志通过 Grafana + Loki 原生集成实现，日志和链路通过 traceId 字段实现，告警通知中附带 Grafana 面板链接和关键日志摘要，让值班人员可以一键进入排障视图。

## 3. 论文主体内容

在本项目中，可观测性设计不是平台建成后的附加优化，而是保障平台长期稳定运行的基础能力。项目服务于 3 个生产基地、24 台边缘节点和 900 余台设备，中心侧采用微服务架构，覆盖接入、监控、告警、工单、权限和分析等多个服务域。系统链路从设备采集到中心处理跨越边缘节点、MQTT 接入、Kafka 分发、规则引擎计算和多个下游服务，一旦出现异常，问题可能出现在链路中的任何一环。如果缺乏统一可观测体系，排障只能依赖逐个服务人工猜测，效率极低且不可持续。

在设计可观测体系时，我从三个支柱分别入手。在指标监控层面，我把指标分为基础设施、中间件、服务和业务四层，采用 Prometheus 统一采集，Grafana 分角色设计看板。运维人员关注系统健康指标，值班人员关注业务连续性指标，管理层关注运营效率指标。告警规则通过 Alertmanager 集中管理，按 P0/P1/P2 三级路由到不同通知渠道。在日志管理层面，我要求所有服务输出结构化日志并携带 traceId，日志通过 Kafka 缓冲后写入 Elasticsearch，既避免日志系统阻塞业务服务，也保证日志不丢失。在链路追踪层面，我对错误请求和慢请求 100% 采样，正常请求按 10% 采样，业务关键链路（告警生成、工单创建）强制全量采样。

三个支柱的真正价值在于关联。当指标发现"告警通知延迟升高"时，可以通过 Grafana 直接跳转到 Loki 查看通知服务的错误日志；从日志中的 traceId 又可以直接跳转到 Jaeger 查看完整请求链路，定位到具体是哪个 span 耗时异常。这种"指标发现 → 链路定位 → 日志定因"的穿透式排障能力，让问题定位从"逐个系统切换"变成"从一个入口贯穿全链路"。

在告警治理上，我没有简单追求"多报警"，而是强调收敛和分级。边缘节点离线时，系统自动识别根因实体，将该节点下所有设备的离线告警合并为一条节点级汇总告警；网络波动时，按时间窗口聚合同类告警。告警按严重程度路由到不同通知渠道，P0 告警电话通知，P1 短信通知，P2 企业微信通知。同时，告警与工单自动联动，P0/P1 告警自动创建工单，告警恢复后自动更新工单状态。

从项目效果看，可观测性体系明显改善了平台的故障发现和恢复效率。一方面，平台具备了从边缘到中心的统一运行视图，问题定位不再依赖单点经验；另一方面，告警收敛机制避免了告警风暴对值班人员的干扰，三支柱关联能力让排障效率从小时级缩短到分钟级。回顾整个项目，我认为可观测性最大的价值不在于工具堆叠，而在于它把复杂系统的运行状态变成了可感知、可分析和可快速响应的工程能力。
