## 1. 技术定位

### 1.1 从技术角度看

数据架构与大数据处理解决的核心问题是：在设备持续产生高频时序数据的场景下，如何同时支撑实时监控、告警识别、趋势分析、管理驾驶舱和预测性维护等不同访问模式的需求，并在实时性、存储成本和数据质量之间取得平衡。

它不是单一的存储或计算问题，而是涵盖数据分层、存储选型、实时处理、离线分析、指标治理和查询优化的完整数据架构设计。

这一技术方向通常包含：

- 数据分层架构（原始层 → 明细层 → 汇总层 → 应用层）
- 时序数据存储与冷热分层
- 实时数据处理与流式计算
- 离线分析与数据湖仓沉淀
- 架构模式选型（Lambda / Kappa / HTAP / 湖仓一体）
- 指标体系与数据质量治理
- 降采样与数据保留策略
- 查询优化与多场景服务

### 1.3 从项目角度看

本项目中，平台需要同时处理三类数据，且访问模式完全不同：

| 数据类型 | 写入特征 | 查询特征 | 时效要求 |
| --- | --- | --- | --- |
| 设备遥测数据 | 高频、持续、有波动 | 最近状态、短时间范围趋势 | 秒级 |
| 运维过程数据 | 中频、事件驱动 | 单条查询、状态跟踪 | 秒级 |
| 管理分析数据 | 低频、周期性汇总 | 多维聚合、长时间跨度 | 分钟级到小时级 |

900 余台设备持续上报运行状态、测点值和事件信息。实时监控和告警要求低延迟写入和查询；集团驾驶舱和趋势分析要求长周期聚合；预测性维护要求数据连续、口径一致。如果把所有数据都简单堆在同一种存储中，高频写入与复杂查询互相干扰，长期历史数据推高存储成本，热点查询和长期归档的访问模式冲突。因此，必须从数据架构层面做系统设计。

## 2. 技术分析

### 2.1 数据分层架构设计（两套方案共用）

#### 技术解释

数据分层是大数据架构的基础思想，两套方案都遵循。核心原则是：不同层次的数据承担不同职责，面向不同消费者，采用不同存储和处理方式。分层后，上游变化不会直接影响下游，下游可以按自己的节奏消费和加工。

经典的数据仓库分层模型：

| 层级 | 名称 | 职责 | 数据特征 | 消费者 |
| --- | --- | --- | --- | --- |
| ODS | 原始数据层 | 保存原始数据，不做清洗转换 | 格式不统一、可能有脏数据 | 开发/运维（数据回放、问题复盘） |
| DWD | 明细数据层 | 清洗、去重、标准化、关联主数据 | 格式统一、质量可控、仍是逐条明细 | 开发/数据分析（明细查询、二次加工） |
| DWS | 汇总数据层 | 按通用维度预计算指标 | 粒度适中、可复用、查询快 | 业务人员/数据分析/规则策略（最常使用） |
| ADS | 应用数据层 | 面向特定消费方的最终结果 | 粒度最粗、直接消费 | 管理者/驾驶舱/预测模型/报表 |

各层的核心定位：

- **ODS**：原始备份，回答"发生了什么"。不做任何加工，保留原始格式，用于回放和复盘。如果 DWD 的清洗逻辑有 bug，可以从 ODS 重新计算。
- **DWD**：统一明细，回答"每条数据长什么样"。核心不是"转换成指标"，而是把异构数据变成统一格式的逐条记录——只做清洗、去重、标准化、关联，不做聚合。
- **DWS**：预计算指标，回答"某个维度的汇总结果"。按通用维度（设备、基地、班组、时间周期）提前计算好，是业务人员和分析人员最常打交道的层，查询快、口径统一。规则策略人员也基于 DWS 的聚合指标做判定（如"某设备日故障次数 > 3 次"）。
- **ADS**：面向场景的最终数据，回答"直接拿来看/用"。任何面向特定消费方的最终结果都算 ADS——管理者看的驾驶舱指标、预测性维护模型需要的特征数据、跨基地对比报表，都是 ADS。粒度最粗，不需要再加工。

以两条指标链路为例，说明每层到底存了什么数据、层与层之间做了什么处理。

**指标一：设备可用率** — 单数据源（设备状态事件）逐层聚合。

**ODS 原始数据层**：边缘上报的原始报文，保留设备侧格式，不做任何转换。

```json
{"deviceId":"CNC-018","protocol":"OPC_UA","rawData":{"ns=2;s=Machine.RunningMode":"auto","ns=2;s=Machine.Spindle.Speed":3200},"timestamp":"2025-03-12T09:30:05+08:00","edgeId":"EDGE-01"}
```

⬇️ **ODS → DWD：协议解析 + 测点映射 + 质量标记**
- 将 OPC UA 原始节点 `ns=2;s=Machine.RunningMode` 映射为平台统一编码 `running_mode`
- 将原始值 `"auto"` 解析为标准化的 metricValue
- 补充 quality 标记（normal/stale/missing）、configVersion、edgeId

**DWD 明细数据层**：清洗后的设备状态逐条明细，格式统一，一条记录对应一个测点的一次采样。

```json
{"deviceId":"CNC-018","metricCode":"running_mode","metricValue":"auto","quality":"normal","edgeId":"EDGE-01","configVersion":"v2.3","timestamp":"2025-03-12T09:30:05+08:00"}
```

⬇️ **DWD → DWS：按设备 + 日期聚合，按状态累计时长**
- 遍历当天该设备所有 `running_mode` 明细记录
- 按状态值分段累计：`auto` 累计 → runHours，`idle` 累计 → idleHours，`fault` 累计 → faultHours
- 计算 `availabilityRate = runHours / 24`

**DWS 汇总数据层**：按设备 + 日期聚合的运行时长和可用率，粒度从"每条采样"变为"每天每台设备"。

```json
{"deviceId":"CNC-018","date":"2025-03-12","runHours":16.5,"idleHours":4.2,"faultHours":3.3,"faultCount":1,"availabilityRate":0.688}
```

⬇️ **DWS → ADS：按基地汇总，补充设备主数据（设备名、所属班组），生成驾驶舱指标**
- 将同基地所有设备的日级汇总聚合为基地级指标
- 关联设备主数据，补充设备名称、所属班组等展示字段
- 按可用率排序，标记异常设备

**ADS 应用数据层**：驾驶舱直接消费的可用率指标，按基地汇总，可直接展示。

```json
{"baseId":"B01","date":"2025-03-12","deviceCount":320,"avgAvailability":0.923,"devices":[{"deviceId":"CNC-018","availability":0.688,"status":"异常"},{"deviceId":"CNC-019","availability":0.952,"status":"正常"}]}
```

**指标二：MTTR（平均修复时间）** — 跨数据源（告警 + 工单）融合。

**ODS 原始数据层**：规则引擎产生的原始告警事件和工单服务产生的原始操作日志，**分别存储**，互不关联。

告警原始事件：
```json
{"deviceId":"CNC-018","rawLevel":"WARNING","rawType":"TEMP_HIGH","rawMessage":"温度超过阈值","triggerTime":"2025-03-12T09:30:10+08:00"}
```

工单操作日志：
```json
{"orderId":"WO-001","action":"create","fromStatus":null,"toStatus":"open","operator":"system","timestamp":"2025-03-12T09:31:00+08:00"}
```

⬇️ **ODS → DWD：标准化 + 关联主数据 + 建立跨数据源关联**
- 告警：等级标准化（`WARNING` → `P1`）、告警分类归一（`TEMP_HIGH` → `TEMPERATURE`）、关联设备主数据补充 `baseId`
- 工单：关联告警 ID（`alarmId`）、关联设备主数据补充 `baseId`、根据 SLA 规则计算 `slaDeadline`
- 关键动作：工单记录通过 `alarmId` 与告警记录建立关联，ODS 层两条独立的记录在 DWD 层有了关联关系

**DWD 明细数据层**：告警明细和工单明细，各自独立存储但通过 `alarmId` 关联。

告警明细：
```json
{"alarmId":"ALM-001","deviceId":"CNC-018","alarmLevel":"P1","alarmType":"TEMPERATURE","triggerValue":82.5,"thresholdValue":80.0,"baseId":"B01","triggerTime":"2025-03-12T09:30:10+08:00"}
```

工单明细：
```json
{"orderId":"WO-001","alarmId":"ALM-001","deviceId":"CNC-018","priority":"P1","assignee":"张工","baseId":"B01","createTime":"2025-03-12T09:31:00+08:00","closeTime":"2025-03-12T11:45:00+08:00","slaDeadline":"2025-03-12T17:31:00+08:00"}
```

⬇️ **DWD → DWS：按 alarmId 关联两张明细表，计算修复时长，再聚合**
- 按 `alarmId` 关联告警明细和工单明细
- 计算单次修复时长：`repairDuration = closeTime - triggerTime = 2.23 小时`
- 判断是否在 SLA 内：`withinSla = closeTime < slaDeadline`
- 按设备/基地/月份聚合：`avgMttr`、`totalFaults`、`slaOnTimeRate`

**DWS 汇总数据层**：单次修复记录 + 月度聚合指标。

单次修复记录：
```json
{"alarmId":"ALM-001","deviceId":"CNC-018","alarmLevel":"P1","repairDuration":2.23,"withinSla":true,"baseId":"B01","date":"2025-03-12"}
```

月度聚合：
```json
{"baseId":"B01","month":"2025-03","totalFaults":45,"totalRepairHours":144.0,"avgMttr":3.2,"slaOnTimeRate":0.956}
```

⬇️ **DWS → ADS：跨基地汇总，生成集团对比指标**
- 将三个基地的月度 MTTR 汇总为一张对比表
- 计算集团平均值

**ADS 应用数据层**：集团驾驶舱的跨基地 MTTR 对比。

```json
{"month":"2025-03","bases":[{"baseId":"B01","avgMttr":3.2,"faults":45},{"baseId":"B02","avgMttr":3.5,"faults":38},{"baseId":"B03","avgMttr":2.2,"faults":28}],"groupAvg":3.0}
```

#### 架构师决策点

分层的核心价值是：上游变化不直接影响下游，同一指标只在 DWS 层计算一次，上层应用消费同一份结果，避免"同一指标不同页面显示不同数字"。两套方案的区别不在于分几层，而在于每层用什么技术实现。

### 2.2 方案 A：轻量方案（InfluxDB + MinIO + MySQL + 定时任务）

这是本项目实际采用的方案，适合中等数据规模（日增量 < 100GB）。

#### 2.2.1 存储层：InfluxDB + MinIO + MySQL

**InfluxDB** 承载时序数据的热数据层和温数据层。

在本项目中的角色：
- 写入：消费 Kafka 中的设备遥测数据，按 deviceId + metricCode + timestamp 写入
- 查询：支撑监控大屏的最近状态查询、告警上下文的短时间范围趋势查询
- 降采样：通过连续查询（Continuous Query）自动生成 5 分钟和 1 小时聚合数据
- 过期：通过保留策略（Retention Policy）自动清理过期热数据

配置示例：

```
# 热数据保留 30 天
CREATE RETENTION POLICY "hot" ON "device_telemetry" DURATION 30d REPLICATION 1

# 温数据（降采样后）保留 180 天
CREATE RETENTION POLICY "warm" ON "device_telemetry" DURATION 180d REPLICATION 1

# 连续查询：每 5 分钟聚合一次
CREATE CONTINUOUS QUERY "cq_5m" ON "device_telemetry"
  BEGIN
    SELECT mean("value"), max("value"), min("value"), count("value")
    INTO "warm"."telemetry_5m"
    FROM "hot"."telemetry"
    GROUP BY time(5m), "deviceId", "metricCode"
  END
```

数据分层映射：
- ODS → Kafka（原始事件短期保留）
- DWD → InfluxDB hot（清洗后的秒级明细）
- DWS → InfluxDB warm（5 分钟/1 小时聚合）+ MySQL 汇总表（业务指标）
- ADS → Redis 缓存（驾驶舱最终指标）

**MinIO** 承载冷数据归档。

在本项目中的角色：
- 归档：180 天后的历史数据通过定时任务导出为 Parquet 列式文件，写入 MinIO
- 查询：历史复盘和预测性维护模型训练时，按时间范围读取 Parquet 文件
- 成本：相比 InfluxDB 长期存储，MinIO 归档的存储成本降低 80% 以上

**MySQL** 承载业务数据和汇总指标。

在本项目中的角色：
- 业务数据：工单表、告警表、通知表、用户表、设备主数据
- 汇总指标：按设备/基地/班组/时间周期聚合的统计结果（设备可用率、故障率、MTTR）
- 查询：驾驶舱的多维聚合查询、基地对比、班组绩效

#### 2.2.2 处理层：Kafka Streams + 定时任务

**Kafka Streams**（轻量流处理）承担实时数据处理。

在本项目中的角色：
- 设备状态更新：每条遥测数据到达后更新 Redis 中的设备最新状态
- 窗口聚合：按 1 分钟/5 分钟窗口计算均值、最大值、最小值
- 连续异常检测：设备温度连续 N 次超限、振动持续偏高时生成异常事件
- 数据清洗去重：按 deviceId + timestamp 去重，修正时间乱序

实时处理链路：

```
Kafka(device.telemetry.standard)
  → Kafka Streams 处理拓扑
    ├── 分支 1: 更新 Redis 设备最新状态
    ├── 分支 2: 窗口聚合 → InfluxDB(DWS)
    ├── 分支 3: 连续异常检测 → Kafka(abnormal.event.detected)
    └── 分支 4: 清洗去重 → Kafka(device.telemetry.clean)
        → 规则引擎消费
```

选择 Kafka Streams 而非 Flink 的原因：本项目的实时处理需求相对简单（状态更新、窗口聚合、去重），Kafka Streams 配合消费组就能满足，不需要 Flink 的复杂流处理能力（CEP、多流 Join、状态后端）。

**定时任务** 承担离线批处理。

在本项目中的角色：
- 每日凌晨：计算昨日设备可用率、故障率、工单及时率，写入 MySQL 汇总表
- 每周一：计算周度故障率趋势、MTTR，写入 MySQL 汇总表
- 每月 1 日：计算月度 OEE、跨基地对比指标，写入 MySQL 汇总表
- 每日凌晨：将 180 天前的 InfluxDB 数据导出为 Parquet 文件，写入 MinIO

#### 2.2.3 服务层：统一查询服务

同一批数据服务多种场景，每种场景的查询模式不同：

| 查询场景 | 查询模式 | 数据范围 | 查询路径 |
| --- | --- | --- | --- |
| 监控大屏 | 单设备最新状态 | 最新一条 | Redis 缓存 |
| 告警上下文 | 单设备近 N 分钟趋势 | 数分钟 | InfluxDB 热数据 |
| 趋势分析 | 单设备数天/数周趋势 | 数天 | InfluxDB 降采样数据 |
| 驾驶舱 | 多设备多基地聚合指标 | 30 天 | MySQL 汇总表 + Redis 缓存 |
| 跨基地对比 | 按基地聚合对比 | 季度 | MySQL 汇总表 |
| 历史复盘 | 特定时段原始数据 | 指定时间段 | MinIO Parquet 文件 |
| 预测性维护 | 单设备数月测点特征 | 3-6 个月 | MinIO 批量导出 |

### 2.3 方案 B：大数据方案（HDFS + HBase + Spark + Flink + Hive + 数据湖）

这是大数据技术栈在本项目中的应用方案，适合大规模数据场景（日增量 > 100GB）或题目明确要求大数据架构时使用。

#### 2.3.1 存储层：HDFS + HBase + Hive

三个组件都基于 HDFS，但数据组织方式不同，面向不同的查询模式。

**HDFS** — 底层文件系统，所有数据最终都存在这里。

HDFS 只负责存文件和读文件，不理解数据内容。本项目中，HDFS 承担三类数据的存储：
- ODS 原始层：设备上报的原始遥测数据、告警事件、工单日志以文件形式写入 HDFS，按日期和基地分区存储
- 中间处理结果：Flink 实时处理和 Spark 离线处理的中间数据
- 冷数据归档：降采样后的长期历史数据以 Parquet 列式格式存储

数据按 `base=B01/date=2025-03-12/` 目录结构组织，查询时可以裁剪分区，只扫描需要的目录。本项目 3 个基地，每个基地部署一个 DataNode，中心部署 NameNode，副本数设为 2，兼顾可靠性和存储成本。

**HBase** — 基于 HDFS 的 NoSQL 数据库，按 RowKey 建索引，支持毫秒级点查。

HBase 在 HDFS 之上加了一层数据级索引（RowKey → 文件位置 → 偏移量），查询时先查索引直接定位到数据所在位置，不需要全表扫描。它的底层是行式存储——一行数据的所有字段连续存放，适合按 key 查单条或小范围扫描。

本项目中 HBase 承载"点击查看"类的实时读写场景：

| 表 | RowKey 设计 | 存什么 | 查询场景 |
| --- | --- | --- | --- |
| 设备最新状态表 | deviceId（如 CNC-018） | 900 台设备 × 30 个测点的最新值 | 监控大屏点击设备详情，毫秒级返回 |
| 设备告警索引表 | deviceId + reverse_timestamp | 按设备倒序排列的告警记录 | 查看某台设备最近的告警列表 |
| 设备测点历史表 | deviceId + metricCode + reverse_timestamp | 单设备某测点的近 30 天数据 | 告警上下文的分钟级趋势图 |

HBase 的 TTL 策略：设备最新状态表不设过期（始终保留最新值），告警索引表保留 180 天，测点历史表保留 30 天（更长时间的查询走 Hive）。

**Hive** — 基于 HDFS 的 SQL 查询引擎，用 Parquet 列式存储，适合批量分析。

Hive 不建索引，而是通过两种方式提升查询效率：一、数据用 Parquet 列式格式存储，做聚合时只读需要的列，不读整行；二、数据按 base_id 和 date 分目录存放，查某天某基地的数据时只扫描对应目录。但本质上还是全表扫描，所以适合"攒一批再算"的离线分析，不适合实时点查。

本项目中 Hive 承载"统计分析"类的离线查询场景：

| 数据层 | 存什么 | 查询场景 |
| --- | --- | --- |
| DWD 明细表 | 清洗后的设备状态、告警、工单逐条明细 | 运维人员查某设备某天的完整运行记录 |
| DWS 汇总表 | 按设备/基地/班组/时间周期预聚合的指标 | 计算设备可用率、故障率、MTTR |
| ADS 应用表 | 面向驾驶舱和报表的最终指标 | 跨基地对比、月度趋势分析 |

Hive 的主题建模围绕四个主题展开：设备主题（设备状态、可用率）、告警主题（告警趋势、闭环率）、工单主题（工单流转、及时率）、运维绩效主题（班组效率、响应时效）。每个主题在 DWS 层建立宽表，上层应用直接查询宽表，不需要每次关联多张明细表。

**HBase 与 Hive 的互补关系**：

同一个查询需求，用 HBase 和 Hive 的路径完全不同。以"查看 CNC-018 的设备可用率"为例：

| 维度 | HBase 路径 | Hive 路径 |
| --- | --- | --- |
| 存储格式 | 行式（一行 = 一台设备的所有字段） | 列式 Parquet（同一列数据连续存放） |
| 有无索引 | 有（RowKey 索引，毫秒定位） | 无（靠分区目录缩小范围） |
| 查询方式 | `get("CNC-018")` → 直接返回 | `SELECT ... WHERE device_id='CNC-018'` → 扫描分区 |
| 适合场景 | 查单台设备的最新状态（实时） | 查 900 台设备昨天的可用率并排序（离线） |

本项目中两者共存的原因：HBase 存热数据用于实时查询（点查快），Hive 存全量数据用于离线分析（批量计算快），底层数据都在 HDFS 上，不浪费存储。Flink 实时处理的结果写入 HBase 供页面查询，同时写入 HDFS 供 Spark 离线计算。

**数据湖** — 不是一个独立组件，而是"把所有原始数据都存下来"的架构思想。

数据湖的底座就是 HDFS，上层通过 Hive Metastore 管理表结构和分区信息。本项目中数据湖的价值在于：设备遥测、告警事件、工单流转、通知记录等多源数据统一沉淀在 HDFS 上，通过 Hive 提供 SQL 查询能力，通过元数据管理实现数据血缘追溯和质量校验。如果未来需要引入新的分析场景（如预测性维护的特征工程），可以直接基于 HDFS 上的原始数据构建，不需要重新采集。

#### 2.3.2 计算层：Spark + Flink

Flink 负责"数据来了立刻算"，Spark 负责"攒一批再算"。两者配合形成 Lambda 架构的两条链路。

**Flink** — 流处理引擎，数据从 Kafka 进来后立刻处理，结果实时写入 HBase。

本项目中 Flink 承担四类实时任务：

| 任务 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 实时状态更新 | Kafka 设备遥测流 | HBase 设备最新状态表 | 每条数据到达后更新 HBase，监控大屏点击查看时从 HBase 读取 |
| 窗口聚合 | Kafka 设备遥测流 | HBase 汇总表 | 按 1 分钟/5 分钟窗口计算均值、最大值、最小值，写入 HBase |
| CEP 模式检测 | Kafka 设备遥测流 | Kafka 告警事件 | 识别多条件组合的异常模式，如"温度连续升高 3 次 + 振动持续偏高 5 次"预示主轴退化 |
| 实时 ETL | Kafka 设备遥测流 | HDFS（ODS 层） | 清洗、去重、标准化后写入 HDFS，供 Spark 离线计算 |

Flink 的实时 ETL 同时完成两个输出：写入 HBase 供实时查询，写入 HDFS 供离线分析。这样同一份数据不需要采集两次。

**Spark** — 批处理引擎，每天凌晨对前一天的全量数据做离线计算。

本项目中 Spark 承担四类离线任务：

| 任务 | 输入 | 输出 | 调度周期 |
| --- | --- | --- | --- |
| DWD 清洗 | HDFS ODS 明细数据 | HDFS DWD 明细表（Parquet 格式） | 每日凌晨 |
| DWS 指标计算 | HDFS DWD 明细表 | Hive DWS 汇总表 | 每日凌晨 |
| ADS 导出 | Hive DWS 汇总表 | MySQL 驾驶舱指标表 | 每日凌晨 |
| 特征工程 | Hive DWD 明细表（近 6 个月） | Hive ADS 特征表 | 每周 |

以设备可用率计算为例：Spark 读取 HDFS 上 DWD 层的设备状态明细（Parquet 列式格式，只读 `running_mode` 和 `device_id` 两列），按设备 + 日期聚合运行时长，再关联告警明细计算故障次数，结果写入 Hive DWS 表。列式存储的优势在这里体现——900 台设备 × 全天数据，只需要读两列而不是全部字段。

#### 2.3.3 调度层：Airflow

**Airflow** 承载数据管道编排和任务调度，解决"哪些任务先跑、哪些后跑、失败了怎么办"的问题。

本项目中的每日数据管道编排：

```
每日凌晨 2:00 触发
  → 任务 1：检查 ODS 层数据是否到位（HDFS 目录是否存在）
  → 任务 2：DWD 层清洗（Spark 读 ODS → 清洗去重 → 写 DWD）
  → 任务 3：DWS 层指标计算（Spark 读 DWD → 聚合计算 → 写 Hive DWS）
  → 任务 4：ADS 层导出（Spark 读 Hive DWS → 写入 MySQL）
  → 任务 5：数据质量校验（检查记录数、空值率、指标范围）
```

任务之间有依赖关系：DWD 清洗必须等 ODS 数据到位，DWS 计算必须等 DWD 清洗完成，ADS 导出必须等 DWS 计算完成。Airflow 通过 DAG 定义这些依赖，自动按顺序执行。任何一步失败时，Airflow 自动告警并支持手动重跑和回填（补跑历史日期的数据）。

每周和每月还有额外的调度任务：每周触发趋势分析和特征工程，每月触发跨基地对比和 OEE 计算。

#### 2.3.4 数据流转全景

方案 B 的完整数据流转链路：

```
设备 → 边缘 → 接入服务 → Kafka（原始事件）
  │
  ├── 实时链路（Flink）
  │   ├── 更新 HBase 设备最新状态
  │   ├── 窗口聚合 → HBase(DWS)
  │   ├── CEP 模式检测 → 告警事件
  │   ├── 清洗去重 → 规则引擎
  │   └── 写入 HDFS(ODS)
  │
  └── 离线链路（Spark + Airflow 调度）
      ├── ODS → DWD 清洗（Spark）
      ├── DWD → DWS 指标计算（Spark/HiveSQL）
      ├── DWS → ADS 导出到 MySQL（Spark）
      └── 冷数据归档（Parquet 格式保留在 HDFS）
```

### 2.5 指标体系与数据质量治理（两套方案共用）

#### 技术解释

指标体系定义"算什么、怎么算、谁使用"，数据质量治理保证"数据完整、准确、一致、可追溯"。两者是数据架构能否真正服务业务的关键。

#### 项目中的具体场景

核心指标定义（必须统一口径）：

| 指标 | 定义 | 计算方式 | 数据来源 |
| --- | --- | --- | --- |
| 设备可用率 | 设备实际运行时间 / 计划运行时间 | 日级汇总 | 设备状态事件 |
| 故障率 | 故障次数 / 运行时间 | 月度汇总 | 告警事件 + 设备状态 |
| MTTR（平均修复时间） | 故障修复总时间 / 故障次数 | 月度汇总 | 工单事件 |
| 工单及时率 | 在 SLA 内处理的工单 / 总工单 | 日级汇总 | 工单事件 |
| 告警闭环率 | 已闭环告警 / 总告警 | 日级汇总 | 告警事件 + 工单事件 |
| OEE（设备综合效率） | 可用率 × 性能率 × 良品率 | 日级汇总 | 多源数据关联 |

数据质量问题及治理方案：

| 问题 | 来源 | 治理方式 |
| --- | --- | --- |
| 重复数据 | 边缘补传、MQTT 重发 | 写入时按 deviceId + timestamp 去重 |
| 时间乱序 | 网络延迟、边缘缓存补传 | 写入时排序，乱序数据标记 quality=time_unsync |
| 测点缺失 | 设备断连、采集失败 | 缺失超过阈值触发离线告警，分析时插值标记 |
| 口径不一致 | 测点映射变更、配置版本差异 | 通过 configVersion 追溯，分析时按版本对齐 |
| 设备编码不一致 | 多基地历史数据编码规则不同 | 主数据统一映射，建立编码对照表 |
| 告警分类不统一 | 各基地告警规则定义不同 | 统一告警等级和分类标准 |

数据血缘追溯：

每条数据从产生到消费的完整链路都有记录：

```
设备上报（sourceProtocol, sourceAddress）
  → 边缘采集（configVersion, edgeId, quality）
  → 中心接入（ingestTime, processTime）
  → 入库存储（storageTime, retentionPolicy）
  → 降采样聚合（aggregationLevel, aggregationTime）
  → 应用消费（queryTime, consumerId）
```

两套方案的指标计算方式差异：

| 指标 | 方案 A 计算方式 | 方案 B 计算方式 |
| --- | --- | --- |
| 设备可用率 | 定时任务扫描 InfluxDB 明细数据 → MySQL 汇总表 | Spark 任务扫描 Hive DWD 表 → Hive DWS 表 → 导出 MySQL |
| 故障率 | 定时任务关联告警表和设备状态表 → MySQL | Spark 任务关联 Hive 告警表和设备状态表 → Hive DWS 表 |
| 实时设备状态 | Kafka Streams 更新 Redis | Flink 更新 HBase |
| 窗口聚合指标 | Kafka Streams 窗口计算 → InfluxDB | Flink 窗口计算 → HBase |

#### 架构师决策点

我没有让各基地自行统计指标再汇总。原因是：如果每个基地对"设备可用率"的定义不同（有的按日历时间算、有的按计划排产时间算），总部看到的横向对比就没有意义。统一指标必须从数据源头做起——统一设备状态事件的定义、统一计算公式、统一统计周期，然后在 DWS 层集中计算，各基地和总部消费同一份指标结果。

#### 技术解释

同一批数据要服务多种场景，每种场景的查询模式不同。查询优化的核心是：为不同的查询模式选择最合适的数据存储和索引策略。

#### 项目中的具体场景

## 3. 论文主体内容

### 论文写法一：数据架构设计（用方案 A）

在本项目中，数据架构设计不是某个单点技术的选择，而是围绕设备运维数据的完整生命周期进行的系统性规划。平台覆盖 3 个生产基地、900 余台设备和 24 台边缘节点，每天持续产生设备状态、测点值、告警事件、工单流转和处置结果数据。按 900 台设备、每台约 30 个测点、平均 5 秒采集频率估算，每秒约产生 5400 个数据点，日增量约 90GB。实时监控和告警要求秒级响应，集团驾驶舱和趋势分析要求长周期聚合，预测性维护要求数据连续、口径一致。这些需求的访问模式完全不同，如果把所有数据都简单堆在同一种存储中，必然互相干扰。

在数据分层上，我把数据组织为四层。原始层保存 Kafka 中的原始事件和 MinIO 中的长期归档，用于数据回放和问题复盘；明细层保存清洗后的设备状态、告警和工单明细，InfluxDB 承载时序明细，MySQL 承载业务明细；汇总层按设备、基地、班组和时间周期聚合指标，通过 InfluxDB 连续查询和 MySQL 汇总表实现；应用层面向驾驶舱和报表提供最终指标结果，通过 Redis 缓存加速。分层的核心价值是：上游变化不直接影响下游，同一指标只在 DWS 层计算一次，上层应用消费同一份结果。

在时序数据存储上，我选型 InfluxDB 而非 TDengine 或 TimescaleDB。选 InfluxDB 不是因为它性能最好，而是因为本项目的指标监控体系已基于 Prometheus 建设，InfluxDB 可以通过 Prometheus Remote Write 无缝对接，降低运维成本。冷热分层策略为：近 30 天数据保留在 InfluxDB 热数据层，通过连续查询生成 5 分钟和 1 小时聚合数据；180 天后的历史数据转入 MinIO 归档（Parquet 列式文件），存储成本降低 80% 以上。

在实时处理上，我采用 Kafka Streams 而非 Flink。原因是本项目的实时处理需求相对简单（状态更新、窗口聚合、去重），Kafka Streams 配合消费组就能满足，不需要 Flink 的复杂流处理能力。实时处理和规则引擎的职责边界也做了明确划分：流处理负责数据层的窗口聚合、状态更新和去重，规则引擎负责业务层的告警判定，两者通过 Kafka 事件衔接。

在指标治理上，我要求设备可用率、故障率、MTTR、工单及时率等核心指标统一定义、统一计算、统一发布。各基地不自行统计指标，而是在 DWS 层集中计算后供各基地和总部消费。对于数据质量问题——边缘补传导致的重复、网络波动导致的时间乱序、测点映射变更导致的口径不一致——在写入时去重、在处理时排序、在分析时通过 configVersion 追溯和对齐。

从项目效果看，数据架构设计使平台同时具备了实时响应和长期分析能力。实时链路支撑了设备状态监控和告警联动，驾驶舱和趋势分析基于预计算指标快速响应，历史数据通过冷热分层低成本保留。回顾整个项目，我认为数据架构的关键不在于堆叠技术组件，而在于根据数据的真实访问模式建立分层、分链路、分场景的处理体系。

### 论文写法二：大数据处理架构设计（用方案 B）

在本项目中，大数据处理架构设计的核心目标是：建立一套能够同时支撑实时监控、离线分析和长期沉淀的数据处理体系。平台覆盖 3 个生产基地、900 余台设备和 24 台边缘节点，每天持续产生设备状态、测点值、告警事件、工单流转和处置结果数据，日增量约 90GB。随着平台覆盖范围扩大，数据规模将持续增长，架构需要具备水平扩展能力。

在存储层，我采用 HDFS 作为数据湖底座，承载 ODS 原始数据和冷数据归档。设备遥测数据按日期和基地分区存储在 HDFS 上，支持后续的离线分析和数据回放。HBase 承载需要实时随机读写的场景——设备最新状态按 deviceId 做 RowKey，支持毫秒级读取；设备测点历史按 deviceId + metricCode + timestamp 做 RowKey，支持单设备的时间范围查询。Hive 基于 HDFS 建立数据仓库，通过 HiveSQL 提供离线指标计算和即席查询能力。数据按 ODS → DWD → DWS → ADS 四层组织，每层的表结构和分区策略独立设计。

在计算层，我采用 Flink 承担实时流处理，Spark 承担离线批处理，两者配合形成 Lambda 架构。Flink 消费 Kafka 中的设备遥测数据流，实时更新 HBase 中的设备最新状态，通过窗口聚合计算分钟级指标，并利用 CEP（复杂事件处理）识别多条件组合的异常模式——例如"温度连续升高 + 振动持续偏高 + 转速下降"组合出现时，预示主轴可能退化，系统自动生成预警事件。Spark 任务在 Airflow 调度下每日凌晨执行：扫描前一天的 HDFS 明细数据，计算设备可用率、故障率、MTTR 等指标，写入 Hive DWS 表，再导出到 MySQL 供驾驶舱查询。

在数据治理上，我通过 Hive Metastore 管理所有表的元数据和分区信息，实现数据血缘追溯。每条数据从设备上报到最终消费的完整链路都有记录。核心指标（设备可用率、故障率、MTTR、工单及时率）统一定义、统一计算、统一发布，各基地不自行统计。数据质量问题——重复、乱序、缺失、口径不一致——在 Flink 实时链路和 Spark 离线链路中分别处理。

从项目效果看，大数据处理架构使平台具备了实时响应、离线分析和长期沉淀三重能力。Flink 实时链路支撑秒级监控和告警，Spark 离线链路支撑每日指标计算和趋势分析，HDFS 数据湖支撑历史数据的长期保留和复盘。随着设备规模扩大，HDFS、HBase 和 Spark 都可以通过增加节点水平扩展，不需要重构架构。回顾整个项目，我认为大数据架构的核心不在于引入了多少组件，而在于根据数据的访问模式和规模选择合适的技术组合，并通过分层和治理保证数据的可信可用。
