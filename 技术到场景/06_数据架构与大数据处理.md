项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

数据架构与大数据处理解决的核心问题是：在设备持续产生高频时序数据的场景下，如何同时支撑实时监控、告警识别、趋势分析、管理驾驶舱和预测性维护等不同访问模式的需求，并在实时性、存储成本和数据质量之间取得平衡。

它不是单一的存储或计算问题，而是涵盖数据分层、存储选型、实时处理、离线分析、指标治理和查询优化的完整数据架构设计。

这一技术方向通常包含：

- 数据分层架构（原始层 → 明细层 → 汇总层 → 应用层）
- 时序数据存储与冷热分层
- 实时数据处理与流式计算
- 离线分析与数据湖仓沉淀
- 架构模式选型（Lambda / Kappa / HTAP / 湖仓一体）
- 指标体系与数据质量治理
- 降采样与数据保留策略
- 查询优化与多场景服务

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 数据架构设计
- 大数据处理架构设计（Lambda 架构 2024.05 真题）
- 数据湖仓架构设计（湖仓一体 2022 真题）
- 数据湖技术及其应用（2019 真题）
- 多源异构数据集成（2023、2024.11 真题）
- 数据分片技术及其应用（2020 真题）
- NoSQL 数据库技术及其应用（2018 真题）
- 实时数据分析设计
- 数据治理与数据质量设计

如果题目强调"数据架构""大数据处理""实时+离线""冷热分层""数据湖仓""数据治理"，这个技术方向都可以作为论文主体。

### 1.3 从项目角度看

本项目中，平台需要同时处理三类数据，且访问模式完全不同：

| 数据类型 | 写入特征 | 查询特征 | 时效要求 |
| --- | --- | --- | --- |
| 设备遥测数据 | 高频、持续、有波动 | 最近状态、短时间范围趋势 | 秒级 |
| 运维过程数据 | 中频、事件驱动 | 单条查询、状态跟踪 | 秒级 |
| 管理分析数据 | 低频、周期性汇总 | 多维聚合、长时间跨度 | 分钟级到小时级 |

900 余台设备持续上报运行状态、测点值和事件信息。实时监控和告警要求低延迟写入和查询；集团驾驶舱和趋势分析要求长周期聚合；预测性维护要求数据连续、口径一致。如果把所有数据都简单堆在同一种存储中，高频写入与复杂查询互相干扰，长期历史数据推高存储成本，热点查询和长期归档的访问模式冲突。因此，必须从数据架构层面做系统设计。

## 2. 技术分析

### 2.1 技术点一：数据分层架构设计

#### 技术解释

数据分层是大数据架构的基础思想。核心原则是：不同层次的数据承担不同职责，面向不同消费者，采用不同存储和处理方式。分层后，上游变化不会直接影响下游，下游可以按自己的节奏消费和加工。

经典的数据仓库分层模型：

| 层级 | 名称 | 职责 | 数据特征 |
| --- | --- | --- | --- |
| ODS | 原始数据层 | 保存原始数据，不做清洗转换 | 格式不统一、可能有脏数据 |
| DWD | 明细数据层 | 清洗、去重、标准化后的明细数据 | 格式统一、质量可控 |
| DWS | 汇总数据层 | 按维度聚合的中间指标 | 粒度适中、可复用 |
| ADS | 应用数据层 | 面向具体场景的最终指标 | 粒度最粗、直接消费 |

#### 项目中的具体场景

本项目中的数据分层设计：

| 层级 | 数据内容 | 存储选型 | 消费方 |
| --- | --- | --- | --- |
| ODS 原始层 | 设备原始上报数据、Kafka 原始事件、告警原始记录 | Kafka（短期）+ 对象存储（长期归档） | 数据回放、问题复盘 |
| DWD 明细层 | 清洗后的设备状态明细、告警明细、工单明细、通知明细 | InfluxDB（时序）、MySQL（业务） | 实时监控、告警上下文、趋势查询 |
| DWS 汇总层 | 按设备/基地/班组/时间周期聚合的指标 | InfluxDB 连续查询 + MySQL 汇总表 | 驾驶舱、基地对比、班组绩效 |
| ADS 应用层 | 面向驾驶舱和报表的最终指标、预测性维护特征 | Redis 缓存 + 前端服务 | 管理层、运维人员 |

数据流转链路：

```
设备 → 边缘 → 接入服务 → Kafka（ODS）
  → 消费组 → 清洗标准化 → InfluxDB/MySQL（DWD）
  → 降采样聚合任务 → InfluxDB 连续查询/汇总表（DWS）
  → 定时计算 → Redis 缓存 → 驾驶舱/报表（ADS）
```

#### 架构师决策点

我没有让每个应用模块直接从 Kafka 或原始存储中取数据加工。原因是：如果监控服务、驾驶舱、分析服务各自从原始数据开始加工，同一指标（如设备可用率）会被计算多次，且算法可能不一致，导致"同一指标不同页面显示不同数字"。分层后，DWS 层的指标是唯一的、经过验证的，上层应用直接消费即可。

我也没有把所有数据放在同一层同一存储中。原因是：ODS 层需要高吞吐写入（Kafka 擅长），DWD 层需要按时间范围快速查询（InfluxDB 擅长），DWS 层需要多维聚合（MySQL 汇总表擅长），ADS 层需要低延迟读取（Redis 缓存擅长）。每层选择最适合的存储，而不是追求一种存储解决所有问题。

### 2.2 技术点二：时序数据存储选型与冷热分层

#### 技术解释

时序数据库是专门为时间序列数据设计的存储系统。与通用数据库相比，时序数据库在写入吞吐、时间范围查询、数据压缩和自动过期方面有明显优势。

主流时序数据库对比：

| 特性 | InfluxDB | TDengine | TimescaleDB | VictoriaMetrics |
| --- | --- | --- | --- | --- |
| 定位 | 通用时序数据库 | 物联网专用时序库 | 基于 PostgreSQL 的时序扩展 | Prometheus 长期存储 |
| 写入性能 | 高 | 很高（超表设计） | 中 | 高 |
| 查询能力 | InfluxQL / Flux，灵活 | SQL，超表聚合快 | 完整 SQL | PromQL，与 Prometheus 一致 |
| 集群能力 | 开源版单机，集群版收费 | 开源支持集群 | 需要 TimescaleDB 企业版或手动分片 | 开源支持集群 |
| 生态集成 | Prometheus Remote Write、Grafana | 自有生态 | PostgreSQL 生态 | Prometheus 原生兼容 |
| 压缩比 | 中 | 高（列式存储 + 专用压缩） | 中 | 高 |
| 社区成熟度 | 高 | 中（国内活跃） | 高 | 高 |

冷热分层的核心思想：

| 层级 | 数据范围 | 存储 | 访问频率 | 典型查询 |
| --- | --- | --- | --- | --- |
| 热数据 | 近 7-30 天 | InfluxDB（SSD） | 高 | 监控大屏、告警上下文、短趋势 |
| 温数据 | 30-180 天 | InfluxDB 降采样数据 | 中 | 周期分析、月度报表 |
| 冷数据 | 180 天以上 | 对象存储（Parquet 格式） | 低 | 年度趋势、复盘分析、模型训练 |

#### 项目中的具体场景

本项目的时序数据规模估算：

| 维度 | 数值 |
| --- | --- |
| 设备数量 | 900 余台 |
| 每台设备测点数 | 约 20-50 个 |
| 平均采集频率 | 5 秒 |
| 每秒数据点 | 900 × 30 × 0.2 ≈ 5400 点/秒 |
| 每天数据点 | 约 4.7 亿 |
| 每条数据大小 | 约 200 字节 |
| 每天原始数据量 | 约 88 GB |

按这个规模，InfluxDB 单机版（配合 SSD）完全能承载热数据阶段的写入和查询。冷热分层的价值在于：180 天后的历史数据不再需要高频查询，转入对象存储后存储成本降低 80% 以上。

InfluxDB 的数据保留策略配置：

```
# 热数据保留 30 天，自动过期
CREATE RETENTION POLICY "hot" ON "device_telemetry" DURATION 30d REPLICATION 1

# 温数据（降采样后）保留 180 天
CREATE RETENTION POLICY "warm" ON "device_telemetry" DURATION 180d REPLICATION 1

# 连续查询：每 5 分钟聚合一次
CREATE CONTINUOUS QUERY "cq_5m" ON "device_telemetry"
  BEGIN
    SELECT mean("value"), max("value"), min("value"), count("value")
    INTO "warm"."telemetry_5m"
    FROM "hot"."telemetry"
    GROUP BY time(5m), "deviceId", "metricCode"
  END
```

#### 架构师决策点

我没有选择 TDengine。原因是：虽然 TDengine 的写入性能和压缩比更好，但本项目的指标监控体系已经基于 Prometheus 建设，InfluxDB 可以通过 Prometheus Remote Write 无缝对接，降低运维成本。同时，InfluxDB 社区成熟度更高，遇到问题更容易找到解决方案。对于 900 台设备的数据规模，InfluxDB 单机版完全够用，不需要 TDengine 的集群能力。

我也没有选择 TimescaleDB。原因是：本项目的时序数据查询以时间范围查询为主（"最近 1 小时的温度趋势"），不需要 TimescaleDB 的完整 SQL 能力。而 TimescaleDB 基于 PostgreSQL，在高频写入场景下的性能不如 InfluxDB。

我更没有选择全量数据都存在 InfluxDB 中。原因是：180 天后的历史数据查询频率很低，但占用的存储空间很大。通过降采样后转入对象存储（Parquet 格式），存储成本降低 80% 以上，且 Parquet 的列式压缩对分析查询依然友好。

### 2.3 技术点三：实时数据处理链路

#### 技术解释

实时数据处理是在数据产生后尽快完成状态更新、窗口聚合和异常识别的计算方式。它与规则引擎的区别在于：规则引擎是业务层的告警判定（"温度超过 85℃ 触发告警"），流处理是数据层的实时计算（"最近 5 分钟的平均温度""设备状态是否连续异常""同类设备的指标是否偏移"）。

两者的关系：

| 维度 | 流处理 | 规则引擎 |
| --- | --- | --- |
| 定位 | 数据层实时计算 | 业务层告警判定 |
| 输入 | 原始遥测数据流 | 已标准化的数据或事件 |
| 输出 | 聚合指标、状态更新、特征值 | 告警事件 |
| 典型操作 | 窗口聚合、状态机、CEP 模式匹配 | 阈值判断、组合条件、时间窗口规则 |
| 技术选型 | Flink、Kafka Streams | Drools、自研规则引擎 |

#### 项目中的具体场景

本项目中，实时数据处理承担以下职责：

| 处理任务 | 说明 | 输出 |
| --- | --- | --- |
| 设备状态更新 | 每条遥测数据到达后更新设备最新状态 | Redis 中的设备实时状态 |
| 窗口聚合 | 按 1 分钟/5 分钟窗口计算均值、最大值、最小值 | 聚合指标写入 InfluxDB |
| 连续异常识别 | 设备温度连续 N 次超限、振动持续偏高 | 异常事件（供规则引擎消费） |
| 数据清洗与去重 | 按 deviceId + timestamp 去重，修正时间乱序 | 清洗后的标准数据流 |
| 同类设备对比 | 同型号设备同时段指标偏移检测 | 横向偏移事件 |

实时处理链路：

```
Kafka(device.telemetry.standard)
  → 流处理引擎
    ├── 分支 1: 更新 Redis 设备最新状态
    ├── 分支 2: 窗口聚合 → InfluxDB(DWS)
    ├── 分支 3: 连续异常检测 → Kafka(abnormal.event.detected)
    └── 分支 4: 清洗去重 → Kafka(device.telemetry.clean)
        → 规则引擎消费
```

#### 架构师决策点

我没有把所有实时处理都放在规则引擎中。原因是：规则引擎擅长"基于单条数据或简单条件做判定"，不擅长"维护状态、做窗口计算、做跨设备对比"。例如"最近 5 分钟平均温度"需要维护一个滑动窗口，"同类设备同时段偏移"需要同时读取多台设备的数据——这些是流处理的强项，不是规则引擎的职责。

我也没有引入 Flink 集群。原因是：本项目的实时处理需求相对简单（状态更新、窗口聚合、去重），Kafka Streams 配合消费组就能满足，不需要 Flink 的复杂流处理能力。引入 Flink 会增加运维复杂度和团队学习成本。如果后续需求升级（如复杂 CEP 模式识别），再考虑引入 Flink 也不迟。

### 2.4 技术点四：离线分析与数据湖仓

#### 技术解释

离线分析处理的是"不着急但要全面"的场景：历史趋势分析、管理驾驶舱、跨基地对比、预测性维护模型训练。这些场景的特点是：数据量大、时间跨度长、计算复杂，但不要求秒级响应。

数据湖仓（Lakehouse）是近年来的架构趋势，核心思想是：在数据湖的低成本存储之上，叠加数据仓库的管理能力（Schema 管理、事务支持、查询优化），实现"湖的灵活性 + 仓的规范性"。

#### 项目中的具体场景

本项目中，离线分析和数据湖仓承担的职责：

| 分析场景 | 数据范围 | 计算频率 | 消费方 |
| --- | --- | --- | --- |
| 设备可用率统计 | 全量设备 × 30 天 | 每日 | 驾驶舱、基地对比 |
| 故障率趋势 | 全量设备 × 12 个月 | 每周 | 管理层报表 |
| 工单处理时效 | 全量工单 × 6 个月 | 每日 | 运维绩效看板 |
| 预测性维护特征 | 单设备 × 3-6 个月测点趋势 | 每周 | 预测模型训练 |
| 跨基地对比分析 | 3 个基地 × 季度 | 每月 | 集团管理驾驶舱 |

湖仓分析层的数据组织——主题建模：

| 主题 | 核心实体 | 关联维度 | 典型指标 |
| --- | --- | --- | --- |
| 设备主题 | 设备档案、运行状态、测点汇总 | 基地、产线、设备类型 | 可用率、故障率、MTTR、OEE |
| 告警主题 | 告警事件、处理结果 | 告警级别、设备、基地 | 告警数量、闭环率、平均响应时间 |
| 工单主题 | 工单流转、处置记录 | 工单类型、优先级、处理人 | 及时率、平均处理时长、积压量 |
| 运维绩效主题 | 人员工作量、处置效率 | 班组、基地、时间段 | 人均处理量、一次修复率 |

降采样策略：

| 数据粒度 | 保留时间 | 存储位置 | 用途 |
| --- | --- | --- | --- |
| 原始秒级 | 7 天 | InfluxDB hot | 实时监控、告警上下文 |
| 5 分钟聚合 | 30 天 | InfluxDB hot | 短趋势分析 |
| 1 小时聚合 | 180 天 | InfluxDB warm | 周期分析、月度报表 |
| 日级聚合 | 3 年 | 对象存储（Parquet） | 年度趋势、复盘、模型训练 |

#### 架构师决策点

我没有建设独立的数据仓库集群（如 ClickHouse 集群）。原因是：本项目的分析场景以设备运维指标为主，数据量和查询复杂度不如互联网公司的用户行为分析。InfluxDB 的连续查询配合 MySQL 汇总表，已经能支撑驾驶舱和基地对比的查询需求。如果后续分析场景升级（如需要复杂的 Ad-hoc 查询），再引入 ClickHouse 也不迟。

我也没有采用纯数据湖方案（如全部写入 HDFS + Spark 分析）。原因是：纯数据湖方案的实时查询能力弱，不能满足监控和告警的秒级响应需求。数据湖仓的价值在于"分层"：实时数据走时序库，分析数据走湖仓层，各取所长。

### 2.5 技术点五：架构模式对比与选型

#### 技术解释

大数据架构有几种经典模式，各有适用场景。架构师的核心工作是根据业务特点选择合适的模式，而不是追求最先进的技术。

| 模式 | 核心思想 | 优点 | 缺点 | 适用场景 |
| --- | --- | --- | --- | --- |
| Lambda | 流 + 批双链路并行 | 兼顾实时和离线 | 两套代码、维护成本高 | 实时和离线需求并存 |
| Kappa | 只用流处理，取消批处理 | 一套代码、架构简单 | 历史重算成本高、不适合复杂聚合 | 以实时为主、少量回放 |
| HTAP | 事务+分析一体化 | 省去 ETL、实时分析 | 分析性能不如专用 OLAP、成本高 | 业务数据量大且需要实时分析 |
| 湖仓一体 | 数据湖 + 仓库融合 | 灵活、成本低、支持多范式 | 架构复杂度高 | 多源数据沉淀和分析 |

#### 项目中的具体场景

本项目的架构模式选择——更接近 Lambda 架构：

| 链路 | 处理方式 | 数据流 | 用途 |
| --- | --- | --- | --- |
| 实时链路 | 流处理 + 规则引擎 | Kafka → 流处理 → InfluxDB/Redis | 监控、告警、状态更新 |
| 离线链路 | 批处理 + 降采样 | InfluxDB → 连续查询/定时任务 → 汇总层/湖仓 | 驾驶舱、趋势分析、模型训练 |

为什么没有选择其他模式：

| 模式 | 不选择的原因 |
| --- | --- |
| 纯 Kappa | 降采样和指标汇总是天然的批处理场景（"每天凌晨计算昨日设备可用率"），Kappa 取消批处理反而增加复杂度 |
| HTAP | 本项目的分析需求主要在时序数据（设备遥测），不在业务数据（工单、告警）。HTAP 的优势是"业务数据实时分析"，但本项目不需要对工单表做实时 OLAP 查询 |
| 纯数据湖 | 实时监控和告警要求秒级响应，纯数据湖的查询延迟不能满足 |

#### 架构师决策点

我选择 Lambda 架构不是因为它是"最先进"的，而是因为本项目的需求天然分为两类：实时类（监控、告警，要求低延迟）和分析类（驾驶舱、趋势，要求长周期聚合）。Lambda 的"流+批双链路"正好对应这两类需求。

但我也没有完全照搬经典 Lambda 架构。经典 Lambda 的问题是"两套代码维护成本高"——同一个指标要在流处理和批处理中各算一遍。我的简化方案是：实时链路只做"状态更新和窗口聚合"，不做复杂指标计算；复杂指标（设备可用率、故障率等）统一在离线链路中计算，结果写入缓存供驾驶舱消费。这样实时链路保持简单，离线链路负责准确性，避免了"两套代码算出不同结果"的问题。

### 2.6 技术点六：指标体系与数据质量治理

#### 技术解释

指标体系定义"算什么、怎么算、谁使用"，数据质量治理保证"数据完整、准确、一致、可追溯"。两者是数据架构能否真正服务业务的关键——没有统一指标，分析结果不可信；没有质量治理，垃圾数据进、垃圾结果出。

#### 项目中的具体场景

核心指标定义（必须统一口径）：

| 指标 | 定义 | 计算方式 | 数据来源 |
| --- | --- | --- | --- |
| 设备可用率 | 设备实际运行时间 / 计划运行时间 | 日级汇总 | 设备状态事件 |
| 故障率 | 故障次数 / 运行时间 | 月度汇总 | 告警事件 + 设备状态 |
| MTTR（平均修复时间） | 故障修复总时间 / 故障次数 | 月度汇总 | 工单事件 |
| 工单及时率 | 在 SLA 内处理的工单 / 总工单 | 日级汇总 | 工单事件 |
| 告警闭环率 | 已闭环告警 / 总告警 | 日级汇总 | 告警事件 + 工单事件 |
| OEE（设备综合效率） | 可用率 × 性能率 × 良品率 | 日级汇总 | 多源数据关联 |

数据质量问题及治理方案：

| 问题 | 来源 | 治理方式 |
| --- | --- | --- |
| 重复数据 | 边缘补传、MQTT 重发 | 写入时按 deviceId + timestamp 去重 |
| 时间乱序 | 网络延迟、边缘缓存补传 | 写入时排序，乱序数据标记 quality=time_unsync |
| 测点缺失 | 设备断连、采集失败 | 缺失超过阈值触发离线告警，分析时插值标记 |
| 口径不一致 | 测点映射变更、配置版本差异 | 通过 configVersion 追溯，分析时按版本对齐 |
| 设备编码不一致 | 多基地历史数据编码规则不同 | 主数据统一映射，建立编码对照表 |
| 告警分类不统一 | 各基地告警规则定义不同 | 统一告警等级和分类标准 |

数据血缘追溯：

每条数据从产生到消费的完整链路都有记录：

```
设备上报（sourceProtocol, sourceAddress）
  → 边缘采集（configVersion, edgeId, quality）
  → 中心接入（ingestTime, processTime）
  → 入库存储（storageTime, retentionPolicy）
  → 降采样聚合（aggregationLevel, aggregationTime）
  → 应用消费（queryTime, consumerId）
```

当指标出现异常时，可以通过血缘信息快速定位：是数据源问题（设备异常）、采集问题（配置变更）、处理问题（降采样错误）还是消费端问题（查询条件错误）。

#### 架构师决策点

我没有让各基地自行统计指标再汇总。原因是：如果每个基地对"设备可用率"的定义不同（有的按日历时间算、有的按计划排产时间算），总部看到的横向对比就没有意义。统一指标必须从数据源头做起——统一设备状态事件的定义、统一计算公式、统一统计周期，然后在 DWS 层集中计算，各基地和总部消费同一份指标结果。

### 2.7 技术点七：查询优化与多场景服务

#### 技术解释

同一批数据要服务多种场景，每种场景的查询模式不同。查询优化的核心是：为不同的查询模式选择最合适的数据存储和索引策略，而不是让所有查询都走同一条路径。

#### 项目中的具体场景

| 查询场景 | 查询模式 | 数据范围 | 优化策略 |
| --- | --- | --- | --- |
| 监控大屏 | 单设备最新状态 | 最新一条 | Redis 缓存，不查时序库 |
| 告警上下文 | 单设备近 N 分钟趋势 | 数分钟 | InfluxDB 热数据，按 deviceId + time 索引 |
| 趋势分析 | 单设备数天/数周趋势 | 数天 | InfluxDB 降采样数据（5 分钟/1 小时聚合） |
| 驾驶舱 | 多设备多基地聚合指标 | 30 天 | MySQL 汇总表 + Redis 缓存 |
| 跨基地对比 | 按基地聚合对比 | 季度 | 湖仓分析层预计算 |
| 历史复盘 | 特定时段原始数据 | 指定时间段 | 对象存储 Parquet 文件 + 列式查询 |
| 预测性维护 | 单设备数月测点特征 | 3-6 个月 | 湖仓分析层批量导出 |

#### 架构师决策点

我没有让所有查询都走 InfluxDB。原因是：监控大屏需要"设备最新状态"，如果每次都查 InfluxDB 最新一条记录，900 台设备 × 30 个测点 = 27000 次查询，时序库压力大。用 Redis 缓存设备最新状态，查询延迟从毫秒级降到微秒级，且不占用时序库的查询资源。

我也没有让驾驶舱直接查询明细数据做聚合。原因是：驾驶舱的"本月各基地设备可用率"需要扫描全月数据并聚合，如果每次都从明细数据实时计算，查询时间不可接受。通过 DWS 层的预计算，驾驶舱查询直接读取汇总结果，响应时间从秒级降到毫秒级。

## 3. 论文主体内容（约 1500 字）

在本项目中，数据架构设计不是某个单点技术的选择，而是围绕设备运维数据的完整生命周期进行的系统性规划。平台覆盖 3 个生产基地、900 余台设备和 24 台边缘节点，每天持续产生设备状态、测点值、告警事件、工单流转和处置结果数据。实时监控和告警要求平台能够低延迟处理最新数据，集团驾驶舱和趋势分析要求平台能够沉淀长周期历史数据并形成统一指标，预测性维护要求数据连续、口径一致。这些需求的访问模式完全不同——实时类要求秒级响应，分析类要求长周期聚合——如果把所有数据都简单堆在同一种存储中，必然互相干扰。

在架构模式选型上，我评估了 Lambda、Kappa、HTAP 和纯数据湖四种方案。Kappa 架构只用流处理，适合以实时为主的场景，但本项目的降采样和指标汇总是天然的批处理场景，取消批处理反而增加复杂度。HTAP 数据库（如 TiDB）可以在同一系统中支撑事务和分析，但本项目的分析需求主要在时序数据而非业务数据——工单和告警的数据量不大，MySQL 完全够用，HTAP 的优势发挥不出来。纯数据湖方案的查询延迟不能满足监控和告警的秒级需求。因此，我采用更接近 Lambda 的架构：实时链路通过 Kafka、流处理引擎和 InfluxDB 支撑监控与告警，离线链路通过降采样、汇总任务和湖仓分析层支撑驾驶舱与趋势分析。

在数据分层上，我把数据组织为四层。原始层保存 Kafka 中的原始事件和对象存储中的长期归档，用于数据回放和问题复盘；明细层保存清洗后的设备状态、告警和工单明细，InfluxDB 承载时序明细，MySQL 承载业务明细；汇总层按设备、基地、班组和时间周期聚合指标，通过 InfluxDB 连续查询和 MySQL 汇总表实现；应用层面向驾驶舱和报表提供最终指标结果，通过 Redis 缓存加速。分层的核心价值是：上游变化不直接影响下游，同一指标只在 DWS 层计算一次，上层应用消费同一份结果，避免"同一指标不同页面显示不同数字"。

在时序数据存储上，我选型 InfluxDB 而非 TDengine 或 TimescaleDB。选 InfluxDB 不是因为它性能最好，而是因为本项目的指标监控体系已基于 Prometheus 建设，InfluxDB 可以通过 Prometheus Remote Write 无缝对接，降低运维成本。对于 900 台设备、约 5400 点/秒的写入规模，InfluxDB 单机版完全够用。冷热分层策略为：近 30 天数据保留在 InfluxDB 热数据层，通过连续查询生成 5 分钟和 1 小时聚合数据；180 天后的历史数据转入对象存储（Parquet 格式），存储成本降低 80% 以上。实时处理和规则引擎的职责边界也做了明确划分：流处理负责数据层的窗口聚合、状态更新和去重，规则引擎负责业务层的告警判定，两者通过 Kafka 事件衔接。

在指标治理上，我要求设备可用率、故障率、MTTR、工单及时率等核心指标统一定义、统一计算、统一发布。各基地不自行统计指标，而是在 DWS 层集中计算后供各基地和总部消费。对于数据质量问题——边缘补传导致的重复、网络波动导致的时间乱序、测点映射变更导致的口径不一致——在写入时去重、在处理时排序、在分析时通过 configVersion 追溯和对齐。每条数据从设备上报到最终消费的完整血缘都有记录，当指标异常时可以快速定位问题环节。

从项目效果看，数据架构设计使平台同时具备了实时响应和长期分析能力。实时链路支撑了设备状态监控和告警联动，驾驶舱和趋势分析基于预计算指标快速响应，历史数据通过冷热分层低成本保留。回顾整个项目，我认为数据架构的关键不在于堆叠技术组件，而在于根据数据的真实访问模式建立分层、分链路、分场景的处理体系，使平台真正把设备数据转化为运维和管理能力。
