# 技术十二：负载均衡与流量分发

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

负载均衡与流量分发本质上属于平台入口治理和高可用保障能力，解决的不是单个业务功能问题，而是“请求如何稳定进入系统、如何被合理分发、如何在故障和扩容场景下保持连续服务”的问题。

在一个分布式平台里，它通常承担四类职责：

- 统一入口：把来自不同终端和不同来源的请求汇聚到统一访问入口
- 流量分发：将请求分发给多个后端实例，避免单点过载
- 故障隔离：在后端节点异常时快速摘除故障实例
- 平滑演进：支撑横向扩容、滚动升级、灰度切流

因此，负载均衡不是一个孤立组件，而是入口层、网关层、服务层协同治理的一部分。

### 1.2 从考题角度看

这个技术方向常见于以下题型：

- 高可用架构设计
- 性能优化设计
- 分布式系统设计
- 服务治理设计
- 微服务架构设计

如果题目是“高可用”“高并发”“微服务治理”，负载均衡通常都是正文里的关键技术点；如果题目是“大数据”或“Serverless”，它未必是中心主题，但仍可作为入口稳定性和流量治理的支撑能力写入方案。

### 1.3 从项目角度看

在本项目中，负载均衡的必要性来自三个现实约束：

1. 平台要同时承接 3 个生产基地 24 台边缘节点的数据上传请求，以及总部和基地运维人员的 Web、移动端访问请求
2. 监控、告警、工单、权限等核心服务不能依赖单实例运行，否则任一节点异常都会影响设备运维主链路
3. 项目采用分 3 期交付，后续还要持续扩展新设备、新基地和新模块，因此必须具备平滑扩容和不停机发布能力

也就是说，本项目写负载均衡，重点不是“流量很大所以要分发”，而是“平台入口必须稳定、后端服务必须能扩、上线发布必须可控”。

## 2. 技术分析

这一部分只写和项目强相关的技术点，并明确区分“项目现网采用”与“考试可延展点”。

### 2.1 技术点一：DNS 与 VIP

#### 技术解释

- `DNS` 用于把平台统一访问域名解析到入口地址
- `VIP` 是对外暴露的统一虚拟入口地址，用于屏蔽后端节点变化（配合 Keepalived 使用，实现高可用）

#### 项目中的使用场景

本项目中，3 个基地的边缘节点、总部 Web 用户和基地移动端用户，都不直接访问后端业务服务，而是统一访问平台域名。平台域名解析后指向入口层 `VIP`，由入口层继续向下分发流量。

典型链路可以写为：

`边缘节点/WEB端/移动端 -> 内网 DNS -> VIP -> 入口负载均衡层`

#### 为什么这样贴合项目

因为本项目是集团统一平台，入口地址必须稳定。后端节点是否扩容、替换、升级，不应影响各基地边缘节点和运维人员的访问配置。通过统一域名和 `VIP`，可以把入口地址与后端部署解耦。

#### 考试可延展点

如果题目强调跨地域高可用或双活多中心，可以把这里延展为：

- `GeoDNS`
- 全局流量调度
- 多入口区 `VIP`

但就本项目主线而言，写“内网 DNS + VIP”更真实。

### 2.2 技术点二：LVS（DR）

#### 技术解释

`LVS（DR，Direct Routing）` 属于四层负载均衡方案，适合高性能、低开销的 TCP/HTTP 入口流量分发。

它的优势在于：

- 四层处理性能高
- 对后端透明
- 适合承接大量连接请求

#### 项目中的使用场景

本项目的平台入口层需要同时承接来自边缘节点的持续上传请求和来自用户侧的访问请求。如果把所有入口压力都直接压在 `Nginx` 上，七层处理开销较大，也不利于构建稳定的入口区。因此更合理的方式是先由 `LVS（DR）` 处理四层流量分发，再把流量送到 `Nginx` 集群。

项目链路可以写为：

`边缘节点/WEB端/移动端 -> DNS -> VIP -> LVS（DR） -> Nginx 集群`

#### 为什么这样贴合项目

这个项目不是纯互联网门户，而是既有机器接入流量，又有人员访问流量。入口压力模型比较复杂，四层负载均衡更适合作为第一层入口。

### 2.3 技术点三：Nginx

#### 技术解释

`Nginx` 主要承担七层反向代理能力，包括：

- TLS 终止
- URI 路由
- Header 处理
- 限流
- 反向代理

#### 项目中的使用场景

在本项目中，`Nginx` 放在 `LVS` 之后，作为七层代理层。它把不同类型的请求按路径或域名分流给 `API 网关` 或特定服务入口，例如：

- `/api/device/**` 走设备接入相关链路
- `/api/alarm/**` 走告警链路
- `/api/workorder/**` 走工单链路
- `/api/auth/**` 走认证与权限链路

如果需要在论文里写具体一点，可以写为：

`LVS（DR） -> Nginx 集群 -> API 网关 -> 各业务服务`

#### 为什么这样贴合项目

本项目后端既有设备数据接入请求，又有用户访问请求，协议处理和业务路径转发不能全部放在四层完成，因此七层代理层是必要的。

### 2.4 技术点四：API 网关

#### 技术解释

`API 网关` 属于应用层网关，主要负责：

- 鉴权前置
- 业务域路由
- 灰度发布
- 限流与熔断前置

#### 项目中的使用场景

在本项目中，`API 网关` 不直接面对公网或内网最终用户，而是位于 `Nginx` 之后，承接平台业务层的统一路由和治理。它根据业务域将流量继续分发到：

- 监控服务
- 告警服务
- 工单服务
- 权限服务
- 报表分析服务

典型链路可写为：

`Nginx -> API 网关 -> 监控服务/告警服务/工单服务/权限服务`

#### 为什么这样贴合项目

因为本项目是微服务平台，七层代理和业务路由要分层治理：`Nginx` 更偏入口代理，`API 网关` 更偏服务治理。

### 2.5 技术点五：健康检查、灰度切流与滚动升级

#### 技术解释

负载均衡真正有价值，不只是“把请求分给多个节点”，而是要配合：

- `健康检查`
- `灰度发布`
- `滚动升级`
- 自动摘除故障节点

#### 项目中的使用场景

本项目分 3 期交付，且后续仍会持续优化，因此上线时不可能每次都停机切换。更稳的做法是：

1. 先部署新版本实例
2. 用健康检查确认新实例可用
3. 通过 `Nginx/API 网关` 逐步切入部分流量
4. 观察稳定后再扩大流量比例
5. 旧实例逐步摘除

这部分很适合写在论文里作为“工程落地能力”，因为它能体现架构师不是只会设计图，而是考虑到了发布、运维和稳定性。

## 3. 论文主体内容（约 1300 字）

在本项目的总体架构设计中，负载均衡并不是一个简单的入口组件，而是保障平台稳定运行和持续演进的关键基础设施。项目面向集团 3 个生产基地，既要承接 24 台边缘节点持续上报的设备数据，也要承接总部和基地运维人员通过 Web 与移动端发起的业务访问。如果平台入口仍采用传统单实例模式，那么一旦访问高峰到来，或者某个节点故障，就可能导致监控、告警、工单等关键链路整体受阻，进而影响设备运维工作的连续性。因此，在负载均衡设计上，我并没有把它理解为单一的流量转发问题，而是把它作为平台入口治理、高可用设计和服务演进控制的一体化能力来建设。

在方案选型阶段，我首先分析了本项目的入口流量特点。与一般纯业务系统不同，本项目的入口流量由两部分组成：一部分是边缘节点持续上报的设备状态、事件和测点数据，这类流量数量大、持续性强；另一部分是运维人员对监控看板、告警中心、工单系统和报表系统的交互访问，这类流量对七层转发、鉴权和路由能力要求更高。基于这一特征，我没有简单地把所有入口请求都交给单层 `Nginx` 处理，而是设计了分层负载均衡架构：最前端由统一域名和 `VIP` 提供稳定访问入口，四层采用 `LVS（DR）` 进行高性能流量分发，七层通过 `Nginx` 集群承担反向代理和协议处理，再由 `API 网关` 根据业务域将请求路由至监控、告警、工单、权限等后端服务。这样做的好处是，每一层只承担自己最擅长的能力，既避免了入口层功能过度堆积，也便于后续按层扩展和治理。

在具体落地过程中，我重点把负载均衡能力和项目主链路结合起来，而不是把它设计成孤立的基础设施。对于边缘节点侧，上报请求统一通过平台域名访问入口区，由内网 `DNS` 解析到 `VIP`，再进入 `LVS（DR）` 集群进行四层分发，从而保证设备侧不感知后端节点变化。对于用户侧，Web 和移动端请求同样经由统一入口进入平台，再由 `Nginx` 和 `API 网关` 完成七层路由、协议处理和业务分发。这样设计以后，无论是监控服务扩容、告警服务升级，还是工单服务迁移，入口地址和访问路径都不需要变更，既降低了运维复杂度，也提高了系统的可维护性。同时，为了避免负载均衡只停留在“流量分发”层面，我还要求团队在入口层引入健康检查机制，能够在后端实例异常时自动摘除故障节点，把流量切到健康实例，减少局部故障扩散为全局故障的风险。

负载均衡在本项目中的另一个关键价值，是支撑分 3 期交付和后续持续优化。由于平台不是一次性上线，而是要随着设备接入范围扩大和功能模块逐步完善而持续演进，因此每次版本发布都必须控制对现网的影响。如果没有分层流量治理能力，所有升级都只能依赖停机切换，既影响业务连续性，也不利于问题回滚。针对这一问题，我在设计中把灰度切流、滚动升级和健康检查纳入统一流量治理体系。具体做法是：先部署新版本实例，通过健康检查验证可用性，再由 `Nginx` 或 `API 网关` 将部分流量切入新版本，观察稳定后逐步扩大流量比例，最终摘除旧实例。这样一来，平台既具备了不停机升级能力，也能够在问题出现时快速回退到旧版本。对于一个需要长期服务集团设备运维主链路的平台而言，这种能力往往比单纯追求理论吞吐量更重要。

从项目效果看，负载均衡与流量分发设计有效支撑了平台入口稳定性和后端服务弹性。它一方面降低了单实例故障对整体平台的影响，另一方面也为监控、告警、工单、权限等核心服务的多实例部署提供了基础条件。更重要的是，这一设计使平台具备了平滑扩容、滚动发布和持续演进的能力，与项目分期建设、持续优化的推进方式形成了良好匹配。回顾整个过程，我认为负载均衡在本项目中并不是配角，而是连接入口治理、高可用设计和微服务演进的关键枢纽。正是因为把它放在平台整体架构中统筹考虑，而不是孤立地看作一个网络组件，平台才能在承载多基地设备接入与多角色业务访问的同时，保持稳定、可扩展和可持续演进。
