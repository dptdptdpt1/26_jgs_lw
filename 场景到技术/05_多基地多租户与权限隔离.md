# 场景五：多基地多租户与权限隔离

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 场景定位

### 1.1 从业务角度看

多基地多租户与权限隔离解决的是“集团统一平台如何既能共享，又能保证边界清晰”的问题。它体现的是平台从功能可用走向集团级治理的能力。

在本项目中，总部需要跨基地监管，基地需要本域自治，车间和班组又需要按职责访问设备、告警、工单和报表。如果权限体系设计不清，平台推广范围越大，越权风险和管理混乱就越明显。

### 1.2 从考题角度看

这个场景适合以下题目：

- 安全架构设计
- 权限体系设计
- 多租户平台设计
- 企业统一平台治理
- 安全与审计设计
- 数据访问控制设计

如果题目涉及“权限”“安全”“多租户”“集团化治理”“审计”，这个场景都非常适合展开。写作时要区分身份认证、功能权限、数据权限和审计追溯。

### 1.3 从项目角度看

本项目面向总部和 3 个生产基地统一建设。如果平台不能同时满足总部监管、基地隔离、角色分工和敏感操作审计，系统即使功能完整，也难以在集团范围长期推广。

因此，该场景承担的是“平台治理边界”的关键作用。

## 2. 场景拆解

### 2.1 业务目标与成功标准

该场景的目标包括：

- 总部能够统一监管集团设备运维情况
- 基地用户只能访问本基地或职责范围内的数据
- 不同角色拥有不同功能和操作权限
- 敏感操作能够被审计和追溯
- 权限模型能够支持后续新增基地、角色和组织层级

成功标准体现为：

- 平台共享但不越权
- 功能权限和数据权限边界清晰
- 权限规则可配置、可审计、可扩展
- 关键操作可追溯，异常访问可发现

### 2.2 场景边界

这个场景重点解决身份统一、角色权限、数据域隔离和审计追溯。

它不直接解决网络安全、主机加固和工业控制安全，也不替代业务流程审批。它关注的是应用平台层的访问控制：谁可以登录、能做什么、能看哪些数据、做过什么操作。

### 2.3 核心矛盾与约束条件

该场景的核心矛盾包括：

1. 总部需要跨基地看整体，基地用户只应访问本域
2. 角色分工复杂，不能只有管理员和普通用户
3. 功能权限和数据权限是两类问题，不能混为一谈
4. 统一平台一旦推广，越权影响范围会扩大
5. 权限规则会随组织和流程调整而变化
6. 关键管理动作必须可追溯，否则难以审计和定责

这意味着平台不能只做基础登录，而必须把身份、角色、数据域和审计统一纳入设计。

### 2.4 备选方案与舍弃理由

| 备选方案 | 表面优势 | 舍弃原因 |
| --- | --- | --- |
| 每个模块各自维护账号权限 | 开发独立 | 账号重复、权限口径不一致，审计困难 |
| 只做菜单级权限 | 实现简单 | 用户进入模块后仍可能看到越权数据 |
| 为每个基地单独部署系统 | 隔离彻底 | 无法支撑总部统一监管，运维成本高 |
| 所有权限靠管理员手工配置 | 灵活 | 规模扩大后易出错，缺少规则化治理 |

因此，我采用“统一认证中心 + RBAC 功能权限 + 数据域隔离 + 审计日志”的复合方案。

### 2.5 架构决策与边界划分

该场景按四层设计。

第一层是身份认证层。通过统一认证中心和单点登录机制统一用户身份，避免各模块重复维护账号。

第二层是功能权限层。通过 `RBAC` 控制菜单、按钮、接口和操作能力，例如查看告警、关闭工单、调整规则等。

第三层是数据权限层。通过组织、基地、车间、产线和设备等数据域控制可见范围。

第四层是审计追溯层。记录权限变更、规则调整、强制关闭工单、导出报表等敏感操作。

### 2.6 关键机制设计

#### 2.6.1 认证与授权分离

统一认证中心负责确认“你是谁”，权限服务负责判断“你能做什么”。用户登录后获得令牌，API 网关完成基础鉴权，业务服务结合角色和数据域进行细粒度控制。

这种分离避免了每个业务模块重复实现认证逻辑，也便于统一接入后续单点登录和组织目录。

#### 2.6.2 功能权限与数据权限分离

功能权限控制操作能力，数据权限控制可见范围。例如总部设备管理人员和基地运维工程师都可以进入监控模块，但总部人员可以查看跨基地汇总，基地人员只能查看本基地设备。

如果只做功能权限，用户进入模块后仍可能越权查看数据；如果只做数据权限，又无法控制敏感操作。因此两者必须同时设计。

#### 2.6.3 审计与追溯

权限变更、告警规则调整、强制关闭工单、导出报表等操作都需要记录操作人、时间、对象、前后变化和来源。审计日志不是普通系统日志，而是平台治理能力的一部分。

### 2.7 质量属性与架构权衡

该场景主要支撑以下质量属性。

- `安全性`
  身份、角色、数据域和审计共同控制访问风险。

- `可扩展性`
  新增基地、角色和组织层级时，可以通过规则扩展而非重写代码。

- `可维护性`
  统一认证和权限服务避免各模块重复建设。

- `可审计性`
  敏感操作留痕，支持追溯和定责。

这里的取舍是：权限体系会增加接口和查询复杂度，特别是数据域过滤会影响部分查询性能。因此在设计中需要把权限规则下沉为统一能力，并对常用数据域关系进行缓存或预计算，避免各业务模块重复实现。

### 2.8 技术落点与协同关系

该场景主要落在以下能力上：

- 单点登录
- `OAuth 2.0 / OIDC / JWT`
- `RBAC`
- 数据域隔离
- API 网关鉴权
- 权限服务
- 审计日志
- 敏感操作告警

典型链路可写为：

`用户登录 -> 统一认证中心 -> 令牌签发 -> API网关鉴权 -> 权限服务 -> 业务服务按角色和数据域过滤 -> 审计日志`

### 2.9 项目推进与验证方式

该场景分阶段推进：

- 第一期：建立账户、角色、组织和基础功能权限
- 第二期：补充数据域控制、跨基地授权和敏感操作审计
- 第三期：增强审计分析、安全告警和权限治理报表

验证重点包括越权访问测试、角色切换测试、跨基地数据隔离测试、审计完整性测试和权限变更追踪。

### 2.10 论文转写角度

如果题目是 `安全架构设计`，重点写统一认证、授权、数据隔离和审计。

如果题目是 `多租户平台设计`，重点写总部共享平台与基地数据域隔离。

如果题目是 `权限体系设计`，重点写 RBAC、数据权限和审计追溯。

如果题目是 `企业平台治理`，重点写共享与边界之间的平衡。

## 3. 论文主体内容（约 1300 字）

在本项目中，多基地多租户与权限隔离并不是一个附属安全问题，而是平台能否真正推广落地的前提条件。项目统一服务总部和 3 个生产基地，不同组织、岗位和角色对设备、告警、工单和报表的访问范围有明显差异。如果权限边界定义不清，平台越成功推广，管理混乱和越权风险就越大。因此，在总体架构设计阶段，我把权限体系作为平台基础能力之一，与监控、告警和工单等业务能力同步考虑。

在方案分析阶段，我排除了每个模块各自维护账号权限的做法。这样虽然短期开发独立，但会造成账号重复、权限口径不一致和审计困难。我也没有选择只做菜单级权限，因为用户进入模块后仍可能看到不属于本基地的数据。为此，我采用“统一认证中心 + RBAC 功能权限 + 数据域隔离 + 审计日志”的复合方案，分别解决身份统一、操作控制、数据范围和行为追溯问题。

具体设计上，统一认证中心负责确认用户身份，用户登录后获得令牌，API 网关完成基础鉴权。权限服务基于角色控制功能权限，例如哪些人可以查看告警、关闭工单、调整规则或导出报表。同时，平台通过组织、基地、车间、产线和设备等维度构建数据域，控制用户能够访问的数据范围。这样，总部设备管理人员可以查看跨基地汇总数据，基地运维工程师则只能查看本基地设备和工单。

在实施过程中，我特别强调功能权限和数据权限必须分开处理。功能权限解决“能不能做某个操作”，数据权限解决“能看到哪些对象”。例如总部和基地人员都可以进入监控模块，但看到的数据范围不同；同样是工单模块，普通运维人员只能处理自己被派发的工单，基地负责人可以查看本基地工单统计，总部管理人员则可以查看跨基地趋势。只有把这两类权限分开，平台才能在共享和隔离之间取得平衡。

此外，我没有把审计日志当作普通系统日志，而是把它纳入权限体系。权限变更、告警规则调整、强制关闭工单、报表导出等动作都可能影响运维决策和管理责任，因此必须记录操作人、时间、对象和前后变化。一旦出现权限越界或处置争议，平台能够还原过程并明确责任。

从项目效果看，多基地多租户与权限隔离场景有效支撑了平台在集团层面的统一推广。总部能够通过统一平台掌握跨基地设备运维态势，基地和车间用户也能保持本域视角和职责边界。回顾整个过程，我认为该场景的核心价值不只是防止越权，而是在共享与边界之间建立了一套稳定、可扩展、可审计的治理机制，这是集团型平台建设中非常关键的一环。
