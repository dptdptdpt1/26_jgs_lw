# 技术十一：权限控制与多租户隔离

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

权限控制与多租户隔离解决的是“共享平台如何做到有边界协同”的问题。它关注的不只是登录认证，而是平台在组织结构、角色职责、数据域边界和审计追踪上的整体治理能力。

这一技术方向通常包含：

- 单点登录
- 统一认证中心
- OAuth 2.0 / OIDC / JWT
- RBAC 角色权限模型
- 数据域隔离
- 审计日志

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 安全架构设计
- 权限体系设计
- 企业级治理设计
- 多租户平台设计
- 平台安全合规设计

如果题目涉及“安全”“权限”“多租户”“平台治理”，这一主题都可以直接展开为论文主体。

### 1.3 从项目角度看

在本项目中，平台同时服务总部与 3 个生产基地，不同角色对功能和数据的访问范围有明显差异。如果权限边界设计不好，平台越推广，风险反而越大。

项目中的典型矛盾是：

1. 总部需要跨基地统一监管
2. 基地只应看到本基地数据和工单
3. 车间和班组应进一步收敛访问范围
4. 敏感操作必须可审计、可追踪

因此，本项目的权限体系不是附属模块，而是平台推广的前提条件。

## 2. 技术分析

### 2.1 技术点一：单点登录与统一认证中心

#### 技术解释

单点登录和统一认证中心解决的是“多个模块如何共享统一身份体系”的问题。

#### 项目中的使用场景

本项目中，监控、告警、工单、报表等模块都不应维护自己的账号体系，而应统一接入认证中心。用户登录一次后，即可访问有权限的各类业务模块。

典型链路可写为：

`用户登录 -> SSO/统一认证中心 -> 获取令牌 -> 访问平台模块`

#### 为什么这样贴合项目

因为本项目是集团统一平台，不可能让每个模块、每个基地各自维护一套身份体系，否则后续治理成本极高。

### 2.2 技术点二：OAuth 2.0 / OIDC / JWT

#### 技术解释

这一组技术用于支撑统一认证与令牌传递：

- `OAuth 2.0`：授权框架
- `OIDC`：身份认证扩展
- `JWT`：令牌承载方式

#### 项目中的使用场景

本项目中，用户在统一认证中心登录后，由认证中心签发令牌。后续用户访问监控、告警、工单等模块时，API 网关和业务服务依据令牌中的身份和角色信息完成鉴权。

典型链路可写为：

`用户登录 -> 统一认证中心 -> JWT Token -> API 网关鉴权 -> 业务服务`

#### 为什么这样贴合项目

因为平台是多模块协同系统，如果每次服务调用都重复查询账号状态，性能和治理都会受到影响，令牌机制更适合统一认证后的跨模块访问。

### 2.3 技术点三：RBAC 角色权限模型

#### 技术解释

`RBAC` 用于把功能权限和角色职责绑定起来，解决“谁能看什么、能做什么”的问题。

#### 项目中的使用场景

本项目中，典型角色包括：

- 总部设备管理人员
- 基地运维工程师
- 基地负责人
- 车间班组长
- 系统管理员

每类角色可访问的菜单和操作权限不同。例如：

- 总部人员可查看跨基地统计看板
- 基地运维工程师可处理本基地告警与工单
- 车间班组长只能查看本车间任务与记录

#### 为什么这样贴合项目

因为本项目的主要差异不仅来自数据域，也来自职责分工，角色模型是最自然的权限承载方式。

### 2.4 技术点四：数据域隔离

#### 技术解释

仅有角色权限还不够，平台还需要把访问范围落到数据层，控制用户能看到哪些基地、哪些车间、哪些设备的数据。

#### 项目中的使用场景

本项目的数据域可按以下层级组织：

- 集团
- 基地
- 车间
- 产线
- 设备

业务服务在返回数据前，需要根据用户所属组织与授权范围做过滤。例如：

- 基地运维工程师默认只查看本基地设备、告警和工单
- 总部管理者可按授权查看跨基地汇总数据

#### 为什么这样贴合项目

因为平台本质上是一个集团统一平台，不同组织边界下的数据隔离能力决定了它是否可以真正推广。

### 2.5 技术点五：审计日志

#### 技术解释

审计日志用于记录关键操作，支撑问题追溯和安全合规。

#### 项目中的使用场景

本项目中，以下动作都应纳入审计日志：

- 告警规则变更
- 权限角色调整
- 强制关闭工单
- 基础参数变更
- 高风险设备策略修改

#### 为什么这样贴合项目

因为设备运维平台不是普通办公系统，错误的规则或权限调整可能直接影响生产运维决策，必须留痕可追溯。

## 3. 论文主体内容

在本项目中，权限控制与多租户隔离不是一个后补的安全模块，而是平台能否真正落地推广的基础能力。项目面向总部和 3 个生产基地，涉及设备管理人员、运维工程师、基地负责人、车间班组长等多个角色，不同角色既有功能权限差异，也有数据访问边界差异。如果这些边界定义不清，平台越成功推广，权限越容易失控，最终会导致管理混乱甚至安全风险。因此，在总体架构设计中，我把权限体系作为平台的基础架构能力之一，与监控、告警、工单等核心模块同步设计。

在方案设计阶段，我首先明确本项目不适合采用各模块独立账号体系。原因很简单：平台本身就是一个集团统一运维平台，若监控、告警、工单、报表等模块各自维护用户身份，不仅用户体验差，而且后续权限治理和审计成本会迅速失控。因此，我首先建立了统一认证中心和单点登录机制，让所有业务模块共享同一身份入口。用户完成一次登录后，即可基于统一身份访问其有权限的模块，平台也由此形成清晰一致的身份边界。

在认证与授权机制上，我采用了以 `OAuth 2.0`、`OIDC` 和 `JWT` 为基础的统一认证方式。用户在认证中心登录后获得令牌，后续请求统一经过 API 网关，再由网关和业务服务依据令牌中的身份、角色和组织信息进行鉴权。这种做法的好处在于，身份认证、令牌传递和业务访问边界被分层治理，既减少了业务服务重复处理认证逻辑的负担，也为后续多模块协同访问提供了稳定基础。对于一个需要长期演进的平台而言，这种统一认证模式明显优于模块各自维护会话和账号状态的做法。

在权限模型设计上，我没有停留在“谁能进系统”这一层，而是把功能权限和数据权限分开治理。功能权限层面，我采用 `RBAC` 角色模型，根据总部设备管理人员、基地运维工程师、基地负责人、车间班组长等不同角色划分菜单和操作权限。例如，总部人员可以查看跨基地汇总看板和关键指标，基地运维工程师可以处理本基地工单和告警，车间班组长则只查看本车间任务和处理记录。数据权限层面，我进一步按集团、基地、车间、产线、设备等层级建立数据域隔离机制，在业务服务返回数据之前，根据用户所属组织和授权范围进行过滤。这种设计使平台能够在共享架构之上实现有边界的协同。

此外，我把审计日志作为权限体系的一部分同步纳入设计。因为在设备运维场景中，权限变更、规则调整、强制关闭工单等操作都可能直接影响运维决策和现场处置结果。如果缺少统一审计能力，一旦发生问题，平台就难以追溯责任和还原过程。因此，我要求所有关键管理动作和敏感操作都必须记录审计日志，使平台具备可追踪、可审查和可复盘的治理能力。

从项目效果看，权限控制与多租户隔离设计有效支撑了平台在集团范围内的推广。一方面，总部能够基于统一平台实现跨基地监管，基地又能保持本域自治，解决了过去各基地系统分散、权限边界模糊的问题；另一方面，统一认证、角色控制、数据域过滤和审计留痕形成了完整的安全治理闭环，使平台既能共享，又不失边界。回顾整个项目，我认为权限体系的价值不只是“防止越权”，更重要的是，它让平台从一个可用系统，变成了一个可以在集团范围内稳定运行、可治理、可审计的企业级平台。
