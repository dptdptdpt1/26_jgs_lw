# 技术七：负载均衡与流量分发

## 1. 技术定位

### 1.1 从技术角度看

负载均衡与流量分发解决的核心问题，不只是“把请求平均分到多台服务器”，而是让流量按类型进入合适链路，让服务实例可以横向扩展，让故障实例能够被摘除，让发布过程可以平滑切换。

在本项目中，这一能力更接近“流量分类和运行治理”，而不是互联网大流量入口堆叠。它主要包含：

- 管理类请求与设备遥测数据分流
- API 网关统一入口、鉴权、限流和审计
- Kubernetes Service 对多副本服务做实例分发
- Readiness Probe 和 Liveness Probe 配合摘除异常实例
- Kafka Topic、分区和消费组承接内部事件流分发
- 分基地灰度发布和快速回滚

因此，本项目写负载均衡，重点不是极限吞吐，而是入口稳定、链路隔离、服务可替换和发布可控。

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 负载均衡技术及其应用
- 高可用架构设计
- 性能优化设计
- 微服务治理设计
- 分布式系统架构设计
- 云原生环境下的流量治理

如果题目明确是“负载均衡”，可以作为全文主线；如果题目是“高可用”“微服务”“持续交付”，它适合作为入口稳定和发布治理的关键措施。

### 1.3 从项目角度看

本项目服务于集团 3 个生产基地、900 余台设备和 24 台边缘节点。它不是互联网秒杀系统，HTTP 管理访问量并不大，因此没有必要把负载均衡写成复杂的多层入口架构。本项目真正需要解决的是三类问题：

1. 设备遥测数据持续上报，不能和 Web、移动端、边缘管理类请求挤在同一个 HTTP 入口。
2. 监控、告警、工单、权限等核心服务不能单实例运行，发布或故障时要能自动切换到健康实例。
3. 项目分三期交付，并按基地逐步推广，版本上线需要灰度验证和快速回滚。

所以，我将本项目的负载均衡与流量分发主线收敛为四点：**入口分流、服务多副本、消息消费隔离、分基地灰度**。

## 2. 技术分析

### 2.1 技术点一：入口统一与链路分流

入口层不宜过度设计。对本项目来说，管理类请求和设备遥测数据的流量特征完全不同，应当分开承接。

管理类请求主要来自总部 Web 端、基地运维人员、移动端工单处理和边缘节点管理接口，例如登录、告警查询、工单处理、配置拉取和指令确认。这类请求频率不高，但要求鉴权、审计、限流和业务路由清晰。可以采用：

```text
统一域名 / VIP -> API 网关 -> K8s Service -> Pod
```

设备遥测数据则是持续、高频、批量上报，适合采用：

```text
边缘节点 -> MQTT Broker -> 中心接入服务 -> Kafka
```

这样设计以后，设备测点数据不会挤占 Web 管理入口；管理类接口也不需要承担设备数据通道职责。入口统一解决“访问地址稳定”，链路分流解决“不同流量走不同处理路径”。

### 2.2 技术点二：API 网关和业务入口治理

API 网关在本项目中的价值不是极限转发性能，而是统一治理管理类接口。网关主要负责：

- 用户 JWT 校验
- 边缘节点证书校验
- 接口路由
- 基础限流
- 访问审计
- 分基地灰度路由

例如：

| 请求类型 | 路由方向 | 网关职责 |
| --- | --- | --- |
| Web 端告警查询 | 告警服务 | JWT 校验、接口限流、访问审计 |
| 移动端工单处理 | 工单服务 | 用户校验、角色校验、审计 |
| 边缘节点配置拉取 | 配置服务 | 设备证书校验、edgeId 限流 |
| 边缘节点指令回执 | 接入服务 | 设备身份校验、请求审计 |

完整权限模型仍由权限服务维护，网关只做入口快速拦截和基础校验；工单分派、跨基地查询、临时授权等细粒度权限由业务服务结合权限服务二次判断。这样既避免所有服务各自暴露外部接口，也避免把复杂业务权限全部堆到网关。

### 2.3 技术点三：Kubernetes Service 与多副本分发

中心侧核心服务运行在 Kubernetes 集群中。设备接入、监控、告警、工单、权限和分析服务均采用 Deployment 多副本部署，并通过 K8s Service 提供稳定服务入口。

典型链路为：

```text
API 网关 -> K8s Service -> 多个 Pod 副本
```

调用方只访问 Service，不感知具体 Pod IP。Pod 扩容、重启、滚动升级后，后端实例变化由 Kubernetes 维护。这样可以解决三个问题：

- 单个实例异常不会导致服务整体不可用。
- 新增副本后流量自动分配到健康实例。
- 发布过程中旧版本和新版本可以平滑替换。

同时，Readiness Probe 和 Liveness Probe 要配合使用。Readiness Probe 用于判断实例是否已经具备业务处理能力，未就绪实例不接收流量；Liveness Probe 用于发现进程卡死或异常状态，触发自动重启。对告警服务、工单服务和权限服务这类同步调用链路，Readiness 判断比简单端口探活更重要。

### 2.4 技术点四：服务扩缩容与容量边界

负载均衡不能脱离容量评估。把流量分给更多实例，前提是这些实例真的有足够资源处理请求。

本项目中，监控查询、告警处理和工单处理的压力峰值主要来自三类场景：

- 早班开机后设备状态集中刷新
- 某基地网络恢复后边缘节点补传数据
- 异常告警集中出现后多人查看告警详情和工单

对 HTTP 管理类服务，可以根据 CPU、内存、接口错误率和 P95/P99 延迟配置 HPA；对 Kafka 消费类服务，可以结合消费 Lag、消费速率和处理延迟配置扩容策略。扩容策略不能只看 CPU，因为告警服务可能 CPU 不高但 Kafka Lag 持续增长，说明消费能力已经不足。

同时，扩容不是无限制的。数据库连接池、Redis、Kafka Broker、时序存储和第三方通知通道都有容量边界。因此，我将负载均衡与限流、队列削峰和降级策略配合使用，避免压力被更快传递到后端依赖。

### 2.5 技术点五：Kafka 消费组与内部事件分发

本项目内部大量业务不是 HTTP 同步调用，而是事件驱动。设备遥测、告警事件、工单事件和分析事件进入 Kafka 后，监控服务、告警服务、工单服务和分析服务按 Topic、分区和消费组独立消费。

这一部分不是传统意义的入口负载均衡，但属于内部流量分发能力。

设计要点包括：

- 设备遥测数据按基地、设备或测点选择分区键，兼顾局部顺序和并行处理。
- 监控、告警和分析使用不同消费组，避免分析任务慢消费影响实时告警。
- 告警链路消费组配置更高优先级和独立资源。
- 报表分析允许延迟，不抢占实时监控和告警处理能力。
- 消费 Lag 进入监控，作为扩容和故障排查依据。

这样，系统不仅能分发外部请求，也能在内部事件流上实现消费隔离。对本项目而言，这一点比复杂 HTTP 入口堆叠更有价值。

### 2.6 技术点六：分基地灰度发布与回滚

本项目采用三期交付，并且系统覆盖多个生产基地，因此发布策略不能只写“滚动更新”。更贴合项目的做法是分基地灰度。

常规服务版本通过 Kubernetes 滚动更新逐步替换副本，新 Pod 通过 Readiness 检查后再接收流量。对于影响告警规则、工单流程、边缘配置下发或数据处理链路的版本，则优先选择一个基地灰度运行：

```text
基地 A 小范围验证 -> 观察核心指标 -> 扩大到基地 B -> 最后推广到全部基地
```

观察指标包括接口错误率、接口延迟、告警生成延迟、Kafka Lag、工单创建成功率、边缘节点在线率和业务投诉。如果指标异常，可以通过网关路由、配置回滚或 Deployment 回滚快速切回旧版本。

灰度切流的重点不是炫技，而是控制影响范围。对生产设备运维平台来说，先在一个基地验证，比一次性全集团切换更稳妥。

### 2.7 技术点七：不过度设计的取舍

本项目当前不需要把 LVS、GeoDNS、全局流量调度、双活入口等能力写成主方案。原因是当前规模下，HTTP 管理类请求不是瓶颈，真正高频的设备遥测数据已经通过 MQTT 和 Kafka 单独承接。

更合适的取舍是：

- 当前主线：统一域名、API 网关、K8s Service、多副本、Kafka 消费隔离、分基地灰度。
- 保留扩展：如果后续基地数量和边缘节点规模显著扩大，再评估四层负载均衡、多入口区或跨地域流量调度。
- 避免堆叠：不把 Nginx、APISIX、Ingress、LVS 同时写成必选主链路。

这样写既能扣住负载均衡题目，又能体现架构师根据项目规模做取舍。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。本文结合该项目建设实践，首先简要描述负载均衡与流量分发的概念，随后围绕负载均衡与流量分发，阐述我如何从入口分流、API 网关治理、服务多副本、消息消费隔离和分基地灰度几个方面开展架构设计与实施，并分析相关技术选型、实施效果和架构取舍。

### 正文

#### 项目背景

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前建设目标并预留后续演进空间。

#### 过渡内容

负载均衡与流量分发不是简单把请求平均分给多台服务器，而是要根据业务流量特征设计合适的入口、服务实例和事件消费策略。本项目不是互联网高并发系统，HTTP 管理流量并不大；真正需要关注的是管理类请求与设备遥测数据不能混在同一入口，核心服务不能依赖单实例，分析任务不能拖慢实时告警，分期上线不能一次性影响全部基地。因此，我将负载均衡设计收敛为入口分流、服务多副本、消息消费隔离和分基地灰度四个方面。

#### 主体内容

首先，我按流量类型进行入口分流。总部和基地运维人员访问 Web 管理端、移动端处理工单、边缘节点拉取配置和确认指令，这些属于 HTTP/HTTPS 管理类请求，统一通过平台域名进入 API 网关，再由网关按业务域转发到监控、告警、工单、权限和配置等服务。设备测点和状态数据属于持续高频遥测流量，不进入 API 网关，而是由边缘节点通过 MQTT Broker 上报到中心接入服务，再写入 Kafka。这样管理类请求可以集中做鉴权、审计和限流，设备遥测链路可以独立扩展，不会相互挤占入口能力。

其次，我在 API 网关层完成基础入口治理。网关负责用户 JWT 校验、边缘节点证书校验、接口路由、基础限流和访问审计。例如告警查询进入告警服务，工单处理进入工单服务，边缘配置拉取进入配置服务。网关只做快速拦截和通用校验，用户角色、基地数据域、工单分派权限等细粒度授权仍由权限服务和业务服务判断。这样既避免各业务服务直接暴露外部接口，也避免把所有权限逻辑堆到网关造成规则复杂。

再次，我依托 Kubernetes Service 和多副本机制完成服务实例级分发。监控、告警、工单、权限和分析等服务均采用 Deployment 多副本部署，调用方只访问 Service，不感知具体 Pod IP。Readiness Probe 用于判断实例是否具备业务处理能力，未就绪实例不接收流量；Liveness Probe 用于发现卡死实例并自动重启。常规扩容或发布时，新增 Pod 通过就绪检查后才加入流量，异常 Pod 被自动摘除，从而降低单实例故障对核心服务的影响。

第四，在内部事件流上，我通过 Kafka Topic、分区和消费组实现消费隔离。设备遥测数据进入 Kafka 后，监控服务、告警服务和分析服务按不同消费组独立消费。监控和告警消费组属于高优先级链路，配置独立资源和更严格的 Lag 告警；分析消费组允许一定延迟，避免报表计算影响实时告警。对同一设备关键事件，我通过合理分区键保证局部顺序；对跨设备数据，则通过增加分区和消费者实例提升并行处理能力。这样，内部事件分发比单纯 HTTP 入口负载均衡更贴合本项目。

第五，我将负载均衡与容量保护结合。扩容不能只看实例数量，还要考虑数据库、Redis、Kafka、时序存储和第三方通知通道的承载能力。API 网关按用户、接口和 edgeId 做入口限流；服务层按连接池、线程池和下游依赖设置保护阈值；Kafka 消费侧通过 Lag、消费速率和处理延迟判断是否扩容。对于非核心报表查询，可以返回最近一次结果或提示稍后刷新；对于监控和告警链路，则优先保障资源。这样可以避免负载均衡把压力更快传递到后端依赖。

第六，我在发布过程中采用分基地灰度。项目三期交付，并覆盖多个生产基地，版本发布不适合一次性全量切换。常规服务通过 Kubernetes 滚动更新逐步替换副本；涉及告警规则、工单流程、边缘配置下发或接入链路的版本，先选择一个基地灰度运行，观察接口错误率、P99 延迟、Kafka Lag、告警生成延迟、工单创建成功率和边缘节点在线率，稳定后再推广到其他基地。若指标异常，可以通过网关路由、配置回滚或 Deployment 回滚快速切回旧版本。

该方案的取舍是，我没有把 LVS、GeoDNS、全局流量调度等能力作为当前主方案，因为本项目 HTTP 管理流量规模有限，过多入口组件会增加排障和运维复杂度。当前阶段更重要的是把管理流量和设备遥测流量分开，把核心服务部署成多副本，把事件消费链路隔离开，并把分期上线过程做成可灰度、可观测、可回滚。后续如果基地规模和边缘节点数量显著扩大，再评估四层负载均衡或跨地域入口调度。

#### 论文结论

项目落地之后，这些设计被落实到“告警发现、现场处置、专家复盘、管理改进”的闭环中：系统识别异常并生成告警后，维修员在移动端查看设备上下文和处置建议，完成检查、维修和复测后回填原因、动作和备件信息；设备专家依据趋势曲线、维修记录和重复告警情况修订规则与知识条目；管理人员根据闭环时长、重复发生和返修情况安排巡检、备件和保养计划。

同时，项目后续仍有两个优化方向：一是告警知识库仍较依赖人工维护。常见故障已能按历史告警、维修工单和处置记录推荐原因与步骤，但复合故障仍需专家补充，后续可用大模型辅助归纳维修记录和告警关联，提升知识沉淀效率。二是内网离线部署仍可优化。当前通过流水线构建扫描、导出镜像tar文件并上传内网导入部署，满足安全隔离要求，但跨基地同步、版本联动和回滚效率仍有提升空间，后续可建设内网镜像仓库和自动化发布编排能力。

回顾项目全过程，作为系统架构师，我进一步认识到，负载均衡与流量分发不能停留在堆叠入口代理和复杂流量组件，也不能脱离业务场景追求复杂方案，而应从问题识别出发，在业务目标、团队能力、运行成本和演进空间之间取得平衡。只有把负载均衡与流量分发落实为可验证、可治理、可演进的工程能力，才能真正支撑平台长期稳定运行和持续发展。
