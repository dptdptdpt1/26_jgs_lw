# 技术十二：分布式事务与数据一致性


## 1. 技术定位

### 1.1 从技术角度看

分布式事务与数据一致性解决的核心问题是：在微服务架构中，一个业务操作跨越多个服务时，如何保证数据最终一致，而不是像单体系统那样靠数据库事务一步完成。

这一技术方向通常包含：

- 分布式事务模型（2PC、TCC、Saga）
- 最终一致性与补偿机制
- 幂等设计与去重保障
- 消息可靠投递与死信处理
- 事件溯源与状态对账

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 分布式事务及其解决方案（2024.11 真题）
- 分布式系统设计
- 事件驱动架构设计
- 高可用与可靠性设计
- 微服务架构设计

### 1.3 从项目角度看

本项目中，一个典型的业务事件会跨越多个服务：设备异常 → 告警服务生成告警 → 写入 Kafka → 工单消费组创建工单 → 通知消费组发送短信/企业微信 → 分析消费组记录统计。这条链路中，告警生成、工单创建、通知发送分别由不同服务处理，任何一环失败都可能导致数据不一致：告警生成了但工单没创建，或者工单创建了但通知没发送。如果靠同步分布式事务（如 2PC）保证强一致性，会严重降低系统吞吐量。因此，本项目采用最终一致性方案。

## 2. 技术分析

### 2.1 技术点一：为什么不能用强一致性事务

#### 技术解释

在单体系统中，一个业务操作可以在同一个数据库事务中完成，要么全部成功，要么全部回滚。但在微服务架构中，告警服务、工单服务、通知服务各有自己的数据库，无法共享同一个事务。

强一致性方案（如 2PC 两阶段提交）的思路是：协调者先让所有参与者准备，全部准备好后再一起提交。但这种方式有几个严重问题：

| 问题 | 影响 |
| --- | --- |
| 性能差 | 每次操作都需要多轮网络通信，延迟增加数倍 |
| 可用性低 | 任何一个参与者不可用，整个事务阻塞 |
| 资源锁定 | 准备阶段锁定资源，高并发下系统吞吐量急剧下降 |
| 协调者单点 | 协调者故障可能导致参与者资源一直锁定 |

#### 项目中的具体场景

本项目中，告警高峰期（如设备故障集中爆发）每秒可能产生数十条告警事件。如果每条告警都需要同步等待工单创建和通知发送完成，告警服务的吞吐量会被下游服务拖慢。更严重的是，如果通知服务（依赖短信网关）变慢，告警服务也会被阻塞，导致新的告警无法生成。

#### 架构师决策点

我没有采用 2PC 或 TCC 等强一致性方案。原因是本项目的业务特点决定了"短暂不一致可以接受，但吞吐量不能降"。告警生成后工单晚几秒创建、通知晚几秒发送，对业务影响很小；但如果告警本身无法生成，后果严重。因此我采用最终一致性方案：告警服务先完成自己的写入，再通过 Kafka 异步触发下游服务，下游服务各自保证自己的处理逻辑正确。

同时，我必须解决一个关键问题：告警表写入和 Kafka 事件发布之间的原子性。数据库事务和 Kafka Producer 是两个不同的系统，无法用一个事务包裹——如果告警表写成功但 Kafka 写失败，事件丢失；如果 Kafka 写成功但告警表回滚，下游消费了一个不存在的告警。因此我引入 **Outbox 模式**：告警服务在同一个本地事务中写入告警表和 outbox 表（两张表在同一个数据库），由 Debezium CDC 监听 outbox 表的变更并写入 Kafka。这样告警表和 outbox 的原子性由本地事务保证，Kafka 的投递由 Debezium 负责（失败自动重试）。本项目边缘层已采用 SQLite Outbox 方案（详见 [项目图示.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目图示.md)），中心层采用相同模式保持一致。

```sql
-- outbox 表结构
CREATE TABLE outbox_events (
  id             BIGINT PRIMARY KEY AUTO_INCREMENT,
  aggregate_type VARCHAR(50),    -- 'Alarm'
  aggregate_id   VARCHAR(64),    -- alarm_id
  event_type     VARCHAR(50),    -- 'AlarmCreated' / 'AlarmRetracted'
  payload        JSON,           -- 完整事件数据
  created_at     DATETIME,
  published      BOOLEAN DEFAULT FALSE,
  published_at   DATETIME
);
```

### 2.2 技术点二：最终一致性与 Saga 模式

#### 技术解释

最终一致性不要求所有操作同时成功，而是保证"经过一段时间后，所有操作最终都成功"。如果某个环节失败，通过重试或补偿机制恢复。

Saga 模式是实现最终一致性的常用方式：把一个分布式事务拆成多个本地事务，每个本地事务完成后发布事件触发下一个，如果某个步骤失败，执行补偿操作回滚前面已完成的步骤。

#### 项目中的具体场景

以"设备异常 → 告警 → 工单 → 通知"链路为例：

```
Step 1: 告警服务生成告警事件，写入 Kafka(alarm.event.created)
  → 本地事务：写入告警表 + 写入 Kafka（同一事务）
  → 如果 Kafka 写入失败，告警不生成，重试
  → 如果告警表写入失败，不写 Kafka，不触发下游

Step 2: 工单消费组消费告警事件，创建工单
  → 本地事务：写入工单表 + 更新告警状态为"已派单"
  → 如果创建失败，消息不确认，Kafka 会重新投递

Step 3: 通知消费组消费告警事件，发送通知
  → 本地事务：调用短信/企业微信 API + 写入通知记录表
  → 如果发送失败，消息不确认，Kafka 会重新投递
```

补偿机制设计（按失败类型分两类）：

**第一类：业务补偿——通过反向事件驱动**

协同式 Saga 没有编排器来"回滚"，补偿靠发布反向事件，下游消费组各自处理：

```
正常链路：
  告警服务 → [alarm.event.created] → 工单消费组（创建工单）
                                   → 通知消费组（发送通知）

补偿链路（告警撤回）：
  告警服务 → [alarm.event.retracted] → 工单消费组（关闭工单）
                                     → 通知消费组（标记已取消，不发通知）
```

| 补偿场景 | 补偿事件 | 下游处理 | 失败兜底 |
| --- | --- | --- | --- |
| 告警误生成需撤回 | `alarm.event.retracted` | 工单消费组关闭工单；通知消费组标记已取消 | 重试 → 死信 → 人工关闭 |
| 工单需升级优先级 | `alarm.priority.changed` | 工单消费组更新优先级；通知消费组重新评估通知方式 | 重试 → 死信 → 人工升级 |
| 通知需撤回（已发短信无法撤回） | `notification.cancelled` | 通知消费组标记为"已取消"，补发更正通知 | 人工处理 |

**第二类：技术故障——通过重试 + 死信兜底**

消费失败时，消息不确认，Kafka 重新投递。重试策略采用指数退避（1s → 4s → 16s），避免下游服务被瞬间打满。超过重试次数后进入死信队列，由人工排查和修复（详见 2.4 死信队列设计）。

**第三类：部分成功——需要降级策略**

| 场景 | 状态 | 处理方式 |
| --- | --- | --- |
| 告警已生成 + 工单已创建 + 通知失败 | 工单正常，通知降级 | 通知记录标记为"待补发"，短信网关恢复后自动补发 |
| 告警已生成 + 工单创建失败 + 通知未触发 | 工单缺失 | 定时对账自动补建（详见 2.5 对账机制） |

#### 架构师决策点

我没有让告警服务同步调用工单服务和通知服务。原因是：一、同步调用意味着告警服务需要等待下游完成，延迟增加；二、下游服务不可用时告警服务也会失败，可用性降低。通过 Kafka 异步解耦，告警服务只需保证事件通过 Outbox 成功写入 Kafka，下游服务按自己的速率消费和处理。即使下游暂时不可用，消息也不会丢失（Kafka 持久化），恢复后自动继续处理。

补偿逻辑的设计原则是"谁消费谁补偿"——告警服务只负责发布补偿事件（如 `alarm.event.retracted`），工单服务和通知服务各自决定如何补偿。这样各服务独立演进，新增补偿场景只需对应消费组订阅新的事件类型，无需修改告警服务。

### 2.3 技术点三：幂等设计与去重保障

#### 技术解释

在最终一致性方案中，消息可能被重复投递（如消费者处理成功但确认失败，Kafka 重新投递）。如果消费端不做去重处理，可能导致重复创建工单或重复发送通知。

幂等设计的核心思想：无论同一个操作执行多少次，结果都与执行一次相同。

#### 项目中的具体场景

本项目中的幂等设计：

| 消费端 | 去重方式 | 实现细节 |
| --- | --- | --- |
| 工单消费组 | 按 alarmId 去重 | 创建工单前先查询是否已存在该 alarmId 的工单，存在则跳过 |
| 通知消费组 | 按 alarmId + 通知类型去重 | 发送通知前先查询是否已发送过该告警的同类型通知，存在则跳过 |
| 监控消费组 | 按 deviceId + timestamp 去重 | 同一设备同一时间点的状态只更新一次 |

去重的实现依赖消费端的唯一约束或 Redis 缓存：

```sql
-- 工单表的唯一约束
ALTER TABLE work_order ADD UNIQUE INDEX uk_alarm_id (alarm_id);

-- 创建工单时，如果 alarmId 已存在，INSERT 会失败，捕获 DuplicateKeyException 后静默跳过
```

并发边界情况：两个消费者实例同时收到同一消息（如 Kafka rebalance 期间），同时查询 alarmId 不存在，同时 INSERT——唯一约束保证只有一个成功，另一个捕获 `DuplicateKeyException` 后记录 DEBUG 日志并跳过，不报错、不重试。

**事件顺序性保障**：Kafka 同一 partition 内保序，但如果 `alarm.event.created` 和 `alarm.event.retracted` 被分到不同 partition，工单消费组可能先收到 retracted 再收到 created，导致状态错误。因此所有同一告警 ID 的事件必须路由到同一 partition——生产端以 `alarmId` 作为 Kafka message key，Kafka 保证相同 key 的消息进入同一 partition。

#### 架构师决策点

我没有让 Kafka 保证"精确一次"（Exactly-once）投递来解决重复问题。原因是 Kafka 的 Exactly-once 语义只在 Kafka 内部有效（生产者 → Kafka → 消费者 offset 提交），无法覆盖消费端的业务操作（如写数据库、调用外部 API）。因此，幂等设计必须在消费端实现，而不是依赖消息中间件。

### 2.4 技术点四：死信队列与人工兜底

#### 技术解释

即使有重试机制，某些消息仍然可能多次消费失败（如数据格式错误、下游服务永久不可用）。这些消息如果一直留在队列中重试，会阻塞后续消息的处理。死信队列（Dead Letter Queue）的作用是：将多次失败的消息转移到专门的队列中，由人工排查和处理。

重试策略需要考虑三个问题：一是重试间隔，采用指数退避（1s → 4s → 16s），避免下游服务被瞬间打满；二是线程隔离，消费线程池中预留部分线程专门处理正常消息，失败消息快速判断后转入死信，不占用正常消费线程；三是快速失败，对于明确不可恢复的错误（如数据格式异常、schema 不匹配），不重试直接进死信队列。

#### 项目中的具体场景

本项目中的死信队列设计：

```
正常消费 → 消费失败 → 重试（最多 3 次）
  → 仍然失败 → 转入 dead-letter.alarm-event topic
  → 告警通知运维人员
  → 人工排查原因（数据格式错误？下游服务异常？）
  → 修复后手动重放消息
```

死信队列的消息包含完整的诊断信息：

```json
{
  "originalTopic": "alarm.event.created",
  "originalPartition": 3,
  "originalOffset": 12345,
  "retryCount": 3,
  "lastError": "connection timeout to work-order-service",
  "lastRetryTime": "2025-03-12T09:35:00+08:00",
  "payload": { "alarmId": "ALM-001", "deviceId": "CNC-018", "..." }
}
```

#### 架构师决策点

我没有让失败消息无限重试。原因是：一、某些失败是数据本身的问题（如设备上报了格式异常的数据），重一万次也不会成功；二、持续重试会占用消费线程，阻塞正常消息的处理。通过死信队列，失败消息被隔离处理，正常消息不受影响。同时，死信队列的消息保留完整诊断信息，便于人工快速定位问题。

### 2.5 技术点五：事件溯源与状态对账

#### 技术解释

在最终一致性方案中，不同服务的状态可能存在短暂不一致。事件溯源（Event Sourcing）的思路是：不只存储当前状态，还存储所有导致当前状态的事件。这样可以通过重放事件还原任意时间点的状态，也可以通过对账机制检测和修复不一致。

#### 项目中的具体场景

本项目中的对账机制：

| 对账场景 | 对账方式 | 不一致处理 |
| --- | --- | --- |
| 告警与工单 | 定时任务比对：有告警但无对应工单 | 自动补建工单 |
| 告警与通知 | 定时任务比对：有告警但无对应通知 | 自动补发通知 |
| 设备状态与告警 | 比对设备当前状态和最近一条告警 | 状态不一致时触发重新评估 |

告警事件本身也支持溯源：每条告警事件记录完整的产生链路（设备 ID、规则版本、触发时间、处理状态），即使工单或通知丢失，也可以通过告警事件表重新触发。

除定时对账外，还需要**端到端延迟监控**。事件从告警生成到工单创建、通知发送的每一跳都有时间戳，监控系统计算各环节延迟，超过 SLA 阈值（如告警到工单 > 30 秒）自动告警。这与可观测性体系（详见 [10_可观测性设计.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/论文主题素材/10_可观测性设计.md)）的链路追踪打通——通过 traceId 可以从延迟告警直接穿透到具体的消费日志，定位是哪一环慢了。

**事件 Schema 版本管理**：随着业务演进，事件结构可能升级（如 AlarmCreated 新增字段）。消费组需要兼容新旧版本的事件：生产端在事件中携带 schema version 字段，消费端按版本分支处理；对于不兼容的 schema 变更，先升级消费端再升级生产端，避免出现老消费组无法解析新事件的情况。

#### 架构师决策点

我没有追求"零不一致"，而是接受"短暂不一致 + 定时对账修复"。原因是：一、在高并发场景下，追求强一致会严重影响吞吐量；二、对账机制可以在分钟级发现并修复不一致，对业务影响可忽略。同时，所有关键事件都持久化存储，即使出现不一致也可以通过事件重放恢复。端到端延迟监控让不一致从"被动发现"变成"主动感知"——不是等对账任务跑完才知道有问题，而是延迟超标时立刻告警。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。本文结合该项目建设实践，首先简要描述分布式事务与数据一致性的概念，随后围绕分布式事务与数据一致性，阐述我如何从一致性级别选择、本地事务、Outbox、幂等消费、补偿事件、死信处理和对账机制几个方面开展架构设计与实施，并分析相关技术选型、实施效果和架构取舍。

### 正文

#### 项目背景

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前建设目标并预留后续演进空间。

#### 过渡内容

分布式事务设计的关键，不是把所有场景都做成强一致，而是根据业务特点选择合适的一致性级别。平台微服务拆分后，告警服务、工单服务、通知服务和分析服务都有独立数据库和业务边界。告警生成后需要创建工单、发送通知、进入统计分析，如果使用 2PC 等强一致方案，告警服务必须等待所有下游完成，会降低吞吐并扩大故障影响面。结合设备运维业务特点，我选择“核心事实先可靠落地，下游动作最终一致”的方案。

#### 主体内容

首先，我明确本地强一致边界。单个服务内部的数据更新，例如告警服务写入告警记录、工单服务更新工单状态、权限服务修改角色权限，必须通过本地数据库事务保证一致。以告警服务为例，规则命中后先在本地事务中写入告警表和 outbox 表，告警事实必须可靠保存；工单创建、通知发送和分析统计不在同一个事务中同步完成，而是由后续事件驱动。这样可以保证核心事实不会因为下游故障而丢失。

其次，我采用 Outbox 模式保证事件可靠发布。告警服务在同一个本地事务中写入告警记录和待发布事件，事务提交后由后台任务或 CDC 组件将 outbox 事件发布到 Kafka。发布成功后更新 outbox 状态，失败则重试。这样避免了“数据库写入成功但消息未发送”或“消息发送成功但数据库回滚”的不一致问题。工单服务和通知服务也采用类似机制发布状态变更事件，保证后续分析和审计链路可追溯。

再次，我在消费端设计幂等和去重。Kafka 至少一次投递可能导致重复消费，边缘补传和网络重试也可能产生重复数据。因此，中心接入服务按 edgeId、deviceId、metricCode、eventTime 和 localSeq 去重；工单服务按 alarmId 建立唯一约束，确保同一告警不会创建多个工单；通知服务按 alarmId、接收人和通道控制重复发送；分析服务按业务事件编号处理指标更新。幂等设计使系统可以接受消息重复投递，而不产生重复业务结果。

在异常处理方面，我设计了重试、死信和补偿机制。短时失败的消息进入延迟重试，并采用退避策略避免持续冲击下游；多次失败后进入死信主题，记录原始消息、Topic、offset、失败原因和重试次数，并触发运维告警。对于告警撤回、工单关闭、通知取消等业务变化，通过补偿事件驱动下游服务各自处理。例如误报确认后，告警服务发布告警撤回事件，工单服务将未处理工单标记为取消，分析服务修正统计口径。补偿不是回滚数据库事务，而是在业务语义上完成纠正。

我还建立了对账机制验证最终一致性。定时任务比对告警表、工单表、通知记录和分析明细，发现“告警已生成但工单未创建”“工单已关闭但分析未更新”“死信未处理”等异常后进入补偿流程。对账任务不直接覆盖业务数据，而是生成待处理记录并保留审计信息，避免自动修复引入新错误。通过对账，系统即使出现短暂不一致，也能在可控时间内发现并修复。

该方案的取舍是，最终一致性提高了吞吐和可用性，但业务上会存在短暂不一致，并要求补充幂等、补偿、死信和对账机制。为控制复杂度，我没有将所有业务都改造成事件驱动。用户提交工单、确认告警和权限变更仍保持同步反馈；告警联动、通知发送、分析统计和外部集成采用异步最终一致。通过边界划分，系统既保持核心操作明确，又具备跨服务协作韧性。

#### 论文结论

项目落地之后，这些设计被落实到“告警发现、现场处置、专家复盘、管理改进”的闭环中：系统识别异常并生成告警后，维修员在移动端查看设备上下文和处置建议，完成检查、维修和复测后回填原因、动作和备件信息；设备专家依据趋势曲线、维修记录和重复告警情况修订规则与知识条目；管理人员根据闭环时长、重复发生和返修情况安排巡检、备件和保养计划。这样，架构设计的效果不再停留在指标描述上，而是具体体现为告警能被及时处理、经验能被持续沉淀、管理决策能有数据支撑。

同时，项目后续仍有两个优化方向：一是告警知识库仍较依赖人工维护。常见故障已能按历史告警、维修工单和处置记录推荐原因与步骤，但复合故障仍需专家补充，后续可用大模型辅助归纳维修记录和告警关联，提升知识沉淀效率。二是内网离线部署仍可优化。当前通过流水线构建扫描、导出镜像tar文件并上传内网导入部署，满足安全隔离要求，但跨基地同步、版本联动和回滚效率仍有提升空间，后续可建设内网镜像仓库和自动化发布编排能力。

回顾项目全过程，作为系统架构师，我进一步认识到，分布式事务与数据一致性不能停留在追求所有跨服务操作强一致，也不能脱离业务场景追求复杂方案，而应从问题识别出发，在业务目标、团队能力、运行成本和演进空间之间取得平衡。只有把分布式事务与数据一致性落实为可验证、可治理、可演进的工程能力，才能真正支撑平台长期稳定运行和持续发展。
