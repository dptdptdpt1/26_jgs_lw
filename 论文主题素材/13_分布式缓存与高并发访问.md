# 技术十三：分布式缓存与高并发访问


## 1. 技术定位

### 1.1 从技术角度看

分布式缓存解决的核心问题，是在高并发访问和热点数据读取场景下，如何减少数据库和后端服务压力，提高系统响应速度，同时控制缓存一致性和故障风险。

它不是单点Redis使用技巧，而是一套完整的访问加速和数据库保护机制。

这一技术方向通常包含：

- 缓存对象选择
- Key设计和命名规范
- Cache Aside、写穿、异步刷新等读写策略
- TTL和主动失效机制
- 缓存穿透、击穿、雪崩防护
- 热点Key识别与拆分
- 分布式锁和幂等控制
- 缓存集群高可用与监控

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 分布式缓存技术及其应用
- 高并发系统架构设计
- 性能优化设计
- 秒杀场景技术解决方案
- NoSQL数据库技术及其应用
- 数据分片和热点治理

### 1.3 从项目角度看

本项目不是典型电商秒杀，但存在类似的高频读取和热点访问问题。监控大屏会周期性刷新设备最新状态，设备详情页频繁读取测点和告警上下文，驾驶舱会集中访问基地级指标；同时告警服务、接入服务和边缘管理链路会频繁读取设备档案、测点配置、规则快照和节点状态。如果这些数据都从MySQL、时序库或湖仓中实时读取，不仅响应慢，也会放大后端压力。

因此，本项目的缓存设计重点不是追求极限QPS，而是保护核心数据库和实时链路，保障用户正在等待的查询稳定响应。

## 2. 技术分析

### 2.1 技术点一：缓存对象选择

不是所有数据都适合缓存。缓存对象必须满足“读多写少、访问频繁、允许短暂不一致或可通过版本控制处理”。

本项目中的缓存对象：

| 缓存对象 | 访问场景 | 一致性要求 | 建议策略 |
| --- | --- | --- | --- |
| 设备最新状态 | 监控大屏、设备详情 | 秒级可接受 | Redis Hash，短TTL |
| 设备档案 | 告警、工单、详情页 | 变更少但需可控 | Cache Aside + 主动失效 |
| 测点配置 | 接入、规则判断 | 版本一致性较重要 | configVersion + 本地缓存 |
| 规则快照 | 告警判断 | 必须按版本生效 | 版本化缓存 |
| 驾驶舱热点指标 | 首页、基地概览 | 分钟级可接受 | 预计算 + Redis缓存 |
| 登录会话/权限摘要 | 管理访问 | 安全要求较高 | 短TTL + 主动失效 |

架构取舍：工单状态、告警确认等强事务数据仍以MySQL为准，缓存只做查询加速，不作为最终事实来源。

### 2.2 技术点二：Key设计与数据结构

缓存Key设计要能表达业务边界，避免命名混乱和批量失效困难。

示例Key：

```text
device:state:{deviceId}
device:profile:{deviceId}
point:config:{deviceId}:{configVersion}
rule:snapshot:{baseId}:{ruleVersion}
dashboard:base:{baseId}:{date}
workorder:summary:{baseId}:{date}
```

常用数据结构：

| 数据结构 | 适用场景 |
| --- | --- |
| String | 单个指标、版本号、令牌 |
| Hash | 设备最新状态、设备档案 |
| Set | 在线设备集合、异常设备集合 |
| Sorted Set | 告警排行、故障次数排行 |
| Bitmap/HyperLogLog | 统计类场景，可作为扩展点 |

Key中保留baseId、deviceId、configVersion、ruleVersion等字段，便于按基地、设备和版本做缓存隔离。

### 2.3 技术点三：读写策略与一致性

本项目主要采用Cache Aside模式：

```text
读请求 -> 查Redis
命中 -> 返回
未命中 -> 查数据库/服务 -> 写Redis -> 返回
```

对于设备最新状态，由实时消费链路主动写入Redis，页面只读缓存；对于设备档案和配置类数据，业务服务更新数据库后发送缓存失效事件，相关服务按版本重新加载。

一致性取舍：

- 最新设备状态允许秒级延迟，不要求与时序库完全强一致。
- 设备档案和测点配置需要带版本号，避免规则判断使用混乱口径。
- 工单创建、告警确认等事务动作不依赖缓存结果提交。
- 页面展示可以读缓存，关键写操作必须回到服务和数据库校验。

### 2.4 技术点四：缓存穿透、击穿和雪崩防护

高并发场景下，缓存异常往往会反向冲击数据库。

| 风险 | 项目例子 | 处理方式 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的deviceId | 参数校验、布隆过滤器或空值短缓存 |
| 缓存击穿 | 某基地驾驶舱热点Key过期 | 互斥重建、逻辑过期、后台刷新 |
| 缓存雪崩 | 大量Key同一时间过期 | TTL加随机抖动、分批刷新 |
| 热点Key | 总部大屏频繁访问集团指标 | 本地缓存、多级缓存、热点拆分 |
| 缓存故障 | Redis不可用 | 降级返回旧值或限制非核心查询 |

架构取舍：缓存保护要和限流、降级配合。缓存不可用时，不能让所有请求直接打到数据库。

### 2.5 技术点五：多级缓存和运行监控

对于变化不频繁但读取极高的配置类数据，可以采用多级缓存：

```text
服务本地缓存 -> Redis分布式缓存 -> 数据库/配置服务
```

本地缓存适合设备主数据、测点配置和规则快照；Redis适合跨实例共享的最新状态、热点指标和会话摘要。配置变更时，通过版本号或事件通知触发失效。

缓存监控指标：

- 命中率
- QPS和慢查询
- 热点Key访问次数
- 内存使用率和淘汰次数
- 连接数
- 主从延迟或集群分片负载
- 缓存重建耗时

这些指标进入可观测体系，作为容量扩展、热点治理和降级策略调整依据。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。由于平台面临监控大屏高频刷新、设备状态热点读取、配置数据频繁访问、数据库压力保护和缓存一致性控制等问题。围绕分布式缓存与高并发访问，我从缓存对象选择、Key 设计、读写策略、多级缓存、热点防护、一致性取舍和运行监控几个方面进行架构设计，重点保障设备上报、规则判定、告警生成和工单派发等核心链路在高并发访问下仍能持续运行。经实践验证，该方案较好支撑了平台查询性能和数据库保护。本文将结合该项目，论述我在分布式缓存设计中的思路和实施过程。

### 正文

#### 项目背景

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前建设目标并预留后续演进空间。

#### 过渡内容

分布式缓存设计不是哪里慢就缓存哪里，而是要明确哪些数据可以缓存、允许多久不一致、失效后如何回源以及缓存异常时如何保护数据库。本项目中，监控大屏需要周期性刷新设备最新状态，设备详情页需要快速展示测点、告警和工单上下文，集团驾驶舱需要集中访问基地级汇总指标。同时，接入服务、告警服务和工单服务频繁读取设备档案、测点配置和规则快照。如果所有查询都直接访问数据库、时序库或分析库，不仅响应时间不稳定，也会在访问高峰时挤占核心业务链路资源。

#### 主体内容

首先，在缓存对象选择上，我按访问频率、变化频率和一致性要求分类。设备最新状态、基地概览和驾驶舱热点指标属于读多、写频繁但允许秒级延迟的数据，适合放入 Redis 支撑页面刷新；设备档案、测点配置和规则快照变化较少但读取频繁，适合采用 Redis 加服务本地缓存，并通过版本号控制一致性；用户会话和权限摘要可以短 TTL 缓存，但关键权限变更必须主动失效；工单创建、告警确认、权限变更等事务性动作不依赖缓存提交，仍以业务服务和数据库为准。这样既提升读取性能，又避免缓存错误影响关键业务事实。

其次，在 Key 设计和读写策略上，我按业务对象和版本建立规范。例如 device:state:{deviceId} 保存设备最新状态，point:config:{deviceId}:{configVersion} 保存测点配置，dashboard:base:{baseId}:{date} 保存基地驾驶舱指标，rule:snapshot:{ruleVersion} 保存规则快照。设备最新状态由 Kafka 消费链路或监控服务主动写入 Redis，页面读取时不再访问时序库；设备档案和配置类数据采用 Cache Aside 模式，未命中时从数据库或配置服务加载，写入缓存后返回。配置变更时发布失效事件，相关服务根据版本重新加载，避免旧规则和新数据混用。

再次，在多级缓存方面，我将服务本地缓存、Redis 分布式缓存和数据库分层使用。本地缓存适合设备主数据、测点配置和规则快照等变化不频繁且读取极高的数据，可以减少跨网络访问；Redis 适合跨实例共享的最新状态、热点指标和会话摘要；数据库和配置服务保留最终事实。多级缓存必须有明确失效机制，因此我要求配置类数据携带版本号，服务发现新版本后主动刷新本地缓存；对短期不一致可接受的数据设置 TTL，对强一致要求高的写操作则绕过缓存直接访问服务和数据库。

在缓存风险防护上，我重点处理穿透、击穿、雪崩和热点 Key。对于不存在的 deviceId，入口和服务层先做参数校验，必要时对空结果设置短 TTL，避免无效请求穿透数据库；对于总部大屏和基地概览这类热点 Key，采用逻辑过期和后台刷新，避免同一时刻大量请求同时回源；批量缓存 Key 的 TTL 增加随机抖动，防止集中失效；集团级指标这类极热点数据结合本地缓存和 Redis 缓存形成多级保护。Redis 不可用时，非核心报表允许返回最近一次结果或提示稍后刷新，核心写操作不依赖缓存继续完成。

在运行治理方面，我将缓存纳入可观测体系。Prometheus 采集命中率、QPS、慢查询、热点 Key、内存水位、连接数、淘汰次数、主从延迟和缓存重建耗时，Grafana 按业务场景展示缓存效果。当驾驶舱命中率下降、Redis 内存淘汰增加或某个 Key 访问异常升高时，系统触发告警，提示检查 TTL、热点拆分或扩容需求。缓存策略不是上线后固定不变，而是根据访问模式持续调整。

该方案的取舍是，缓存提高了读取性能和数据库保护能力，但引入了一致性和失效管理问题。为控制风险，我坚持“查询可缓存，事实不依赖缓存；热点可缓存，关键写操作回源校验；允许延迟的数据缓存，强一致数据谨慎缓存”的原则。通过缓存对象分级和异常降级设计，缓存成为高并发访问的保护层，而不是新的不确定因素。

#### 论文结论

“智能设备运维平台”于2026年1月完成三期交付并全面上线。运行实践表明，平台在多基地、多设备、边缘协同的生产环境下总体稳定，关键设备非计划停机率下降约18%，运维响应效率和集团统一管理能力明显提升，基本达成了由“事后抢修”向“预防性维护”转型的建设目标。

从本次分布式缓存与高并发访问设计看，我没有把它作为 Redis 使用处理，而是围绕热点读取加速、数据库保护和一致性控制这一主线，在缓存对象选择、Key 设计、多级缓存、风险防护和运行监控等方面建立可落地的架构能力。实施过程中也存在一些取舍：缓存提升了访问性能，但也带来了失效治理、热点识别和短暂不一致问题；后续还需要结合生产运行数据，在热点自动发现、缓存预热和故障降级策略方面持续改进。

回顾项目全过程，作为系统架构师，我进一步认识到，缓存设计不能只追求命中率，而要服务于业务正确性和系统稳定性。只有把分布式缓存落实为可控制、可降级、可观测的工程能力，才能真正支撑平台长期稳定运行和持续发展。
