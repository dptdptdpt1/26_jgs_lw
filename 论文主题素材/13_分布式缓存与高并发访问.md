# 技术十三：分布式缓存与高并发访问

## 过渡段（可直接写入正文）

分布式缓存不是简单在数据库前面加一层Redis，而是要围绕高频读取、热点状态、数据库保护和缓存一致性进行系统设计。本项目既有监控大屏实时刷新、设备详情查询、驾驶舱指标访问，也有边缘节点和中心服务对设备档案、测点配置、规则快照的频繁读取。如果所有请求都直接访问数据库或分析存储，容易造成热点压力和响应延迟。因此，我从缓存对象选择、Key设计、读写策略、一致性控制、热点防护和运行监控几个方面设计缓存体系。

## 1. 技术定位

### 1.1 从技术角度看

分布式缓存解决的核心问题，是在高并发访问和热点数据读取场景下，如何减少数据库和后端服务压力，提高系统响应速度，同时控制缓存一致性和故障风险。

它不是单点Redis使用技巧，而是一套完整的访问加速和数据库保护机制。

这一技术方向通常包含：

- 缓存对象选择
- Key设计和命名规范
- Cache Aside、写穿、异步刷新等读写策略
- TTL和主动失效机制
- 缓存穿透、击穿、雪崩防护
- 热点Key识别与拆分
- 分布式锁和幂等控制
- 缓存集群高可用与监控

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 分布式缓存技术及其应用
- 高并发系统架构设计
- 性能优化设计
- 秒杀场景技术解决方案
- NoSQL数据库技术及其应用
- 数据分片和热点治理

### 1.3 从项目角度看

本项目不是典型电商秒杀，但存在类似的高频读取和热点访问问题。监控大屏会周期性刷新设备最新状态，设备详情页频繁读取测点和告警上下文，驾驶舱会集中访问基地级指标；同时告警服务、接入服务和边缘管理链路会频繁读取设备档案、测点配置、规则快照和节点状态。如果这些数据都从MySQL、时序库或湖仓中实时读取，不仅响应慢，也会放大后端压力。

因此，本项目的缓存设计重点不是追求极限QPS，而是保护核心数据库和实时链路，保障用户正在等待的查询稳定响应。

## 2. 技术分析

### 2.1 技术点一：缓存对象选择

不是所有数据都适合缓存。缓存对象必须满足“读多写少、访问频繁、允许短暂不一致或可通过版本控制处理”。

本项目中的缓存对象：

| 缓存对象 | 访问场景 | 一致性要求 | 建议策略 |
| --- | --- | --- | --- |
| 设备最新状态 | 监控大屏、设备详情 | 秒级可接受 | Redis Hash，短TTL |
| 设备档案 | 告警、工单、详情页 | 变更少但需可控 | Cache Aside + 主动失效 |
| 测点配置 | 接入、规则判断 | 版本一致性较重要 | configVersion + 本地缓存 |
| 规则快照 | 告警判断 | 必须按版本生效 | 版本化缓存 |
| 驾驶舱热点指标 | 首页、基地概览 | 分钟级可接受 | 预计算 + Redis缓存 |
| 登录会话/权限摘要 | 管理访问 | 安全要求较高 | 短TTL + 主动失效 |

架构取舍：工单状态、告警确认等强事务数据仍以MySQL为准，缓存只做查询加速，不作为最终事实来源。

### 2.2 技术点二：Key设计与数据结构

缓存Key设计要能表达业务边界，避免命名混乱和批量失效困难。

示例Key：

```text
device:state:{deviceId}
device:profile:{deviceId}
point:config:{deviceId}:{configVersion}
rule:snapshot:{baseId}:{ruleVersion}
dashboard:base:{baseId}:{date}
workorder:summary:{baseId}:{date}
```

常用数据结构：

| 数据结构 | 适用场景 |
| --- | --- |
| String | 单个指标、版本号、令牌 |
| Hash | 设备最新状态、设备档案 |
| Set | 在线设备集合、异常设备集合 |
| Sorted Set | 告警排行、故障次数排行 |
| Bitmap/HyperLogLog | 统计类场景，可作为扩展点 |

Key中保留baseId、deviceId、configVersion、ruleVersion等字段，便于按基地、设备和版本做缓存隔离。

### 2.3 技术点三：读写策略与一致性

本项目主要采用Cache Aside模式：

```text
读请求 -> 查Redis
命中 -> 返回
未命中 -> 查数据库/服务 -> 写Redis -> 返回
```

对于设备最新状态，由实时消费链路主动写入Redis，页面只读缓存；对于设备档案和配置类数据，业务服务更新数据库后发送缓存失效事件，相关服务按版本重新加载。

一致性取舍：

- 最新设备状态允许秒级延迟，不要求与时序库完全强一致。
- 设备档案和测点配置需要带版本号，避免规则判断使用混乱口径。
- 工单创建、告警确认等事务动作不依赖缓存结果提交。
- 页面展示可以读缓存，关键写操作必须回到服务和数据库校验。

### 2.4 技术点四：缓存穿透、击穿和雪崩防护

高并发场景下，缓存异常往往会反向冲击数据库。

| 风险 | 项目例子 | 处理方式 |
| --- | --- | --- |
| 缓存穿透 | 查询不存在的deviceId | 参数校验、布隆过滤器或空值短缓存 |
| 缓存击穿 | 某基地驾驶舱热点Key过期 | 互斥重建、逻辑过期、后台刷新 |
| 缓存雪崩 | 大量Key同一时间过期 | TTL加随机抖动、分批刷新 |
| 热点Key | 总部大屏频繁访问集团指标 | 本地缓存、多级缓存、热点拆分 |
| 缓存故障 | Redis不可用 | 降级返回旧值或限制非核心查询 |

架构取舍：缓存保护要和限流、降级配合。缓存不可用时，不能让所有请求直接打到数据库。

### 2.5 技术点五：多级缓存和运行监控

对于变化不频繁但读取极高的配置类数据，可以采用多级缓存：

```text
服务本地缓存 -> Redis分布式缓存 -> 数据库/配置服务
```

本地缓存适合设备主数据、测点配置和规则快照；Redis适合跨实例共享的最新状态、热点指标和会话摘要。配置变更时，通过版本号或事件通知触发失效。

缓存监控指标：

- 命中率
- QPS和慢查询
- 热点Key访问次数
- 内存使用率和淘汰次数
- 连接数
- 主从延迟或集群分片负载
- 缓存重建耗时

这些指标进入可观测体系，作为容量扩展、热点治理和降级策略调整依据。

## 3. 可写入论文的主体内容

在本项目中，【**分布式缓存设计**】不是简单引入Redis，而是围绕设备运维平台的高频读取、热点状态展示和数据库保护进行系统设计。平台覆盖3个生产基地、900余台设备和24台边缘节点，监控大屏需要周期性刷新设备最新状态，设备详情页需要快速展示测点、告警和工单上下文，集团驾驶舱需要集中访问基地级汇总指标。同时，接入服务、告警服务和工单服务还会频繁读取设备档案、测点配置和规则快照。如果所有查询都直接访问MySQL、时序库或分析库，不仅响应时间难以稳定，也会在访问高峰时挤占核心业务链路资源。因此，我将缓存体系作为性能优化和数据库保护的重要组成部分来设计。

首先，在【**缓存对象选择**】上，我没有把所有数据都放入缓存，而是按访问频率、变化频率和一致性要求分类。设备最新状态、基地概览、驾驶舱热点指标属于读多写频繁但允许短暂延迟的数据，适合放入Redis支撑页面快速刷新；设备档案、测点配置和规则快照变化较少但使用频繁，适合采用Redis加服务本地缓存，并通过版本号控制一致性；工单创建、告警确认、权限变更等事务性动作则仍以数据库和业务服务为准，缓存只用于查询加速，不作为最终事实来源。这样既提升读取性能，又避免因缓存错误影响关键业务提交。

其次，在【**Key设计和读写策略**】上，我按业务对象和版本设计缓存Key，例如device:state:{deviceId}保存设备最新状态，point:config:{deviceId}:{configVersion}保存测点配置，dashboard:base:{baseId}:{date}保存基地驾驶舱指标。对于设备最新状态，由Kafka消费链路或监控服务主动写入Redis，页面读取时不再访问时序库；对于设备档案和配置类数据，采用Cache Aside模式，未命中时从数据库或配置服务加载，写入缓存后返回。配置变更时，通过配置版本或失效事件通知相关服务重新加载，避免旧规则和新数据混用。

再次，在【**缓存风险防护**】上，我重点处理穿透、击穿、雪崩和热点Key问题。对于不存在的deviceId，入口层和服务层先做参数合法性校验，必要时对空结果设置短TTL，避免无效请求穿透数据库；对于总部大屏、基地概览这类热点Key，采用逻辑过期和后台刷新方式，避免同一时刻大量请求同时回源；对于批量缓存Key，TTL增加随机抖动，防止集中失效；对于集团级指标这类极热点数据，则结合服务本地缓存和Redis缓存形成多级缓存。缓存不可用时，非核心报表允许返回最近一次结果或提示稍后刷新，核心写操作不依赖缓存继续完成。

最后，在【**运行监控和容量治理**】方面，我将缓存命中率、QPS、慢查询、热点Key、内存水位、连接数、淘汰次数和缓存重建耗时纳入Prometheus监控，并在Grafana中按业务场景展示。例如当驾驶舱命中率下降、Redis内存淘汰增加或某个Key访问异常升高时，系统会触发运行告警，提示检查TTL策略、热点拆分或扩容需求。这样缓存不只是一个性能组件，而是纳入平台运行治理的基础能力。

从项目效果看，分布式缓存有效降低了设备状态查询、驾驶舱访问和配置读取对后端数据库的压力，也使监控和管理页面响应更加稳定。我的体会是，缓存设计的关键不在于“哪里慢就缓存哪里”，而在于明确哪些数据可以缓存、允许多长时间不一致、失效后如何回源、异常时如何降级。只有把缓存一致性、热点治理和监控告警一起设计，缓存才能真正服务于高并发系统，而不是成为新的不确定因素。

## 4. 考场快速组织方式

遇到分布式缓存、高并发、秒杀迁移、性能优化类题目，可以按下面顺序写：

```text
项目高频读取和热点访问问题
-> 缓存对象选择
-> Key设计和读写策略
-> 一致性取舍
-> 穿透/击穿/雪崩/热点Key防护
-> 监控、降级和效果
```

不要只写“使用Redis”。要写清楚缓存什么、不缓存什么、如何保证一致性、缓存异常时如何保护数据库和核心链路。
