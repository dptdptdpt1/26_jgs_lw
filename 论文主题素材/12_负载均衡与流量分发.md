# 技术十二：负载均衡与流量分发

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

负载均衡与流量分发本质上属于平台入口治理和高可用保障能力，解决的不是单个业务功能问题，而是“请求如何稳定进入系统、如何被合理分发、如何在故障和扩容场景下保持连续服务”的问题。

在一个分布式平台里，它通常承担四类职责：

- 统一入口：把来自不同终端和不同来源的请求汇聚到统一访问入口
- 流量分发：将请求分发给多个后端实例，避免单点过载
- 故障隔离：在后端节点异常时快速摘除故障实例
- 平滑演进：支撑横向扩容、滚动升级、灰度切流

因此，负载均衡不是一个孤立组件，而是入口层、网关层、K8s Service 层和服务实例层协同治理的一部分。

### 1.2 从考题角度看

这个技术方向常见于以下题型：

- 高可用架构设计
- 性能优化设计
- 分布式系统设计
- 服务治理设计
- 微服务架构设计

如果题目是“高可用”“高并发”“微服务治理”，负载均衡通常都是正文里的关键技术点；如果题目是“大数据”或“Serverless”，它未必是中心主题，但仍可作为入口稳定性和流量治理的支撑能力写入方案。

### 1.3 从项目角度看

在本项目中，负载均衡的必要性来自三个现实约束：

1. 平台要同时承接 3 个生产基地 24 台边缘节点的数据上报与管理请求，以及总部和基地运维人员的 Web、移动端访问请求
2. 监控、告警、工单、权限等核心服务不能依赖单实例运行，否则任一节点异常都会影响设备运维主链路
3. 项目采用分 3 期交付，后续还要持续扩展新设备、新基地和新模块，因此必须具备平滑扩容和不停机发布能力

也就是说，本项目写负载均衡，重点不是“流量很大所以要分发”，而是“平台入口必须稳定、后端服务必须能扩、上线发布必须可控”。

## 2. 技术分析

这一部分只写和项目强相关的技术点，并明确区分“项目现网采用”与“考试可延展点”。

### 2.1 技术点一：DNS 与 VIP

#### 技术解释

- `DNS` 用于把平台统一访问域名解析到入口地址
- `VIP` 是对外暴露的统一虚拟入口地址，用于屏蔽后端节点变化（配合 Keepalived 使用，实现高可用）

#### 项目中的使用场景

本项目中，3 个基地的边缘节点、总部 Web 用户和基地移动端用户，都不直接访问后端业务服务，而是统一访问平台域名。平台域名解析后指向入口层 `VIP`，由入口层继续向下分发流量。

典型链路可以写为：

`边缘节点/WEB端/移动端 -> 内网 DNS -> VIP -> 入口负载均衡层`

#### 为什么这样贴合项目

因为本项目是集团统一平台，入口地址必须稳定。后端节点是否扩容、替换、升级，不应影响各基地边缘节点和运维人员的访问配置。通过统一域名和 `VIP`，可以把入口地址与后端部署解耦。

#### 考试可延展点

如果题目强调跨地域高可用或双活多中心，可以把这里延展为：

- `GeoDNS`
- 全局流量调度
- 多入口区 `VIP`

但就本项目主线而言，写“内网 DNS + VIP”更真实。

### 2.2 技术点二：入口层选型取舍

#### 技术解释

入口层选型需要在“足够稳定”和“避免过度设计”之间取舍。`LVS（DR，Direct Routing）` 属于四层负载均衡方案，适合高性能、低开销的大连接量入口流量分发；`Nginx` 属于七层反向代理，更适合 HTTPS 接入、域名分流和基础路径转发。

LVS 的优势在于：

- 四层处理性能高
- 对后端透明
- 适合承接大量连接请求

#### 项目中的使用场景

结合本项目现网规模，我没有把 `LVS` 作为当前 HTTP/HTTPS 管理类请求的主链路组件。原因是项目只有 24 台边缘节点，HTTP 管理类请求主要来自 Web、移动端和边缘节点注册/配置拉取/指令确认，压测结果显示 `DNS/VIP -> Nginx -> Apache APISIX -> K8s Service -> Pod` 已能覆盖当前并发和可用性要求。如果再把 LVS 放到 HTTP 主链路前面，会增加一层运维和排障复杂度，但对管理类请求收益有限。

因此，项目现网采用的 HTTP/HTTPS 管理类请求链路为：

`DNS / VIP -> Nginx -> Apache APISIX -> K8s Service -> Pod`

高频设备遥测链路独立承接：

`DNS / VIP -> MQTT Broker -> 中心接入服务 -> Kafka`

#### 为什么这样贴合项目

这个项目不是纯互联网门户，真正高频的设备遥测流量已经被单独分流到 MQTT Broker，不进入 HTTP API 网关；HTTP/HTTPS 管理类请求更强调鉴权、审计、限流和业务路由，而不是极限四层吞吐。因此保留 `DNS/VIP + Nginx + APISIX + K8s Service` 更符合“够用、清晰、可维护”的原则。

但我没有否定 LVS 的价值。如果后续设备规模扩展到多个集团基地、边缘节点数量显著增加，或入口压测发现 Nginx 集群前端连接数、网络吞吐或故障切换能力成为瓶颈，可以在 VIP 后补充 `LVS（DR）`，将 MQTT Broker 集群和 Nginx 集群挂在四层负载均衡之后。也就是说，LVS 是高连接数场景下的扩展预案，而不是当前阶段必须放入主链路的组件。

### 2.3 技术点三：Nginx

#### 技术解释

`Nginx` 主要承担七层反向代理能力，包括：

- TLS 终止
- 域名和路径的基础转发
- Header 处理
- 基础限流
- 反向代理

#### 项目中的使用场景

在本项目中，`Nginx` 位于 `DNS/VIP` 之后，作为七层代理层。它把 HTTP/HTTPS 管理类请求统一转发给 `Apache APISIX`，由 APISIX 再按业务域路由到后端服务，例如：

- `/api/edge/**` 走边缘节点注册、配置拉取和版本上报等管理链路
- `/api/alarm/**` 走告警链路
- `/api/workorder/**` 走工单链路
- `/api/auth/**` 走认证与权限链路

如果需要在论文里写具体一点，可以写为：

`DNS / VIP -> Nginx 集群 -> Apache APISIX -> K8s Service -> Pod`

#### 为什么这样贴合项目

本项目后端既有边缘管理类请求，又有用户访问请求，协议处理和业务路径转发不能全部放在四层完成，因此七层代理层是必要的。高频设备遥测数据不走 Nginx，而是由 MQTT Broker 承接。

### 2.4 技术点四：API 网关与 K8s Service

#### 技术解释

`API 网关` 属于应用层网关，主要负责：

- 鉴权前置
- 业务域路由
- 灰度发布
- 限流与熔断前置

`K8s Service` 是 Kubernetes 中的服务发现和负载均衡机制，负责为一组 Pod 提供稳定访问入口。API 网关不直接访问 Pod IP，而是通过 K8s Service 将请求转发到后端健康实例。

#### 项目中的使用场景

在本项目中，`API 网关` 采用 `Apache APISIX` 实现，位于 Nginx 之后，承接平台业务层的统一路由和治理。它根据业务域将流量继续分发到：

- 监控服务
- 告警服务
- 工单服务
- 权限服务
- 报表分析服务

典型链路可写为：

`DNS / VIP -> Nginx -> Apache APISIX -> K8s Service -> 监控/告警/工单/权限等 Pod`

对于少数不需要复杂业务鉴权的内部管理页面或只需要普通 HTTP 路由的服务，也可以由 `Nginx -> K8s Service -> Pod` 直接转发。但人员访问和边缘管理类接口仍优先经过 `Apache APISIX`，保证鉴权、审计、限流和业务路由口径统一。

#### 为什么这样贴合项目

因为本项目是微服务平台，七层代理、业务网关和 K8s 内部服务发现要分层治理：`Nginx` 更偏入口代理和 HTTPS 接入，`Apache APISIX` 更偏业务治理，`K8s Service` 负责 Pod 级服务发现和负载均衡。为避免入口层过重，本项目没有再单独引入一层集群 HTTP 入口控制器。高频设备遥测数据不走 API 网关，而是走 `MQTT Broker -> 中心接入服务 -> Kafka` 链路。

我保留 `Nginx + APISIX` 两层，不是为了堆组件，而是为了把“接入兼容”和“业务治理”拆开。Nginx 作为边界接入层，只做相对稳定、通用的入口能力，例如 HTTPS 证书、域名监听、基础安全头、上传大小限制、超时控制和反向代理；APISIX 作为业务网关层，负责用户是谁、设备是谁、能访问什么、是否超限、流量怎么切、请求转到哪个业务服务以及访问如何审计。

如果只用一层网关同时承担 HTTPS、Header 兼容、上传大小、超时、JWT、设备证书、限流、灰度、业务路由和审计，配置项会逐渐混在一起，入口规则、业务规则和安全规则相互影响，后续新增业务服务、调整限流策略或灰度规则时维护成本会越来越高。分成两层以后，Nginx 专注“怎么安全稳定地接进来”，APISIX 专注“进来以后怎么治理 API”，后端业务服务只需要关注自身业务逻辑。

这个分层成立的前提是职责边界要明确：Nginx 不做复杂业务治理，APISIX 不承担边界兼容和静态资源职责；如果两层都做 JWT、限流和业务路由，就会变成真正的过度设计。

#### 落地接入顺序

这条链路只承接 Web、移动端和边缘节点注册、配置拉取、指令确认等 HTTP/HTTPS 管理类请求；设备高频遥测数据仍走 `MQTT Broker -> 中心接入服务 -> Kafka`。

实际落地时，可以按“从后往前接”的顺序实施：

1. 先部署业务 Pod，例如设备服务、配置服务、告警服务和工单服务，Pod 只处理业务逻辑，不直接暴露给外部。
2. 为 Pod 创建 `K8s Service`，例如 `device-service:8080 -> device Pod:8080`。APISIX 访问的是 Service，不是 Pod IP；Pod 扩缩容或重启后，Service 后端实例自动变化，APISIX 路由规则不需要调整。
3. 部署 `Apache APISIX`，配置 `/api/device/*`、`/api/config/*`、`/api/alarm/*`、`/api/workorder/*` 等业务路由，并在网关层配置设备证书校验、JWT 校验、限流、审计和灰度策略。
4. 部署 `Nginx` 作为 HTTPS 入口代理，负责证书、域名监听、基础安全头、上传大小限制和超时控制。Nginx 不再做复杂 API 路由，只统一反向代理到 APISIX。
5. 配置内网 DNS 和 VIP，将平台域名解析到入口 VIP，VIP 后面对应一组 Nginx 实例。用户、移动端和边缘节点只访问统一域名。

以边缘节点拉取配置为例，实际流向是：`边缘节点请求 /api/config/pull -> DNS/VIP -> Nginx -> APISIX -> config-service -> config Pod`。APISIX 在入口层完成设备证书校验、edgeId 限流和访问审计，配置服务只关注“该节点应该拿到哪个版本的采集配置”。其中，APISIX 负责入口层基础鉴权、限流和审计；用户、角色、基地和数据域等权限模型仍由权限服务维护，必要时由 APISIX 或后端服务调用权限服务完成细粒度授权。

最终职责边界可以概括为：`DNS/VIP` 提供稳定入口地址，`Nginx` 负责 HTTPS 入口代理，`APISIX` 负责 API 网关治理，`K8s Service` 负责服务稳定入口和 Pod 负载均衡，`Pod` 负责业务处理。

### 2.5 技术点五：健康检查、灰度切流与滚动升级

#### 技术解释

负载均衡真正有价值，不只是“把请求分给多个节点”，而是要配合：

- `健康检查`
- `灰度发布`
- `滚动升级`
- 自动摘除故障节点

#### 项目中的使用场景

本项目分 3 期交付，且后续仍会持续优化，因此上线时不可能每次都停机切换。更稳的做法是：

1. 先部署新版本实例
2. 用健康检查确认新实例可用
3. 通过 `Nginx/API 网关` 逐步切入部分流量
4. 观察稳定后再扩大流量比例
5. 旧实例逐步摘除

这部分很适合写在论文里作为“工程落地能力”，因为它能体现架构师不是只会设计图，而是考虑到了发布、运维和稳定性。

## 3. 论文主体内容

在本项目的总体架构设计中，【**负载均衡与流量分发**】并不是一个简单的入口组件，而是保障平台稳定运行和持续演进的关键基础设施。项目面向集团 3 个生产基地，既要承接 24 台边缘节点持续上报的设备数据，也要承接总部和基地运维人员通过 Web 与移动端发起的业务访问。如果平台入口仍采用传统单实例模式，那么一旦访问高峰到来，或者某个节点故障，就可能导致监控、告警、工单等关键链路整体受阻，进而影响设备运维工作的连续性。因此，在负载均衡设计上，我并没有把它理解为单一的流量转发问题，而是把它作为平台入口治理、高可用设计和服务演进控制的一体化能力来建设。

在方案选型阶段，我首先分析了本项目的【**入口流量特点**】。与一般纯业务系统不同，本项目的入口流量由两部分组成：一部分是边缘节点持续上报的设备状态、事件和测点数据，这类流量数量大、持续性强，主要通过 MQTT Broker 和中心接入服务进入平台内部 Kafka；另一部分是运维人员对监控看板、告警中心、工单系统和报表系统的交互访问，以及边缘节点注册、配置拉取等管理类请求，这类流量对七层转发、鉴权和路由能力要求更高。基于这一特征，我没有简单地把所有入口请求都交给单层 `Nginx` 处理，而是将链路分为【**两类入口流量**】：高频遥测流量进入 `MQTT Broker` 集群，再由中心接入服务写入 Kafka；HTTP/HTTPS 管理类流量通过 `DNS/VIP -> Nginx -> Apache APISIX -> K8s Service -> Pod` 进入业务服务。压测中，HTTP 管理类请求的并发主要集中在看板查询、工单操作和边缘配置拉取，Nginx + APISIX 多实例已经可以满足当前吞吐和故障切换要求，因此没有把 `LVS` 放入当前主链路，而是将其作为后续高连接数场景下的扩展预案。这样做既避免入口层组件堆叠，也便于排障和运维。

在【**具体落地过程**】中，我重点把负载均衡能力和项目主链路结合起来，而不是把它设计成孤立的基础设施。对于边缘节点侧，设备遥测上报统一通过平台域名访问 MQTT 接入入口，由内网 `DNS` 解析到 `VIP`，再进入 MQTT 接入层，从而保证设备侧不感知后端节点变化；边缘节点注册、配置拉取等管理类请求则进入 HTTP 入口，由 `Nginx`、`Apache APISIX` 和 `K8s Service` 逐层分发。对于用户侧，Web 和移动端请求同样经由统一入口进入平台，再由 `Nginx` 和 `APISIX` 完成七层接入、鉴权、限流和业务路由。这样设计以后，无论是监控服务扩容、告警服务升级，还是工单服务迁移，入口地址和访问路径都不需要变更，既降低了运维复杂度，也提高了系统的可维护性。同时，为了避免负载均衡只停留在“流量分发”层面，我还要求团队在入口层和 K8s 服务层引入健康检查机制，能够在后端实例异常时自动摘除故障节点，把流量切到健康实例，减少局部故障扩散为全局故障的风险。

负载均衡在本项目中的另一个关键价值，是支撑分 3 期交付和后续持续优化。由于平台不是一次性上线，而是要随着设备接入范围扩大和功能模块逐步完善而持续演进，因此每次版本发布都必须控制对现网的影响。如果没有分层流量治理能力，所有升级都只能依赖停机切换，既影响业务连续性，也不利于问题回滚。针对这一问题，我在设计中把【**灰度切流、滚动升级和健康检查**】纳入统一流量治理体系。具体做法是：先部署新版本实例，通过健康检查验证可用性，再由 `Nginx` 或 `API 网关` 将部分流量切入新版本，观察稳定后逐步扩大流量比例，最终摘除旧实例。这样一来，平台既具备了不停机升级能力，也能够在问题出现时快速回退到旧版本。对于一个需要长期服务集团设备运维主链路的平台而言，这种能力往往比单纯追求理论吞吐量更重要。

从项目效果看，负载均衡与流量分发设计有效支撑了平台入口稳定性和后端服务弹性。它一方面降低了单实例故障对整体平台的影响，另一方面也为监控、告警、工单、权限等核心服务的多实例部署提供了基础条件。更重要的是，这一设计使平台具备了平滑扩容、滚动发布和持续演进的能力，与项目分期建设、持续优化的推进方式形成了良好匹配。回顾整个过程，我认为负载均衡在本项目中并不是配角，而是连接入口治理、高可用设计和微服务演进的关键枢纽。正是因为把它放在平台整体架构中统筹考虑，而不是孤立地看作一个网络组件，平台才能在承载多基地设备接入与多角色业务访问的同时，保持稳定、可扩展和可持续演进。
