## 1. 技术定位

### 1.1 从技术角度看

数据架构与大数据处理解决的核心问题是：在设备持续产生高频时序数据的场景下，如何同时支撑实时监控、告警识别、趋势分析、管理驾驶舱和预测性维护等不同访问模式的需求，并在实时性、存储成本和数据质量之间取得平衡。

它不是单一的存储或计算问题，而是涵盖数据分层、存储选型、实时处理、离线分析、指标治理和查询优化的完整数据架构设计。

这一技术方向通常包含：

- 数据分层架构（原始层 → 明细层 → 汇总层 → 应用层）
- 时序数据存储与冷热分层
- 实时数据处理与流式计算
- 离线分析与数据湖仓沉淀
- 架构模式选型（Lambda / Kappa / HTAP / 湖仓一体）
- 指标体系与数据质量治理
- 降采样与数据保留策略
- 查询优化与多场景服务

### 1.3 从项目角度看

本项目中，平台需要同时处理三类数据，且访问模式完全不同：

| 数据类型 | 写入特征 | 查询特征 | 时效要求 |
| --- | --- | --- | --- |

| 运维过程数据 | 中频、事件驱动 | 单条查询、状态跟踪 | 秒级 |

## 2. 技术分析

### 2.1 数据分层架构设计

#### 技术解释

数据分层是大数据架构的基础思想。核心原则是：不同层次的数据承担不同职责，面向不同消费者，采用不同存储和处理方式。分层后，上游变化不会直接影响下游，下游可以按自己的节奏消费和加工。

经典的数据仓库分层模型：

| 层级 | 名称 | 职责 | 数据特征 | 消费者 |
| --- | --- | --- | --- | --- |
| ODS | 原始数据层 | 保存原始数据，不做清洗转换 | 格式不统一、可能有脏数据 | 开发/运维（数据回放、问题复盘） |
| DWD | 明细数据层 | 清洗、去重、标准化、关联主数据 | 格式统一、质量可控、仍是逐条明细 | 开发/数据分析（明细查询、二次加工） |
| DWS | 汇总数据层 | 按通用维度预计算指标 | 粒度适中、可复用、查询快 | 业务人员/数据分析/规则策略（最常使用） |
| ADS | 应用数据层 | 面向特定消费方的最终结果 | 粒度最粗、直接消费 | 管理者/驾驶舱/预测模型/报表 |

各层的核心定位：

- **ODS**：原始备份，回答"发生了什么"。不做任何加工，保留原始格式，用于回放和复盘。如果 DWD 的清洗逻辑有 bug，可以从 ODS 重新计算。
- **DWD**：统一明细，回答"每条数据长什么样"。核心不是"转换成指标"，而是把异构数据变成统一格式的逐条记录——只做清洗、去重、标准化、关联，不做聚合。
- **DWS**：预计算指标，回答"某个维度的汇总结果"。按通用维度（设备、基地、班组、时间周期）提前计算好，是业务人员和分析人员最常打交道的层，查询快、口径统一。规则策略人员也基于 DWS 的聚合指标做判定（如"某设备日故障次数 > 3 次"）。
- **ADS**：面向场景的最终数据，回答"直接拿来看/用"。任何面向特定消费方的最终结果都算 ADS——管理者看的驾驶舱指标、预测性维护模型需要的特征数据、跨基地对比报表，都是 ADS。粒度最粗，不需要再加工。

以两条指标链路为例，说明每层到底存了什么数据、层与层之间做了什么处理。

**指标一：设备可用率** — 单数据源（设备状态事件）逐层聚合。

**ODS 原始数据层**：边缘上报的原始报文，保留设备侧格式，不做任何转换。

```json
{"deviceId":"CNC-018","protocol":"OPC_UA","rawData":{"ns=2;s=Machine.RunningMode":"auto","ns=2;s=Machine.Spindle.Speed":3200},"timestamp":"2025-03-12T09:30:05+08:00","edgeId":"EDGE-01"}
```

⬇️ **ODS → DWD：协议解析 + 测点映射 + 质量标记**
- 将 OPC UA 原始节点 `ns=2;s=Machine.RunningMode` 映射为平台统一编码 `running_mode`
- 将原始值 `"auto"` 解析为标准化的 metricValue
- 补充 quality 标记（normal/stale/missing）、configVersion、edgeId

**DWD 明细数据层**：清洗后的设备状态逐条明细，格式统一，一条记录对应一个测点的一次采样。

```json
{"deviceId":"CNC-018","metricCode":"running_mode","metricValue":"auto","quality":"normal","edgeId":"EDGE-01","configVersion":"v2.3","timestamp":"2025-03-12T09:30:05+08:00"}
```

⬇️ **DWD → DWS：按设备 + 日期聚合，按状态累计时长**
- 遍历当天该设备所有 `running_mode` 明细记录
- 按状态值分段累计：`auto` 累计 → runHours，`idle` 累计 → idleHours，`fault` 累计 → faultHours
- 计算 `availabilityRate = runHours / 24`

**DWS 汇总数据层**：按设备 + 日期聚合的运行时长和可用率，粒度从"每条采样"变为"每天每台设备"。

```json
{"deviceId":"CNC-018","date":"2025-03-12","runHours":16.5,"idleHours":4.2,"faultHours":3.3,"faultCount":1,"availabilityRate":0.688}
```

⬇️ **DWS → ADS：按基地汇总，补充设备主数据（设备名、所属班组），生成驾驶舱指标**
- 将同基地所有设备的日级汇总聚合为基地级指标
- 关联设备主数据，补充设备名称、所属班组等展示字段
- 按可用率排序，标记异常设备

**ADS 应用数据层**：驾驶舱直接消费的可用率指标，按基地汇总，可直接展示。

```json
{"baseId":"B01","date":"2025-03-12","deviceCount":320,"avgAvailability":0.923,"devices":[{"deviceId":"CNC-018","availability":0.688,"status":"异常"},{"deviceId":"CNC-019","availability":0.952,"status":"正常"}]}
```

---

**指标二：MTTR（平均修复时间）** — 跨数据源（告警 + 工单）融合。

**ODS 原始数据层**：规则引擎产生的原始告警事件和工单服务产生的原始操作日志，**分别存储**，互不关联。

告警原始事件：
```json
{"deviceId":"CNC-018","rawLevel":"WARNING","rawType":"TEMP_HIGH","rawMessage":"温度超过阈值","triggerTime":"2025-03-12T09:30:10+08:00"}
```

工单操作日志：
```json
{"orderId":"WO-001","action":"create","fromStatus":null,"toStatus":"open","operator":"system","timestamp":"2025-03-12T09:31:00+08:00"}
```

⬇️ **ODS → DWD：标准化 + 关联主数据 + 建立跨数据源关联**
- 告警：等级标准化（`WARNING` → `P1`）、告警分类归一（`TEMP_HIGH` → `TEMPERATURE`）、关联设备主数据补充 `baseId`
- 工单：关联告警 ID（`alarmId`）、关联设备主数据补充 `baseId`、根据 SLA 规则计算 `slaDeadline`
- 关键动作：工单记录通过 `alarmId` 与告警记录建立关联，ODS 层两条独立的记录在 DWD 层有了关联关系

**DWD 明细数据层**：告警明细和工单明细，各自独立存储但通过 `alarmId` 关联。

告警明细：
```json
{"alarmId":"ALM-001","deviceId":"CNC-018","alarmLevel":"P1","alarmType":"TEMPERATURE","triggerValue":82.5,"thresholdValue":80.0,"baseId":"B01","triggerTime":"2025-03-12T09:30:10+08:00"}
```

工单明细：
```json
{"orderId":"WO-001","alarmId":"ALM-001","deviceId":"CNC-018","priority":"P1","assignee":"张工","baseId":"B01","createTime":"2025-03-12T09:31:00+08:00","closeTime":"2025-03-12T11:45:00+08:00","slaDeadline":"2025-03-12T17:31:00+08:00"}
```

⬇️ **DWD → DWS：按 alarmId 关联两张明细表，计算修复时长，再聚合**
- 按 `alarmId` 关联告警明细和工单明细
- 计算单次修复时长：`repairDuration = closeTime - triggerTime = 2.23 小时`
- 判断是否在 SLA 内：`withinSla = closeTime < slaDeadline`
- 按设备/基地/月份聚合：`avgMttr`、`totalFaults`、`slaOnTimeRate`

**DWS 汇总数据层**：单次修复记录 + 月度聚合指标。

单次修复记录：
```json
{"alarmId":"ALM-001","deviceId":"CNC-018","alarmLevel":"P1","repairDuration":2.23,"withinSla":true,"baseId":"B01","date":"2025-03-12"}
```

月度聚合：
```json
{"baseId":"B01","month":"2025-03","totalFaults":45,"totalRepairHours":144.0,"avgMttr":3.2,"slaOnTimeRate":0.956}
```

⬇️ **DWS → ADS：跨基地汇总，生成集团对比指标**
- 将三个基地的月度 MTTR 汇总为一张对比表
- 计算集团平均值

**ADS 应用数据层**：集团驾驶舱的跨基地 MTTR 对比。

```json
{"month":"2025-03","bases":[{"baseId":"B01","avgMttr":3.2,"faults":45},{"baseId":"B02","avgMttr":3.5,"faults":38},{"baseId":"B03","avgMttr":2.2,"faults":28}],"groupAvg":3.0}
```

#### 架构师决策点

分层的核心价值是：上游变化不直接影响下游，同一指标只在 DWS 层计算一次，上层应用消费同一份结果，避免"同一指标不同页面显示不同数字"。

### 2.2 存储层：统一存储架构

本项目的存储层不是选择某一种数据库，而是根据数据的访问模式和生命周期，将不同组件放在合适的位置。从架构模式上看，这是一个典型的**"一湖两翼"湖仓一体架构**——以 HDFS + Apache Iceberg 为数据湖底座，Hive 和 HBase 为两翼，分别承担离线分析和实时查询的职责。

"一湖"指的是 HDFS + Iceberg 构成的湖仓一体存储层。HDFS 提供分布式文件存储，Iceberg 作为表格式层（Table Format）管理 HDFS 上的数据文件，提供 ACID 事务、Schema 演进、增量读取和时间旅行等能力。ODS 层和 DWD 层的数据都以 Iceberg 表格式存储在 HDFS 上——ODS 保留原始报文不做转换，DWD 保存 Flink ETL 清洗后的标准化明细。Iceberg 的引入让 HDFS 从一个"只能存文件"的数据湖升级为一个"可管理、可治理、可追溯"的湖仓一体存储层。

"两翼"指的是 Hive 和 HBase：Hive 作为 SQL 引擎直接读取 Iceberg 表，提供离线分析能力（"算得清"）；HBase 在 HDFS 之上加 RowKey 索引，提供实时点查能力（"查得快"）。两者底层都基于 HDFS，数据不重复存储，不制造数据孤岛。

InfluxDB 作为独立的时序数据库补充了 HDFS + HBase 都不擅长的时序范围查询能力，Redis 和 MySQL 作为业务缓存和业务数据库服务于上层应用。整体构成"热 → 温 → 冷"三级分层，每个组件有明确的定位。

存储层总览：

| 层级 | 组件 | 存什么 | 保留周期 | 查询模式 | 定位 |
| --- | --- | --- | --- | --- | --- |
| 热数据 | InfluxDB | 设备时序遥测（秒级采样） | 30 天原始 + 180 天降采样 | 时间范围查询、聚合 | "看现在" |
| 热数据 | HBase | 设备最新状态、告警索引、测点历史 | 30 天（TTL） | 按 RowKey 点查，毫秒级 | "查得快" |
| 湖仓 | HDFS + Iceberg（ODS/DWD） | 原始报文 + 清洗后明细 | 永久 | 增量读取、时间旅行、Schema 演进 | "存得下、管得住" |
| 温数据 | Hive on Iceberg（DWS/ADS） | 汇总指标 + 应用数据 | 永久 | SQL 批量分析 | "算得清" |
| 冷数据 | MinIO / HDFS 归档 | 超过保留期的历史数据 | 永久 | 按需读取 | "存得便宜" |
| 全文检索 | Elasticsearch | 日志和告警事件（从 Kafka clean topic 消费） | 30 天 | 全文检索、traceId 追踪 | "搜得到" |
| 业务数据 | MySQL | 工单、告警、用户、设备主数据 | 永久 | 关系查询 | 业务操作 |
| 缓存 | Redis | 设备最新状态、驾驶舱指标 | 短期 | Key-Value 读取 | "读得快" |

#### InfluxDB — "看现在"

InfluxDB 承载设备时序遥测数据的热数据层。本项目的指标监控体系已基于 Prometheus 建设，InfluxDB 可以通过 Prometheus Remote Write 无缝对接，降低运维成本。

在本项目中的角色：
- 写入：消费 Kafka 中的设备遥测数据，按 deviceId + metricCode + timestamp 写入
- 查询：支撑监控大屏的趋势图（近 N 分钟/小时的设备状态变化）
- 降采样：通过连续查询自动生成 5 分钟和 1 小时聚合数据
- 过期：通过保留策略自动清理过期热数据

冷热分层策略：

| 数据层 | 保留周期 | 数据粒度 | 用途 |
| --- | --- | --- | --- |
| 热数据（原始） | 30 天 | 秒级采样 | 监控趋势图、告警上下文 |
| 温数据（降采样） | 180 天 | 5 分钟/1 小时聚合 | 周级/月级趋势分析 |
| 冷数据（归档） | 永久 | Parquet 列式文件 | 历史复盘、模型训练 |

180 天后的历史数据通过定时任务导出为 Parquet 列式文件，写入 MinIO 或 HDFS 归档，存储成本降低 80% 以上。

InfluxDB 面向的查询模式是**时间范围查询和聚合**——"CNC-018 最近 10 分钟的温度趋势""B01 基地最近 1 小时的平均振动值"。它擅长的是按时间维度扫一段数据做聚合，不适合按 key 精确查单条。

#### HBase — "查得快"

HBase 承载需要实时随机读写的海量数据。它在 HDFS 之上加了一层 RowKey 索引（RowKey → 文件位置 → 偏移量），查询时先查索引直接定位到数据所在位置，不需要全表扫描。底层是行式存储，适合按 key 查单条或小范围扫描。

在本项目中的角色：

| 表 | RowKey 设计 | 存什么 | 查询场景 |
| --- | --- | --- | --- |
| 设备最新状态表 | deviceId（如 CNC-018） | 900 台设备 × 30 个测点的最新值 | 监控大屏点击设备详情，毫秒级返回 |
| 设备告警索引表 | deviceId + reverse_timestamp | 按设备倒序排列的告警记录 | 查看某台设备最近的告警列表 |
| 设备测点历史表 | deviceId + metricCode + reverse_timestamp | 单设备某测点的近 30 天数据 | 告警上下文的分钟级趋势图 |

HBase 面向的查询模式是**按 key 精确点查**——"给我 CNC-018 的最新状态""给我 CNC-018 最近 20 条告警"。它擅长毫秒级定位单条或少量数据，不适合做聚合分析。

**InfluxDB 与 HBase 的分工**：两者都服务于实时场景，但面向的查询模式不同。InfluxDB 面向时序数据的范围查询和聚合（监控趋势图），HBase 面向按 key 的精确点查（设备详情页）。同一个设备的数据同时存在于两个系统中，但用途不同，不构成冗余。

#### Apache Iceberg — "管得住"

Iceberg 是本项目数据湖仓的核心表格式层。它不是数据库，而是一种开放的表格式（Table Format），管理 HDFS 上的数据文件，提供 ACID 事务、Schema 演进、增量读取、时间旅行等能力。HDFS 解决"存得下"，Iceberg 解决"管得住"——让 HDFS 上的数据从"一堆文件"变成"可管理的表"。

在本项目中的角色：

| 能力 | 本项目场景 | 解决的问题 |
| --- | --- | --- |
| ACID 事务 | Spark 写入 DWD 表时，Hive 查询不会读到不完整文件 | 解决 HDFS 文件层面的并发读写冲突 |
| Schema 演进 | 设备新增测点时，DWD 表新增列无需重写历史 Parquet 文件 | 新增列自动对历史数据生效，查询不报错 |
| 增量读取 | Spark 每日计算 DWS 时只读新增和变更的数据 | 替代全量分区扫描，降低计算开销 |
| 时间旅行 | 回溯某天某个时刻的 DWD 数据快照 | 支持数据回放、问题复盘、审计追溯 |
| 分区演化 | 设备数据从按日期分区改为按基地+日期分区 | 无需重写数据即可调整分区策略 |
| 统一表格式 | Spark 和 Flink 同时读写同一张 Iceberg 表 | 不再依赖 Hive Metastore 的特定格式 |

在本项目中的数据组织：

| Iceberg 表 | 存什么 | 写入方 | 读取方 |
| --- | --- | --- | --- |
| ods_device_telemetry | 设备遥测原始报文 | Flink 归档 | Spark（问题复盘） |
| ods_alarm_events | 告警原始事件 | Flink 归档 | Spark（问题复盘） |
| dwd_device_status | 清洗后的设备状态明细 | Flink ETL | Spark（离线计算）、Trino（即席查询） |
| dwd_alarm_detail | 清洗后的告警明细 | Flink ETL | Spark（离线计算） |
| dwd_workorder_detail | 清洗后的工单明细 | Flink ETL | Spark（离线计算） |
| dws_device_daily | 按设备+日期聚合的指标 | Spark | Hive（驾驶舱查询） |

Iceberg 与 HDFS 的关系：HDFS 是底层文件系统，Iceberg 是上层的表管理层。数据文件（Parquet 格式）存储在 HDFS 上，Iceberg 通过元数据文件（Manifest List → Manifest File → Data File）管理这些文件的版本、分区和 Schema。每次写入都会生成一个新的快照（Snapshot），旧快照可以被保留用于时间旅行或回滚。

#### Hive — "算得清"

Hive 作为 SQL 引擎，直接读取 Iceberg 表提供离线指标计算和即席查询能力。Hive 不再直接管理 HDFS 目录和 Parquet 文件，而是通过 Iceberg 表格式获取数据文件的位置和元数据信息。这样做的好处是：Hive 获得了 ACID 事务和 Schema 演进能力，同时保持了 SQL 接口的兼容性。

在本项目中 Hive 承载的数据层：

| 数据层 | 存什么 | 查询场景 |
| --- | --- | --- |
| DWD 明细表（Iceberg） | 清洗后的设备状态、告警、工单逐条明细 | 运维人员查某设备某天的完整运行记录 |
| DWS 汇总表 | 按设备/基地/班组/时间周期预聚合的指标 | 计算设备可用率、故障率、MTTR |
| ADS 应用表 | 面向驾驶舱和报表的最终指标 | 跨基地对比、月度趋势分析 |

Hive 面向的查询模式是**SQL 批量分析**——"B01 基地 320 台设备昨天的可用率排序""3 月份 P1 告警最多的 10 台设备"。它擅长对大量数据做聚合、关联、排序，不适合实时点查。

**HBase 与 Hive 的互补**：HBase 是行式存储 + 索引，适合点查；Hive 是列式存储 + 无索引，适合批量分析。同一个查询需求用两者走的路径完全不同——查 CNC-018 的最新状态，HBase 按 RowKey 毫秒返回；查 900 台设备昨天的可用率排序，Hive 用 SQL 扫描聚合。两者底层都在 HDFS 上，数据不重复存储。

#### MySQL + Redis — 业务数据与缓存

MySQL 承载业务数据（工单表、告警表、通知表、用户表、设备主数据）和汇总指标（驾驶舱的多维聚合查询）。

Redis 在本项目中有明确的职责边界，与 HBase 互补而非重叠：

| 存储 | 存什么 | 查询模式 | 响应速度 | 用途 |
| --- | --- | --- | --- | --- |
| Redis | 设备最新 1 条状态 | Key-Value 点查 | 毫秒级 | 监控大屏实时刷新，每次请求直接返回最新值 |
| HBase | 设备近 N 条历史状态 + 告警索引 | RowKey 范围扫描 | 秒级 | 监控大屏详情查询，查看设备历史变化趋势 |

两者的分工：Redis 是"实时快照"，只保留每个设备的最新状态，由 Kafka Streams 每条数据到达时覆盖更新；HBase 是"历史索引"，保留近 30 天的状态记录和告警记录，支持按设备 + 时间范围扫描。监控大屏的实时刷新走 Redis，点击设备详情查看历史趋势走 HBase。

#### 数据流转

数据在存储层之间的流转路径：

```
设备 → 中心接入服务（协议解析/基础校验/路由分发）
      → Kafka raw（保留边缘原始报文）
        ├── Flink 归档 → HDFS ODS（Iceberg 表格式，原始数据不做转换）
        └── Flink 实时 ETL（去重/标准化/质量标记/测点映射）
            ├── 写入 Kafka clean topic（供下游消费）
            ├── 写入 HDFS DWD（Iceberg 表格式，清洗后标准化明细）
            └── 写入 HBase 告警索引表（供告警查询）
                     ↓
            Kafka clean topic
            ├── Kafka Streams → Redis（设备最新状态，供大屏实时刷新）
            ├── Kafka Streams → InfluxDB（窗口聚合，供趋势图查询）
            ├── Elasticsearch（日志/告警事件全文检索，供排障排查）
            └── Flink CEP → Kafka 告警事件（供告警/工单/通知）
                     ↓
            Spark（Airflow 调度，每日凌晨离线计算）
            ├── 读 Iceberg DWD → 增量读取/跨源关联/主数据补全 → 写入 Hive DWS
            └── 读 Hive DWS → 导出 → 写入 MySQL（驾驶舱指标）
```

ODS 层保存 Flink 处理前的原始报文，与数据源保持一致，不做任何业务转换，用于数据回放和问题复盘。DWD 层保存 Flink ETL 清洗后的标准化明细数据。中心接入服务只做协议解析和基础校验，不做去重和标准化——这些工作由 Flink ETL 统一处理。

#### 架构师决策点

实时链路的数据流顺序是关键设计决策。我没有让 Kafka Streams 和 Flink CEP 直接从 raw topic 消费。原因是：raw topic 中的数据可能存在重复、乱序、格式不统一等问题，如果 Kafka Streams 在原始数据上做窗口聚合，聚合结果的质量会受影响；如果 Flink CEP 在原始数据上做模式检测，可能因为数据质量问题产生误报。因此我让 Flink ETL 作为实时链路的第一道处理，输出到 clean topic 后再由下游消费，保证所有消费方拿到的都是已清洗的干净数据。

在存储层，我没有只用一种存储解决所有问题。原因是：本项目的数据访问模式差异极大——实时监控要求毫秒级响应，趋势分析要求时间范围聚合，驾驶舱要求多维聚合，历史复盘要求批量导出，日志排障要求全文检索。任何一种存储都无法同时满足这些需求。InfluxDB 擅长时序聚合但不擅长点查，HBase 擅长点查但不擅长聚合分析，Hive 擅长批量分析但不擅长实时查询，Elasticsearch 擅长全文检索但不擅长批量分析。让每个组件做自己擅长的事，通过数据流转把它们串联起来，才是合理的架构。Elasticsearch 从 Kafka clean topic 消费日志和告警事件，仅承担全文检索职责——按关键词搜索错误信息、按 traceId 还原请求链路，这是 HBase 和 Hive 都做不了的。日志的归档、点查和分析都复用其他存储组件，不重复建设。

我也没有让数据在多个存储之间自由复制。数据的写入有明确的单一入口：Flink ETL 写入 HDFS 和 HBase，Kafka Streams 写入 Redis 和 InfluxDB，Spark 写入 Hive 和 MySQL。每条数据的流转路径是确定的，不会出现"不知道这份数据从哪来"的问题。

### 2.3 计算层：Flink + Spark + Kafka Streams

计算层采用 Lambda 架构——Flink 和 Kafka Streams 负责实时链路（数据来了立刻算），Spark 负责离线链路（攒一批再算），两者结果在 ADS 层合并。

实时链路的数据流有明确的先后顺序：Kafka 原始 topic → Flink 实时 ETL（清洗、标准化、质量标记）→ Kafka clean topic → 下游消费。Kafka Streams 和 Flink CEP 都从 clean topic 消费，保证下游处理的都是已清洗的干净数据，避免在原始数据上做聚合导致质量问题。

| 引擎 | 角色 | 处理方式 | 本项目任务 | 消费来源 |
| --- | --- | --- | --- | --- |
| Flink 实时 ETL | 数据清洗与标准化 | 数据来了立刻算 | 清洗、去重、标准化、质量标记，同时写入 HDFS（供离线）和 HBase（供实时） | Kafka raw topic |
| Kafka Streams | 轻量实时处理 | 数据来了立刻算，逻辑简单 | 设备状态更新（写 Redis）、窗口聚合（写 InfluxDB） | Kafka clean topic |
| Flink CEP | 复杂实时处理 | 数据来了立刻算，支持 CEP | 多条件组合异常检测（温度连续升高 + 振动持续偏高） | Kafka clean topic |
| Spark | 离线批处理 | 攒一批再算 | 每日指标计算、特征工程、数据导出 | HDFS DWD |

#### Kafka Streams — 轻量实时处理

Kafka Streams 是 Kafka 自带的流处理库，不需要额外部署集群。本项目中从 Flink ETL 输出的 clean topic 消费，承担逻辑简单的实时任务：

- 设备状态更新：每条遥测数据到达后更新 Redis 中的设备最新状态（Redis 存最新 1 条，毫秒级响应，供监控大屏实时刷新）
- 窗口聚合：按 1 分钟/5 分钟窗口计算均值、最大值、最小值，写入 InfluxDB（供趋势图查询）

选择 Kafka Streams 而非 Flink 处理这些任务的原因：这些任务逻辑简单（状态更新、窗口聚合），Kafka Streams 配合消费组就能满足，不需要 Flink 的复杂流处理能力。数据清洗去重已在上游 Flink ETL 中完成，Kafka Streams 不需要重复处理。

#### Flink — 复杂实时处理

Flink 在本项目中承担两个角色：实时 ETL 和 CEP 模式检测。两者的输入来源不同：

| 任务 | 输入 | 输出 | 说明 |
| --- | --- | --- | --- |
| 实时 ETL | Kafka raw topic | Kafka clean topic + HDFS DWD + HBase（告警索引） | 清洗、去重、标准化、质量标记，同时输出到 clean topic 供下游消费、写入 HDFS DWD 供离线分析、写入 HBase 告警索引表供实时查询 |
| CEP 模式检测 | Kafka clean topic | Kafka 告警事件 | 识别多条件组合的异常模式，如"温度连续升高 3 次 + 振动持续偏高 5 次"预示主轴退化 |

Flink ETL 是实时链路的第一道处理，它从 raw topic 消费原始数据，完成清洗和标准化后输出到 clean topic 和 HDFS DWD（Iceberg 表格式）。同时，Kafka raw topic 的原始数据直接归档到 HDFS ODS（Iceberg 表格式），保留原始报文不做任何转换。Flink 通过 Iceberg Sink Connector 写入 Iceberg 表，自动管理文件提交和快照生成。Kafka Streams 和 Flink CEP 都从 clean topic 消费，保证下游处理的都是已清洗的干净数据。

Flink 的 CEP（复杂事件处理）是它区别于 Kafka Streams 的核心能力。Kafka Streams 能做"单条数据超不超标"的判断，但做不了"多个事件在时间窗口内是否构成某种危险模式"的识别。本项目中，单条温度超限可能是正常波动，但"温度连续升高 3 次 + 振动持续偏高 5 次 + 转速下降"的组合模式预示主轴可能退化，这种多条件、时序关联的检测必须用 Flink CEP。

#### Spark — 离线批处理

Spark 每天凌晨对前一天的全量数据做离线计算：

| 任务 | 输入 | 输出 | 调度周期 |
| --- | --- | --- | --- |
| DWD 补充加工 | HDFS DWD 明细数据（Flink ETL 已清洗） | Hive DWD 表（跨源关联、主数据补全） | 每日凌晨 |
| DWS 指标计算 | Hive DWD 表 | Hive DWS 汇总表 | 每日凌晨 |
| ADS 导出 | Hive DWS 汇总表 | MySQL 驾驶舱指标表 | 每日凌晨 |
| 特征工程 | Hive DWD 明细表（近 6 个月）+ InfluxDB 降采样数据 | Hive ADS 特征表 | 每周 |

以设备可用率计算为例：Spark 读取 DWD 层的 Iceberg 表（Parquet 列式格式，只读 `running_mode` 和 `device_id` 两列），利用 Iceberg 的增量读取能力只处理新增和变更的数据，按设备 + 日期聚合运行时长，再关联告警明细计算故障次数，结果写入 Hive DWS 表。列式存储的优势在这里体现——900 台设备 × 全天数据，只需要读两列而不是全部字段。Iceberg 增量读取的优势在于——每日计算不需要扫描前一天整个分区，只读新增数据即可。

#### 架构师决策点

Kafka Streams 和 Flink 在本项目中共存而非二选一。原因是：简单任务用 Kafka Streams（无额外部署、逻辑简单），复杂任务用 Flink（CEP、多流 Join、状态后端）。如果所有任务都用 Flink，增加了运维复杂度；如果所有任务都用 Kafka Streams，CEP 模式识别实现不了。让每个引擎做自己擅长的事。

Flink 和 Spark 的分工是 Lambda 架构的经典模式：Flink 处理实时数据，结果秒级可见；Spark 处理离线数据，结果每日更新。两者结果在 ADS 层合并——驾驶舱的实时指标来自 Flink → HBase → Redis，历史趋势指标来自 Spark → Hive → MySQL。

### 2.4 调度层：Airflow

Airflow 承载数据管道编排和任务调度，解决"哪些任务先跑、哪些后跑、失败了怎么办"的问题。

本项目中的每日数据管道编排：

```
每日凌晨 2:00 触发
  → 任务 1：检查 Iceberg DWD 表快照是否到位（Flink ETL 是否已完成当日写入）
  → 任务 2：DWD 数据完整性校验（Iceberg 元数据校验记录数、空值率，不通过则阻断）
  → 任务 3：DWD 补充加工（Spark 读 Iceberg DWD → 增量读取/跨源关联/主数据补全 → 写入 Hive DWS）
  → 任务 4：DWS 层指标计算（Spark 读 Hive DWS → 聚合计算 → 更新 Hive DWS）
  → 任务 5：ADS 层导出（Spark 读 Hive DWS → 写入 MySQL）
  → 任务 6：最终质量校验（指标范围、跨表一致性、环比异常检测）
```

数据质量校验分为两道：任务 2 在离线计算前做第一道校验，通过 Iceberg 元数据检查 DWD 表的快照完整性和记录数，发现数据缺失时阻断后续任务；任务 6 在 ADS 导出后做最终校验，检查指标是否合理、环比是否异常。实时链路的质量监控在 Flink ETL 中完成——每条数据经过清洗和标准化时都会打上质量标记（normal/stale/missing/out_of_range），质量异常的数据不会写入 clean topic，而是进入隔离队列供人工复核。ODS 层保存原始报文，仅用于回放和复盘。Iceberg 的元数据管理能力让质量校验更高效——通过 Snapshot 元数据可以直接获取每次写入的记录数和文件数，无需扫描数据文件。

任务之间有依赖关系：DWD 补充加工必须等 Flink ETL 清洗完成（HDFS DWD 数据到位），DWS 计算必须等 DWD 补充加工完成，ADS 导出必须等 DWS 计算完成。Airflow 通过 DAG 定义这些依赖，自动按顺序执行。任何一步失败时，Airflow 自动告警并支持手动重跑和回填（补跑历史日期的数据）。

每周和每月还有额外的调度任务：每周触发趋势分析和特征工程，每月触发跨基地对比和 OEE 计算。

### 2.5 服务层：统一查询服务

同一批数据服务多种场景，每种场景的查询模式不同，需要从不同的存储组件读取数据：

| 查询场景 | 数据来源 | 查询模式 | 响应要求 |
| --- | --- | --- | --- |
| 监控大屏（实时刷新） | Redis（最新 1 条状态） | Key-Value 点查 | 毫秒级 |
| 监控大屏（设备详情） | HBase（近 N 条历史 + 告警索引） | RowKey 范围扫描 | 秒级 |
| 监控趋势图（近 N 分钟） | InfluxDB 热数据 | 时间范围查询 | 秒级 |
| 告警上下文 | HBase 告警索引表 | 按 deviceId + 时间范围 | 秒级 |
| 日志全文检索 | Elasticsearch | 按关键词/traceId 搜索日志和告警事件 | 秒级 |
| 趋势分析（天/周级） | InfluxDB 降采样数据 | 聚合查询 | 秒级 |
| 驾驶舱（聚合指标） | MySQL（从 Hive DWS 导出）+ Redis 缓存 | 多维聚合 | 秒级 |
| 跨基地对比 | Hive DWS 表 | SQL 分析 | 秒到分钟 |
| 历史复盘 | HDFS Parquet 文件 | Spark 读取 | 分钟级 |
| 预测性维护特征 | Hive ADS 特征表 + InfluxDB 时序特征 | 批量导出 | 分钟级 |

查询路径的设计原则：用户正在等待的交互查询，走 Redis/HBase/InfluxDB 等低延迟存储；后台分析和报表查询，走 Hive/Spark 等高吞吐引擎。监控大屏的实时刷新走 Redis（最新 1 条，毫秒级），设备详情和历史趋势走 HBase（近 N 条，秒级），两者职责不重叠。驾驶舱的聚合指标虽然来自 Hive 离线计算，但结果导出到 MySQL 并缓存到 Redis，用户查询时走的是缓存路径，响应速度不受 Hive 离线计算的影响。预测性维护的特征工程同时需要 Hive 中的离线汇总指标和 InfluxDB 中的时序特征数据。

### 2.6 架构模式与演进方向

#### 架构模式选型

| 模式 | 核心思想 | 本项目适用性 |
| --- | --- | --- |
| Lambda | 流 + 批双链路并行 | **采用**。Flink/Kafka Streams 负责实时链路，Spark 负责离线链路，两者结果在 ADS 层合并 |
| Kappa | 只用流处理 | 不适合。降采样和指标汇总是天然的批处理场景，用流处理做成本高且复杂 |
| HTAP | 事务+分析一体化 | 不适合。分析需求主要在时序数据，不在业务数据，TiDB 等 HTAP 数据库解决不了时序聚合问题 |
| 湖仓一体 | 数据湖 + 仓库融合 | **已落地**。HDFS + Iceberg 为湖，Hive 为分析翼，HBase 为服务翼 |

#### 湖仓一体架构：HDFS + Iceberg + Hive

本项目的存储架构是一个落地的**湖仓一体架构**，核心是 HDFS + Apache Iceberg + Hive 三层协作：

**数据湖的核心特征在本项目中的体现：**

| 特征 | 含义 | 本项目实现 |
| --- | --- | --- |
| 集中式原始存储 | 所有数据集中存放，保留原始格式 | ODS 层将 Kafka 原始报文以 Iceberg 表格式归档到 HDFS，不做 Schema 强制转换 |
| Schema-on-Read | 写入时不强制 Schema，读取时按需解析 | ODS 原始数据保留设备侧格式，DWD 层通过 Iceberg Schema 演进统一结构 |
| 数据多样性 | 同时支持结构化、半结构化数据 | 设备遥测（半结构化 JSON）、告警事件（结构化）、工单日志（结构化）统一落在 HDFS Iceberg 表 |
| 保真度 | 原始数据不被修改或丢弃 | ODS 层永久保留原始快照，即使 DWD 清洗逻辑有 bug，也可以通过 Iceberg 时间旅行从 ODS 重新计算 |
| ACID 事务 | 读写互不影响 | Iceberg 快照隔离机制保证 Spark 写入和 Hive 查询并发安全 |
| 增量处理 | 只处理新增和变更数据 | Iceberg 增量读取替代全量分区扫描，降低 Spark 计算开销 |

**"一湖两翼"架构：**

当前架构可以概括为"一湖两翼"——以 HDFS + Iceberg 为湖，Hive 和 HBase 为两翼：

- **HDFS + Iceberg（湖）**：数据湖底座 + 表格式管理层。HDFS 承载所有数据文件（Parquet 格式），Iceberg 管理这些文件的版本、分区、Schema 和 ACID 事务。ODS 和 DWD 数据都以 Iceberg 表格式存储。HDFS 解决"存得下"，Iceberg 解决"管得住"。
- **Hive（分析翼）**：SQL 引擎，直接读取 Iceberg 表提供离线分析能力。面向"算得清"——批量聚合、指标计算、即席查询。Hive 通过 Iceberg 获得了 ACID 事务和 Schema 演进能力，同时保持 SQL 接口兼容。
- **HBase（服务翼）**：在 HDFS 之上加 RowKey 索引，提供实时点查能力。面向"查得快"——设备最新状态、告警索引、测点历史，按 key 毫秒级定位。

三者的互补关系：
- Iceberg 管理 HDFS 上的数据文件，提供事务和治理能力
- Hive 通过 Iceberg 读取数据做批量分析
- HBase 直接在 HDFS 上构建索引做实时点查

这种"一湖两翼"加全文检索的设计解决了传统数据湖最大的痛点——查询性能差和数据治理弱。HDFS + Iceberg 解决了"存得下、管得住"，HBase 补上了"查得快"的短板，Hive 补上了"算得清"的短板，Elasticsearch 补上了"搜得到"的短板。加上 InfluxDB 补充时序范围查询能力，整个存储层覆盖了点查、范围查询、全文检索、批量分析四种核心查询模式。

#### 元数据统一管理与数据血缘

当前数据分布在 HDFS 目录、HBase 表、Hive Metastore、InfluxDB 和 MySQL 中。作为架构师，需要一个统一的数据目录（Data Catalog）来回答"数据从哪来、经过了什么处理、当前在哪里"的问题。

当前通过 Hive Metastore 作为统一数据目录，管理 ODS/DWD Iceberg 表和 DWS/ADS Hive 表的元数据和分区信息。Hive Metastore 与 Iceberg 之间是互补关系：Iceberg 管理数据文件的版本、快照和 Schema，Hive Metastore 管理表的逻辑名称和分区映射。Spark 和 Flink 通过 Iceberg Catalog 读写 Iceberg 表，Hive 通过 Hive Metastore 读取同一张表，三方基于同一份数据协作。Hive Metastore 与 Spark 之间是双向依赖关系：Hive 表的定义和分区信息由 Metastore 管理，Spark 读写 Hive 表时需要通过 Metastore 定位数据文件；同时 Spark 写入新分区后需要向 Metastore 注册分区元数据，否则 Hive 查询无法感知新数据。

数据血缘追溯覆盖完整链路：从"某台设备通过 OPC UA 上报原始数据"到"经过边缘协议适配和标准化"到"写入 HDFS ODS（Iceberg 快照）"到"Flink ETL 清洗为 DWD（Iceberg 快照）"到"Spark 聚合为 DWS"到"导出到 MySQL 被驾驶舱消费"。Iceberg 的快照机制为血缘追溯提供了天然的版本锚点——每个快照对应一次写入操作，可以通过快照 ID 追溯到具体的数据文件和写入时间。如果某个驾驶舱指标的数值异常，可以通过血缘链路逐层追溯，定位是源头数据异常还是计算逻辑问题。

#### 冷热分层深化

当前的冷热分层通过 InfluxDB 保留策略（30 天原始 + 180 天降采样）和 HBase TTL（30 天）实现。未来可利用 HDFS 的异构存储策略（Heterogeneous Storage Policy）进一步优化存储成本：

- **热数据**（HBase/InfluxDB 近期数据）：存储在 SSD 节点，保障实时查询的低延迟
- **温数据**（Hive DWD/DWS 近 6 个月数据）：存储在普通 HDD 节点，满足批量分析的吞吐需求
- **冷数据**（归档 Parquet，超过保留期的历史数据）：存储在低成本 HDD 或归档到对象存储（如 S3/OSS），存储成本降低 80% 以上

数据从热到温到冷的流转通过 Airflow 定时任务自动执行，不需要人工干预。这种分层策略在存储成本和查询性能之间取得平衡，是防止数据湖退化为"数据沼泽"的关键治理手段。

### 2.7 指标体系与数据质量治理

#### 技术解释

指标体系定义"算什么、怎么算、谁使用"，数据质量治理保证"数据完整、准确、一致、可追溯"。两者是数据架构能否真正服务业务的关键。

#### 项目中的具体场景

核心指标定义（必须统一口径）：

| 指标 | 定义 | 计算方式 | 数据来源 |
| --- | --- | --- | --- |
| 设备可用率 | 设备实际运行时间 / 计划运行时间 | 日级汇总 | 设备状态事件 |
| 故障率 | 故障次数 / 运行时间 | 月度汇总 | 告警事件 + 设备状态 |
| MTTR（平均修复时间） | 故障修复总时间 / 故障次数 | 月度汇总 | 工单事件 |
| 工单及时率 | 在 SLA 内处理的工单 / 总工单 | 日级汇总 | 工单事件 |
| 告警闭环率 | 已闭环告警 / 总告警 | 日级汇总 | 告警事件 + 工单事件 |
| OEE（设备综合效率） | 可用率 × 性能率 × 良品率 | 日级汇总 | 多源数据关联 |

数据质量问题及治理方案：

| 问题 | 来源 | 治理方式 |
| --- | --- | --- |
| 重复数据 | 边缘补传、MQTT 重发 | 写入时按 deviceId + timestamp 去重 |
| 时间乱序 | 网络延迟、边缘缓存补传 | 写入时排序，乱序数据标记 quality=time_unsync |
| 测点缺失 | 设备断连、采集失败 | 缺失超过阈值触发离线告警，分析时插值标记 |
| 口径不一致 | 测点映射变更、配置版本差异 | 通过 configVersion 追溯，分析时按版本对齐 |
| 设备编码不一致 | 多基地历史数据编码规则不同 | 主数据统一映射，建立编码对照表 |
| 告警分类不统一 | 各基地告警规则定义不同 | 统一告警等级和分类标准 |

数据血缘追溯：

每条数据从产生到消费的完整链路都有记录：

```
设备上报（sourceProtocol, sourceAddress）
  → 边缘采集（configVersion, edgeId, quality）
  → 中心接入（ingestTime, processTime）
  → 入库存储（storageTime, retentionPolicy）
  → 降采样聚合（aggregationLevel, aggregationTime）
  → 应用消费（queryTime, consumerId）
```

指标计算链路：

| 指标 | 实时链路（Flink/Kafka Streams） | 离线链路（Spark） |
| --- | --- | --- |
| 设备最新状态 | Kafka Streams 更新 Redis，毫秒级可见 | — |
| 窗口聚合指标 | Kafka Streams 窗口计算 → InfluxDB | — |
| 设备可用率 | — | Spark 扫描 HDFS DWD → Hive DWS → 导出 MySQL |
| 故障率 | — | Spark 关联告警表和设备状态表 → Hive DWS |
| MTTR | — | Spark 关联告警明细和工单明细 → Hive DWS |

实时链路和离线链路各有分工：实时链路处理"现在发生了什么"（设备状态、窗口聚合），离线链路处理"过去一段时间的统计结果"（可用率、故障率、MTTR）。两者在 ADS 层合并，驾驶舱同时展示实时状态和历史趋势。

#### 架构师决策点

我没有让各基地自行统计指标再汇总。原因是：如果每个基地对"设备可用率"的定义不同（有的按日历时间算、有的按计划排产时间算），总部看到的横向对比就没有意义。统一指标必须从数据源头做起——统一设备状态事件的定义、统一计算公式、统一统计周期，然后在 DWS 层集中计算，各基地和总部消费同一份指标结果。

## 3. 论文主体内容

在本项目中，【**数据架构设计**】不是某个单点技术的选择，而是围绕设备运维数据的完整生命周期进行的系统性规划。平台覆盖 3 个生产基地、900 余台设备和 24 台边缘节点，每天持续产生设备状态、测点值、告警事件、工单流转和处置结果数据。按 900 台设备、每台约 30 个测点、平均 5 秒采集频率估算，每秒约产生 5400 个数据点，日增量约 90GB。实时监控和告警要求秒级响应，集团驾驶舱和趋势分析要求长周期聚合，预测性维护要求数据连续、口径一致。这些需求的访问模式完全不同，如果把所有数据都简单堆在同一种存储中，必然互相干扰。

在【**数据分层**】上，我把数据组织为四层。原始层（ODS）保存 Kafka raw topic 的原始报文直接归档到 HDFS，不做任何转换，用于数据回放和问题复盘；明细层（DWD）保存 Flink ETL 清洗后的标准化设备状态、告警和工单明细，写入 HDFS DWD 表；汇总层（DWS）按设备、基地、班组和时间周期聚合指标，通过 Hive DWS 表和 MySQL 汇总表实现；应用层（ADS）面向驾驶舱和报表提供最终指标结果，通过 Redis 缓存加速。分层的核心价值是：ODS 保留原始数据保证可追溯，DWD 统一格式保证口径一致，同一指标只在 DWS 层计算一次，上层应用消费同一份结果。

在存储层，我采用"【**一湖两翼**】"湖仓一体架构。HDFS 作为数据湖底座，Apache Iceberg 作为表格式层管理 HDFS 上的数据文件——ODS 原始报文和 DWD 清洗后明细都以 Iceberg 表格式存储在 HDFS 上。Iceberg 提供 ACID 事务（Spark 写入和 Hive 查询并发安全）、Schema 演进（新增测点无需重写历史文件）、增量读取（每日计算只读新增数据）和时间旅行（数据回放和问题复盘）。Hive 作为"分析翼"，直接读取 Iceberg 表提供 SQL 批量分析能力；HBase 作为"服务翼"，在 HDFS 之上加 RowKey 索引，提供毫秒级实时点查能力。InfluxDB 补充时序范围查询能力，承载设备遥测热数据，支撑监控趋势图。Elasticsearch 从 Kafka clean topic 消费日志和告警事件，仅承担全文检索职责——按关键词搜索错误信息、按 traceId 还原请求链路，这是 HBase 和 Hive 都做不了的场景。日志的归档、点查和分析都复用其他存储组件，不重复建设。这种"一湖两翼"加 ES 全文检索的设计，覆盖了点查、时序聚合、全文检索、批量分析四种核心查询模式。

在【**计算层**】，我采用 Lambda 架构——Flink 和 Kafka Streams 负责实时链路，Spark 负责离线链路。中心接入服务只做协议解析和基础校验，将边缘原始报文写入 Kafka raw topic，不做去重和标准化。Flink 实时 ETL 作为第一道处理，从 Kafka raw topic 消费原始数据，完成去重、标准化、测点映射和质量标记后输出到 clean topic 和 HDFS DWD 层。同时，Kafka raw topic 的原始数据直接归档到 HDFS ODS 层，保留原始报文不做任何转换，用于数据回放和问题复盘。Kafka Streams 和 Flink CEP 都从 clean topic 消费，保证下游处理的都是已清洗的干净数据。简单任务（设备状态更新写 Redis、窗口聚合写 InfluxDB）用 Kafka Streams，无额外部署成本；复杂任务（多条件组合异常检测）用 Flink 的 CEP 能力识别"温度连续升高 + 振动持续偏高"这类多事件时序模式。Flink ETL 同时写入 HDFS（供离线分析）和 HBase 告警索引表（供实时查询），同一份数据不需要采集两次。Spark 在 Airflow 调度下每日凌晨执行离线计算，扫描前一天的 HDFS 明细数据，计算设备可用率、故障率、MTTR 等指标，写入 Hive DWS 表，再导出到 MySQL 供驾驶舱查询。

在【**数据治理**】上，我要求核心指标统一定义、统一计算、统一发布。各基地不自行统计指标，而是在 DWS 层集中计算后供各基地和总部消费。中心接入服务只做协议解析和基础校验，原始报文直接归档到 HDFS ODS 层（Iceberg 表格式），保留与数据源一致的原始格式。Flink ETL 统一负责去重、标准化、测点映射和质量标记，清洗后的数据写入 HDFS DWD 层（Iceberg 表格式）。Iceberg 的 ACID 事务保证了 Spark 写入和 Hive 查询的并发安全，Schema 演进支持设备新增测点时无需重写历史文件，时间旅行支持数据回放和问题复盘。对于数据质量问题——边缘补传导致的重复、网络波动导致的时间乱序、测点映射变更导致的口径不一致——在 Flink ETL 中处理并对每条数据打质量标记（normal/stale/missing/out_of_range），异常数据进入隔离队列。离线链路在计算前通过 Iceberg 元数据做第一道校验（记录数、空值率），在 ADS 导出后做最终校验（指标范围、环比异常）。每条数据从设备上报到最终消费的完整链路都有血缘记录。

在【**架构演进方向**】上，当前架构已经是一个落地的湖仓一体架构——HDFS + Iceberg 为湖、Hive 为分析翼、HBase 为服务翼。Iceberg 的引入让 HDFS 从"只能存文件"升级为"可管理、可治理、可追溯"的湖仓一体存储层。通过 Hive Metastore 作为统一数据目录实现全链路数据血缘追溯，利用 HDFS 异构存储策略实现热数据存 SSD、冷数据存 HDD 的成本优化。下一步计划引入 Apache Flink SQL 直接读写 Iceberg 表，实现流批一体的数据处理——Flink 实时写入 Iceberg 表，Spark 批量读取同一张表做离线计算，两者基于同一份数据、同一个表格式，进一步降低架构复杂度。

从项目效果看，统一数据架构使平台同时具备了实时响应和长期分析能力。Flink 实时链路支撑了设备状态监控和告警联动，Spark 离线链路支撑了每日指标计算和趋势分析，HDFS + Iceberg 数据湖仓支撑了历史数据的长期保留、ACID 事务和问题复盘，Elasticsearch 支撑了日志和告警事件的全文检索与排障排查。日志事件和设备遥测数据走同一条管道，享受同一套清洗、质量标记和归档能力，不重复建设。随着设备规模扩大，HDFS、HBase 和 Spark 都可以通过增加节点水平扩展，不需要重构架构。回顾整个项目，我认为数据架构的关键不在于堆叠技术组件，而在于根据数据的真实访问模式建立"一湖两翼"加全文检索的存储体系——以 HDFS + Iceberg 为湖、Hive/HBase 为翼、ES 为检索，让每个组件做自己擅长的事。
