# 技术十：可观测性设计

## 过渡段（可直接写入正文）

可观测性设计不是在系统上线后补几张监控图表，而是要让设备数据、服务调用、消息积压和业务处置过程都能被追踪、解释和复盘。本项目链路跨越边缘节点、MQTT、Kafka、规则引擎、告警和工单服务，异常可能发生在现场网络、中心服务或下游消费环节。如果缺少统一可观测能力，排障只能依赖人工猜测。因此，我从指标、日志、链路追踪和告警治理四个方面建立定位闭环。

> **写作主线：**
> **工业 IoT 场景特点：日志即业务、设备数量多、数据持续上报、现场网络不稳定、边缘节点可能断网，可观测性不能只做普通服务监控 ——> 指标分层：按业务层、服务层、中间件层、基础设施层组织指标，用“业务层发现异常、服务层定位服务、中间件层判断积压、基础设施层排查资源”的方式追踪故障 ——> 日志与业务事件链路：运行指标走 Prometheus + Grafana，设备告警、操作日志、运行事件等业务日志走 SQLite Outbox、MQTT、Kafka、Flink 和 ES/HBase/HDFS ——> 分布式链路设计：通过 MQTT payload、Kafka Header、HTTP Header 传递 traceId，边缘节点通过 SQLite Outbox 和 localSeq 支持断网缓存与补传 ——> 告警治理：从“多报警”转向“有效报警”，通过分级、时间窗口聚合、根因收敛和工单联动减少告警风暴 ——> 三支柱关联：Grafana 看指标，Kibana 查业务日志，Jaeger 看链路追踪，通过 traceId、deviceId、alarmId 打通，形成“指标发现、链路定位、日志定因”的闭环 ——> 项目效果：提升故障定位效率，减少无效告警，增强边缘弱网场景下的运维稳定性。**

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

可观测性解决的核心问题是：系统出了问题，能不能快速定位到根因。它不是"能监控到异常就够了"，而是要让系统的行为可以从外部输出（指标、日志、链路）中被完整理解和还原。

可观测性的三个支柱：

- **指标（Metrics）**：系统"现在怎么样"——连续采样的数值型数据，回答"健康还是不健康"
- **日志（Logs）**：系统"发生了什么"——离散的事件记录，回答"具体出了什么事"。在传统软件中日志是调试用的"副产品"，但在工业 IoT 中，设备告警日志就是工单的触发源，操作日志就是合规审计证据，温度曲线日志就是质量追溯依据——**日志本身就是业务数据**，丢失一条日志可能意味着丢失一条生产记录
- **链路追踪（Traces）**：系统"请求经过了哪"——一次请求在多个服务间的完整路径，回答"卡在了哪里"

三者缺一不可：指标告诉你"有问题"，日志告诉你"是什么问题"，链路告诉你"问题在哪一环"。

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 可观测性设计
- 自动化运维及其应用
- 高可用与可靠性设计
- 分布式系统故障诊断
- 性能优化与监控
- SRE 实践

### 1.3 从项目角度看

本项目服务于 3 个生产基地、24 台边缘节点、900 余台设备，中心侧采用微服务架构，覆盖接入、监控、告警、工单、权限和分析等多个服务域。系统链路长：

`设备 → 边缘采集代理 → MQTT → 中心接入服务 → Kafka → 规则引擎/监控/分析 → 告警/工单/通知`

一旦出现"告警延迟""工单未生成""数据丢失"等问题，故障可能出现在链路中的任何一环。如果没有统一可观测体系，排障只能靠逐个服务人工猜测，效率极低。

## 2. 技术分析

### 2.1 技术点一：指标监控分层设计

#### 技术解释

指标监控是可观测性的第一层基础。它通过持续采集数值型时间序列数据，建立系统的实时运行画像。核心不是"采集了哪些指标"，而是指标体系怎么分层设计、怎么驱动告警。

指标体系通常分为四层：

- **基础设施层**：CPU、内存、磁盘、网络
- **中间件层**：Kafka 消费延迟、MQTT 连接数、Redis 命中率
- **服务层**：请求 QPS、响应时间 P99、错误率
- **业务层**：设备在线率、告警生成速率、工单处理时长

这四层不是随便分的，它对应排障时的**自顶向下排查顺序**：业务层发现异常（如告警延迟了）→ 服务层确认哪个服务慢了 → 中间件层排查是否 Kafka 积压 → 基础设施层看 CPU 是否打满。如果只监控基础设施层，CPU 100% 你看到了但不知道是哪个业务出了问题；如果只监控业务层，你知道告警延迟了但不知道根因在哪。四层都要有，才能形成完整的排查链路。

#### 项目中的具体场景

四层指标的具体设计：

| 层级 | 关键指标 | 采集方式 | 告警阈值示例 |
| --- | --- | --- | --- |
| 基础设施 | CPU 使用率、内存使用率、磁盘使用率、网络丢包率 | node_exporter | CPU > 80% 持续 5 分钟 |
| 中间件 | Kafka 消费组 Lag、MQTT 活跃连接数、Redis 命中率 | JMX exporter / 内置指标 | Kafka Lag > 10000 持续 3 分钟 |
| 服务 | 请求 QPS、响应时间 P99、错误率、线程池使用率 | 应用内置 Metrics SDK | P99 > 500ms 或错误率 > 1% |
| 业务 | 设备在线率、告警生成速率、工单平均处理时长、数据上报成功率 | 业务自定义指标 | 设备在线率 < 95% |

告警规则按严重程度分为三级。分级的核心逻辑是运营效率——不是所有告警都值得叫醒人：P2 只发企业微信，上班看就行；P0 必须秒级触达，电话 + 短信 + 企业微信全上：

| 级别 | 条件 | 通知方式 | 示例 |
| --- | --- | --- | --- |
| P0 紧急 | 影响核心业务链路 | 电话 + 短信 + 企业微信 | 中心接入服务宕机、Kafka 集群异常 |
| P1 严重 | 影响部分功能 | 短信 + 企业微信 | 单基地设备在线率骤降、消息积压持续增长 |
| P2 警告 | 需要关注但不紧急 | 企业微信 | 磁盘使用率偏高、单台边缘节点离线 |

#### 架构师决策点

我没有让每个服务自己做告警判断。原因是如果每个服务各自配告警阈值和通知方式，会出现两个问题：一是告警规则分散在各处，修改和审计困难；二是无法做跨服务的关联告警（比如"消息积压 + 规则引擎 CPU 高"组合出现时，可能指向规则引擎性能瓶颈，而不是消息队列问题）。统一由 Alertmanager 集中管理后，告警规则可审计，也便于后续做告警收敛和关联分析。

同时，我必须考虑监控体系本身的资源消耗。指标采集、心跳检测、日志收集这些机制都会占用网络带宽、计算资源和存储资源。以采集频率为例，我按指标变化速度分级：服务存活状态 15 秒采集一次（需要快速发现崩溃），CPU/内存 30 秒一次（变化较慢），业务指标 60 秒一次（变化最慢）。边缘节点心跳选择 30 秒频率，既能过滤大部分短暂断连，24 台节点每天约 7 万条心跳消息，资源消耗可接受。日志采集按级别分级：ERROR 实时采集并告警，INFO 采样采集（每分钟 1 条），DEBUG 不采集。监控体系资源消耗约占系统总资源的 10%，这个投入是值得的，因为没有监控就无法发现和定位问题，而监控不足导致的故障损失远大于监控本身的资源成本。

### 2.2 技术点二：指标采集与存储架构

#### 技术解释

指标采集架构解决的是"数据从哪来、存哪里、怎么看"的问题。本项目中有两类指标数据，来源不同、访问模式不同，采集链路也不同：

| 指标类型 | 举例 | 来源 | 采集链路 | 存储 |
| --- | --- | --- | --- | --- |
| 系统运维指标 | CPU、内存、QPS、错误率、Kafka Lag | 中心服务自身 | Prometheus Pull | Prometheus TSDB → InfluxDB |
| 设备业务指标 | 温度、振动、转速、可用率、OEE | 设备传感器 | 统一数据管道（Flink） | InfluxDB / HBase / Hive |

系统运维指标采用 Prometheus Pull 模式，设备业务指标走 Flink 统一数据管道（详见 [02_数据架构与大数据处理_收敛版.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/论文主题素材/02_数据架构与大数据处理_收敛版.md)）。两类指标最终汇聚到 InfluxDB，由 Grafana 统一展示。

#### 项目中的具体场景

系统运维指标采用 Prometheus + Grafana 架构。Prometheus Server 作为中心采集端，通过 Pull 模式定期拉取各服务暴露的指标端点。选择 Pull 模式而非 Push 有三个原因：一是采集端知道全局有哪些目标，方便做服务发现和统一管理；二是服务只需要暴露一个 HTTP 端点（如 `/metrics`），不需要知道数据往哪推，实现了采集与业务的解耦；三是采集频率由 Prometheus 统一控制，不会被异常服务打爆。

Prometheus 默认采用 Pull 模式采集指标，但现场边缘节点可能位于 NAT 或防火墙之后，中心监控系统无法稳定主动访问。因此我在边缘侧引入 Pushgateway 作为指标中转组件，由边缘节点主动推送在线状态、采集成功率、缓存积压量和 MQTT 重连次数等指标，再由中心 Prometheus 定时拉取 Pushgateway 中的指标。这样既保留了 Prometheus 统一采集和告警体系，又解决了边缘节点弱网和不可直连的问题。这里的 Pushgateway 只负责监控指标中转，不保存设备遥测、告警日志、操作日志等业务事件明细；这些日志和遥测在本项目中仍属于业务数据，其本地缓存和断点续传由边缘节点上的 SQLite Outbox 负责，后续通过 MQTT、Kafka 和 Flink 进入统一数据管道。

设备业务指标走统一数据管道：设备传感器数据经边缘网关 → MQTT → 中心接入服务 → Kafka → Flink ETL 清洗后，由流式写入任务写入 InfluxDB（详见 2.4 日志统一采集链路，日志和遥测数据走同一条管道）。两类指标最终都汇聚到 InfluxDB，由 Grafana 统一展示，用户无需关心底层是哪条链路采集的。

Prometheus 的存储采用本地 TSDB 保留 15 天热数据，同时通过 Remote Write 将长期数据写入中心 InfluxDB（详见 [02_数据架构与大数据处理_收敛版.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/论文主题素材/02_数据架构与大数据处理_收敛版.md)）。InfluxDB 通过连续查询自动生成降采样数据（5 分钟/1 小时聚合），180 天后的历史数据导出为 Parquet 归档到 HDFS，存储成本降低 80% 以上。

Grafana 按角色分层设计看板，不同角色关注的指标维度不同：

- **运维人员看板**：基础设施和服务层指标，关注系统健康
- **值班人员看板**：告警趋势、设备在线率、消息积压，关注业务连续性
- **管理层看板**：OEE、故障率、响应时效，关注运营效率

#### 架构师决策点

我没有把系统运维指标也纳入 Flink 管道，而是保留 Prometheus 独立采集。原因是：Prometheus 自带服务发现（自动发现新增的服务实例）和告警规则引擎（Alertmanager），这是运维监控的标准工具链，Flink 不擅长这些。而设备业务数据量大、需要复杂的清洗和聚合逻辑，这正是 Flink 的强项。两者各有所长，没必要强行统一到一个引擎。两类指标最终汇聚到 InfluxDB，由 Grafana 统一展示，对上层用户透明。

虽然本项目将设备告警日志、操作日志和运行事件视为业务数据，并通过 SQLite Outbox、MQTT、Kafka 和 Flink 进入统一数据管道，但这并不意味着可以取消 Prometheus。业务事件链路解决的是“发生了什么、是否可追溯”的问题，而 Prometheus 解决的是“系统当前是否健康、是否需要告警”的问题。Kafka Lag、服务 P99 延迟、错误率、Pod 资源水位、MQTT 连接数和边缘缓存积压量更适合用 Prometheus 按固定周期采集，并通过 Alertmanager 触发运行告警。二者分工不同：统一数据管道承接业务事实，Prometheus 承接运行健康。

Prometheus 本地 TSDB 只保留 15 天热数据，长期数据通过 Remote Write 写入 InfluxDB，再通过降采样和归档实现冷热分层。这种设计的核心逻辑是：Prometheus 擅长短期高精度采集，InfluxDB 擅长长期时序存储和降采样查询，两者配合覆盖从"最近 15 分钟的秒级精度"到"最近 180 天的小时级精度"的完整时间跨度。

### 2.3 技术点三：边缘层日志预处理

#### 技术解释

日志是离散的事件记录，回答"具体发生了什么事"。指标只能告诉你"P99 延迟升高了"，但日志能告诉你"是哪个请求、传了什么参数、在哪一行代码报了什么错"。

在讨论日志技术方案之前，需要先建立一个关键认知：在工业 IoT 中，**日志本身就是业务数据**，而不仅仅是调试用的"副产品"。传统互联网系统里，日志丢了不影响业务——用户下单成功了，日志没记下来，订单还在。但在工业 IoT 中，一条设备告警日志就是工单的触发源，丢了告警日志工单就不生成；一条操作日志就是合规审计的证据，丢了就无法追溯责任人；一条温度曲线记录就是质量追溯的依据，产品出了质量问题要靠它回溯。这个认知直接影响设计决策——日志系统的可靠性要求从"尽量不丢"变成"绝对不能丢"，这反过来决定了为什么需要边缘缓存、断点续传、ACK 确认这一整套可靠性机制。

IoT 场景的日志管理与传统互联网有本质差异，设计前必须理解这些约束：

| 挑战 | 具体表现 | 影响 |
| --- | --- | --- |
| 海量设备 | 900 台设备并发上报 | 采集端需横向扩展，不能单点瓶颈 |
| 弱网/断网 | 工厂内网不稳定、边缘网络时断时续 | 必须支持本地缓存 + 断点续传，不能丢日志 |
| 设备异构 | PLC、传感器、工控机协议各异（OPC-UA/Modbus/MQTT） | 需统一日志格式适配层 |
| 数据量巨大 | 高频采样产生 TB 级原始数据，且日志本身就是业务数据（告警、操作记录等），不能简单丢弃 | 必须在边缘层分级过滤、压缩、降采样，但业务关键日志不能丢 |
| 时间同步问题 | 边缘设备时钟漂移 | 日志时间戳不可直接信任，需要多级校准 |
| 安全合规 | 工业数据（配方参数等）不能随意外传 | 需数据分级与脱敏 |

这些约束决定了日志系统不能简单套用互联网方案，必须在边缘层做大量预处理工作。

#### 项目中的具体场景

本项目中，设备端产生的不只是"日志"，而是**业务事件记录**。按业务价值分为五类，不同类型的事件在采集优先级和保留策略上区别对待：

```
设备业务事件
  ├── 告警事件     → 超温、超压、故障码（优先级最高，保证不丢失——它是工单的触发源）
  ├── 运行事件     → 设备状态变化、启停记录（生产履历的组成部分）
  ├── 操作事件     → 工人操作记录、参数调整（合规审计的证据）
  ├── 通信事件     → 协议交互、连接状态
  └── 诊断事件     → 自检结果、传感器校准（优先级最低，可采样上报）
```

设备端采用本地循环写入（Ring Buffer）防止存储撑满，告警事件优先级最高，空间不足时淘汰低优先级的旧数据。这里需要特别说明的是：告警事件和操作事件的可靠性要求远高于传统日志——告警事件丢了意味着工单不生成，操作事件丢了意味着合规审计链断裂。

边缘层是 IoT 日志系统成败的关键环节，本项目中边缘网关承担五大职责：

| 职责 | 说明 | 解决的问题 |
| --- | --- | --- |
| 协议适配与格式统一 | 不同设备协议（OPC-UA/Modbus/MQTT）统一转换为结构化 JSON | 设备异构 |
| 本地缓存与断点续传 | 网络断开时日志写入本地 SQLite Outbox 缓存，网络恢复后按 `localSeq` 序号续传，上传成功收到 ACK 才删除本地缓存 | 弱网/断网 |
| 预过滤与降噪 | 高频重复日志在边缘层聚合（如每秒心跳合并为每分钟汇总，减少 98% 流量）；DEBUG 日志采样上报（1%） | 数据量巨大 |
| 本地实时告警 | 一级告警（设备紧急故障）不依赖云端，边缘直接触发声光报警和短信通知 | 云端不可达时仍能响应 |
| 数据脱敏 | 生产配方参数做 Hash 处理，操作员工号脱敏为岗位编码后再上传 | 安全合规 |

缓存空间按优先级分配：告警日志 > 运行日志 > 诊断日志，空间不足时淘汰低优先级旧日志。

各服务统一采用结构化日志格式：

```json
{
  "timestamp_device": "2025-03-12T09:30:04.800+08:00",
  "timestamp_gateway": "2025-03-12T09:30:05.123+08:00",
  "timestamp_ingest": "2025-03-12T09:30:05.200+08:00",
  "level": "ERROR",
  "service": "rule-engine",
  "traceId": "abc-123-def",
  "deviceId": "CNC-018",
  "baseId": "B01",
  "edgeGatewayId": "GW-ZONE-B-02",
  "logType": "ALARM",
  "eventCode": "THRESHOLD_EVAL_FAILED",
  "message": "threshold rule evaluation failed",
  "error": "connection timeout to InfluxDB",
  "duration_ms": 5023,
  "localSeq": 10293
}
```

关键字段说明：

- `timestamp_device`、`timestamp_gateway`、`timestamp_ingest`：**三重时间戳**。IoT 设备时钟可能漂移，不能只信任设备本地时间。三个时间戳分别记录设备产生时间、边缘网关接收时间（NTP 同步校准）、云端入库时间，查询时以网关时间为准
- `traceId`：链路追踪 ID，是连接日志和链路追踪的桥梁——当链路追踪发现某个 span 耗时异常时，可以通过 `traceId` 直接检索到该 span 对应的详细日志，快速定位根因。没有 traceId，日志和链路就是两个孤岛
- `deviceId`、`baseId`：业务维度字段，支持按设备和基地检索
- `edgeGatewayId`：记录日志来源的边缘网关，用于定位边缘节点问题
- `logType`：日志类型分类（告警/运行/操作/通信/诊断），用于不同优先级处理
- `localSeq`：边缘网关本地序号，用于**日志完整性校验和断点续传**——云端接收后检测序号连续性，发现跳跃则主动向网关拉取缺失日志
- `duration_ms`：耗时字段，支持性能分析

#### 架构师决策点

我将边缘网关定位为日志系统的"第一道防线"而非简单的"数据转发器"。原因是：在工厂弱网环境下，如果边缘网关只做转发不做缓存，网络断开时日志就丢了——而日志本身就是业务数据，丢一条告警事件意味着少一张工单。因此边缘网关必须具备本地持久化缓存（SQLite Outbox）和断点续传能力，配合 `localSeq` 序号校验和 ACK 机制，确保即使长时间断网，恢复后也能补传完整数据。预过滤降噪的逻辑是：高频重复的心跳数据在边缘层聚合后再上传，减少 98% 的云端流量，但告警事件和操作事件不做降采样，保证业务完整性。

### 2.4 技术点四：日志统一采集链路

#### 技术解释

日志采集链路解决的是"事件从边缘到存储的完整传输路径"问题。核心设计点是链路架构选型、中间件缓冲和存储定位。

#### 项目中的具体场景

日志采集链路依附于统一的数据架构（详见 [02_数据架构与大数据处理_收敛版.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/论文主题素材/02_数据架构与大数据处理_收敛版.md)），不另起独立的采集管道：

`设备 → 边缘网关（协议转换 + 预过滤 + 本地缓存）→ MQTT → 中心接入服务 → Kafka raw topic → Flink ETL（清洗/标准化/质量标记）→ Kafka clean topic → Elasticsearch（全文检索）`

日志事件和设备遥测数据走**同一条数据管道**：边缘网关将设备事件（遥测 + 告警 + 操作日志等）统一通过 MQTT 上报到中心接入服务，中心接入服务写入 Kafka raw topic，Flink ETL 统一完成清洗、去重、标准化和质量标记后输出到 Kafka clean topic。Elasticsearch 从 clean topic 消费日志和告警事件，**仅承担全文检索职责**——按关键词搜索错误信息、按 traceId 还原请求链路这类场景是 ES 的独有能力。日志的归档（HDFS + Iceberg）、点查（HBase）、分析（Hive）都复用统一数据架构中的存储组件，不重复建设。

这种设计的核心逻辑是：既然日志已经是业务数据，就应该和其他业务数据走同一条管道，享受同一套清洗、质量标记、归档和血缘追溯能力，而不是另建一套独立的 Filebeat + 日志消费服务链路。

日志平台的核心能力：

| 能力 | 用途 | 示例 |
| --- | --- | --- |
| 关键字检索 | 快速定位错误 | 搜索 `level:ERROR AND service:rule-engine` |
| 请求追踪 | 还原一次完整请求 | 按 `traceId:abc-123-def` 查看全链路日志 |
| 设备维度查询 | 按设备排查问题 | 按 `deviceId:CNC-018` 查看该设备所有日志 |
| 基地维度统计 | 按基地分析趋势 | 统计各基地最近 1 小时的 ERROR 日志数量 |
| 日志告警 | 基于日志模式触发告警 | ERROR 日志 5 分钟内超过 100 条触发 P1 告警 |
| 完整性校验 | 检测日志是否丢失 | 按 `localSeq` 序号连续性检测，发现跳跃主动拉取缺失日志 |
| 时间对齐 | 处理设备时钟漂移 | 以网关 NTP 校准时间为准，同时保留设备原始时间供参考 |

#### 架构师决策点

我没有为日志系统建设独立的采集链路（如 Filebeat + 日志消费服务），而是让日志事件和设备遥测数据走同一条管道。原因是：既然日志已经是业务数据，就应该和其他业务数据享受同一套清洗、质量标记、归档和血缘追溯能力，维护两套采集链路既增加运维成本，也容易导致数据口径不一致。Elasticsearch 不再作为日志系统的中心存储，而是统一数据架构中的一个存储组件，仅承担全文检索这一个职责——按关键词搜索错误信息、按 traceId 还原请求链路这类场景是 HBase 和 Hive 都做不了的。

在日志完整性方面，我设计了基于 `localSeq` 的校验机制：边缘网关为每条日志分配单调递增的本地序号，云端接收后检测序号连续性，发现跳跃则主动向网关拉取缺失日志。配合边缘层的本地 SQLite Outbox 缓存和"上传成功收到 ACK 才删除"的策略，确保即使在工厂弱网环境下日志也不丢失。

同时，我要求所有日志事件必须输出 `traceId`。这个字段是连接日志和链路追踪的桥梁——当链路追踪发现某个 span 耗时异常时，可以通过 `traceId` 在 ES 中检索到该 span 对应的详细日志，快速定位根因。

### 2.5 技术点五：分布式链路追踪

#### 技术解释

链路追踪解决的是"一次请求在多个服务之间经历了什么"的问题。在微服务架构中，一个业务事件可能经过接入服务 → Kafka → 规则引擎 → 告警服务 → 工单服务，如果某个环节延迟或失败，单看每个服务的日志和指标无法还原完整链路。

链路追踪的核心概念：

- **Trace**：一次完整请求的全链路，由唯一的 traceId 标识
- **Span**：链路中的一个操作单元（如一次服务调用、一次数据库查询），包含开始时间、耗时、状态。Span 之间有父子关系，形成树状结构
- **Context Propagation**：traceId 在服务间的传递机制（通常通过 HTTP Header 或消息 Header）。这是链路追踪最关键的技术问题——如果 traceId 在某个环节断了，后续的 Span 就无法和前面关联起来，链路就"断链"了
- **采样率**：不是每条请求都记录链路，按比例采样以控制存储和性能开销

在本项目中，链路追踪不是只追 Web 请求，而是要覆盖“设备上报 -> 中心接入 -> Kafka 分发 -> 规则判定 -> 告警生成 -> 工单联动”这条异步主链路。它有两个难点：一是链路起点在边缘节点，MQTT 不像 HTTP 一样天然有标准 Header；二是 Kafka 把同步调用拆成了生产和消费两个阶段，如果只记录服务内部日志，就看不到消息在队列中等待了多久。因此我要求 traceId 在边缘 payload、Kafka Header、HTTP Header 和结构化日志中保持一致，同时在 Kafka 生产和消费两侧分别记录 span，用于区分“服务处理慢”和“消息等待久”。

#### 项目中的具体场景

本项目中，一条典型业务链路的 span 结构：

```
Trace: abc-123-def
├── Span 1: 接入服务接收 MQTT 数据 (15ms)
│   ├── Span 1.1: 数据校验 (2ms)
│   ├── Span 1.2: 幂等去重查询 Redis (5ms)
│   └── Span 1.3: 写入 Kafka (8ms)
├── Span 2: Kafka 消费延迟 (50ms, 等待消费)
├── Span 3: 规则引擎处理 (120ms)
│   ├── Span 3.1: 加载规则快照 (5ms)
│   ├── Span 3.2: 阈值规则判定 (10ms)
│   ├── Span 3.3: 组合规则判定 (30ms)
│   └── Span 3.4: 时间窗口规则判定 (75ms)
├── Span 4: 告警事件写入 Kafka (10ms)
└── Span 5: 工单服务消费告警事件并创建工单 (45ms)
    ├── Span 5.1: 幂等校验 alarmId (8ms)
    ├── Span 5.2: 创建工单记录 (25ms)
    └── Span 5.3: 写入工单状态事件 (12ms)
```

通过这个 span 树，可以清晰看到：整条链路耗时约 240ms，其中规则引擎中时间窗口规则判定耗时 75ms，是告警生成链路中的主要瓶颈；工单创建耗时 45ms，属于告警闭环后的下游处理。

为了让链路追踪真正可用，我没有只保存技术上的 traceId，还把关键业务标识一起写入 Span 标签和结构化日志，例如 `baseId`、`edgeGatewayId`、`deviceId`、`pointCode`、`ruleId`、`alarmId`、`workorderId`、`topic`、`partition`、`offset`。这样排障时既可以从 traceId 还原一次事件的技术路径，也可以从 deviceId 或 alarmId 反查相关链路。例如用户反馈“B01 基地 CNC-018 的告警没有生成”，运维人员可以先按 deviceId 和时间范围在 Elasticsearch 中找到对应事件，再通过 traceId 跳转到 Jaeger 查看它是否卡在接入、Kafka、规则引擎还是工单消费环节。

链路追踪在本项目中的三个典型使用场景：

| 场景 | 问题 | 排查方式 |
| --- | --- | --- |
| 告警延迟 | 设备异常后告警生成慢了 2 分钟 | 按 traceId 查看完整链路，定位到 Kafka 消费 Lag 导致等待 |
| 工单未生成 | 告警已生成但工单服务没有创建工单 | 查看 span 发现告警事件写入 Kafka 成功，但工单服务消费时因参数校验失败静默丢弃 |
| 数据丢失 | 某设备的数据偶尔缺失 | 按 deviceId 和时间范围检索 trace，发现边缘节点 MQTT 断连重连时丢失了中间几条数据 |

链路追踪的 Context Propagation 设计，不同协议用不同方式传递 traceId：

| 协议 | 传递方式 | 说明 |
| --- | --- | --- |
| HTTP 服务间调用 | 通过 `traceparent` Header | HTTP 协议标准机制 |
| Kafka 消息 | 通过消息 Header 中的 `traceId` 字段，并记录 topic、partition、offset | 用于关联生产端 span、队列等待时间和消费端 span |
| MQTT 上报 | 边缘节点在数据 payload 中携带 `traceId`、`edgeGatewayId`、`deviceId`、`localSeq` | MQTT 不像 HTTP 有标准 Header 机制，需要在 payload 里手动携带 |

MQTT 的传递设计需要特别注意：这个项目的链路起点是边缘设备，如果边缘节点没带 `traceId`，从接入服务往后的 Span 都无法和前面关联起来，链路就断了。

对于边缘节点无法生成 traceId 的历史设备数据，中心接入服务会在首次接收时补生成 traceId，并把 `edgeGatewayId + deviceId + localSeq` 写入日志，保证从中心接入服务之后的链路仍然可追踪。但对于新接入的边缘节点，我要求在边缘侧生成或透传 traceId，因为只有这样才能覆盖断网缓存、补传、MQTT 重连和中心接入之前的现场链路。

引入 Jaeger 对开发侧的影响，重点不在于“把日志接入 Jaeger”，而在于“把链路上下文接入追踪体系”。日志仍然进入 Elasticsearch、HBase 和 HDFS；Jaeger 接收的是 OpenTelemetry 采集到的 trace/span。对边缘节点来说，需要在 MQTT payload 中增加或透传 `traceId`，并把 `edgeGatewayId`、`deviceId`、`localSeq` 等字段一起带上，便于中心侧把现场事件和后续处理链路关联起来。对中心服务来说，接入服务、规则服务、告警服务和工单服务需要通过 OpenTelemetry SDK 或统一拦截器生成 span，并在写入 Kafka 时把 traceId 放入消息 Header，消费 Kafka 时再从 Header 中恢复上下文。对业务日志来说，只需要在结构化日志中输出同一个 traceId，不需要把日志正文写入 Jaeger。

#### 架构师决策点

我没有只依赖 Elasticsearch、HBase 或 HDFS 来做链路追踪。原因是这些组件主要保存业务事件和日志明细，擅长回答“发生了什么”：例如设备上报了什么数据、触发了哪条规则、告警内容是什么、工单状态如何。但链路追踪还需要回答“这件事经过了哪些服务、每一步耗时多少、父子调用关系是什么、Kafka 中间等待了多久”。这些关系如果全部靠日志字段在 ES 中人工拼接，查询复杂、可视化差，也不容易区分服务处理时间和消息排队时间。

因此我引入 Jaeger 存储和展示 trace/span 数据。Jaeger 不替代 HDFS、HBase 和 Elasticsearch，也不保存完整业务事件明细；它只保存一次链路的结构化耗时信息，例如接入服务接收 MQTT 用了多久、写入 Kafka 用了多久、消息等待消费多久、规则服务处理多久、工单服务创建工单多久。业务事实仍由统一数据管道进入 HDFS、HBase、Hive 和 Elasticsearch，链路耗时则由 OpenTelemetry 采集后进入 Jaeger。二者通过 traceId、deviceId、alarmId 等字段关联，排障时先用指标发现异常，再用 Jaeger 定位慢在哪一跳，最后回到 Elasticsearch 或 HBase 查看业务内容和错误日志。

我没有采用 100% 全量采样。原因是本项目 900 台设备、秒级采集，每秒产生的链路数据量极大，全量采集会带来巨大的存储和性能开销。我采用的策略是**分场景采样**——核心思路是"宁可漏掉正常请求的链路，也不能漏掉异常链路"：

- **错误请求**：100% 采样，任何报错的链路必须完整记录（排障需要）
- **慢请求**：响应时间超过阈值的 100% 采样（性能分析需要）
- **正常请求**：按 10% 比例采样，足够支撑趋势分析和抽样排查

同时，业务关键链路（告警生成、工单创建）通过配置强制 100% 采样，因为这些链路的异常直接影响业务闭环，不能遗漏。

我也没有把链路追踪当作替代日志或指标的工具。指标用于发现 Kafka Lag、P99 延迟和错误率异常；链路追踪用于判断耗时发生在哪一跳；日志用于解释为什么失败，例如规则版本、参数内容、异常堆栈和业务状态。三者通过 traceId 和业务 ID 关联后，才能完整回答“有没有问题、问题在哪、为什么发生”。

### 2.6 技术点六：告警收敛与降噪

#### 技术解释

可观测体系不能只是"发现很多报警"，还必须具备降噪和分级能力。工业场景中，一次网络波动可能导致几百台设备同时离线告警，如果不做收敛，值班人员会被海量告警淹没，反而抓不住真正的故障点。

告警收敛的常用策略：

- **按时间窗口聚合**：同一类型告警在 N 分钟内只发一次汇总通知
- **按源头合并**：同一根因触发的多条告警合并为一条（如"边缘节点 EDGE-03 离线"导致该节点下 40 台设备离线告警，合并为一条）
- **按严重程度分级**：P0 电话、P1 短信、P2 企业微信
- **静默与维护窗口**：计划维护期间自动静默相关告警

#### 项目中的具体场景

本项目中的告警收敛设计：

| 告警场景 | 原始告警量 | 收敛策略 | 收敛后 |
| --- | --- | --- | --- |
| 边缘节点离线 | 该节点下 40 台设备各一条离线告警 | 按源头合并：识别为"边缘节点离线"，设备离线作为附属信息 | 1 条汇总告警 + 40 台设备列表 |
| 网络波动 | 3 个基地数百台设备上报异常 | 按时间窗口聚合：5 分钟内同类告警合并 | 1 条"网络波动影响汇总" |
| 规则引擎异常 | 同一规则对多台设备反复触发 | 按规则 + 时间窗口去重 | 每 10 分钟一条汇总 |

告警通知路由：

```
告警事件 → Alertmanager → 路由规则匹配
  ├── P0 紧急 → 电话 + 短信 + 企业微信群 @值班人
  ├── P1 严重 → 短信 + 企业微信群
  ├── P2 警告 → 企业微信群
  └── 信息类 → 仅记录，不通知
```

告警与工单联动：

- P0/P1 告警自动创建工单，工单优先级与告警级别对应
- 告警恢复后自动更新工单状态
- 同一设备 24 小时内重复触发同一告警，工单自动升级

#### 架构师决策点

我没有简单地按"设备 → 基地 → 集团"逐级聚合告警。因为实际场景中，一个边缘节点离线可能导致该节点下所有设备离线，如果按设备维度聚合，需要先知道设备属于哪个节点，再判断是否为同一根因。因此我采用"先识别根因实体，再聚合关联告警"的策略：系统先判断是边缘节点离线还是单台设备异常，如果是节点离线，则自动将该节点下所有设备的离线告警合并为一条节点级告警。

### 2.7 技术点七：三支柱关联与统一观测平台

#### 技术解释

指标、日志、链路追踪三者不是独立存在的，真正的可观测性价值在于三者的关联。如果三者之间没有关联，运维人员需要在 Grafana、Kibana、Jaeger 三个系统之间反复切换，排障效率反而不如以前看单机日志。三支柱的关联关系：

- **指标 → 日志**：指标发现异常后，通过时间范围和服务名快速检索相关日志（如 Grafana 面板直接跳转到 Kibana / Elasticsearch）
- **日志 → 链路**：日志中的 traceId 可以直接跳转到链路追踪视图（如从 Kibana 日志跳转到 Jaeger）
- **链路 → 日志**：链路中某个 span 异常时，可以通过 traceId 查看该 span 的详细日志（如从 Jaeger span 跳转到 Kibana / Elasticsearch）

这种关联能力让排障从"逐个系统切换查看"变成"从一个入口穿透到所有相关信息"。

#### 项目中的具体场景

**在本项目中，Prometheus 周期采集系统运行指标，并通过 Grafana 展示运行健康状态；设备告警、操作日志和运行事件作为业务数据进入 MQTT、Kafka、Flink 和 Elasticsearch/HBase/HDFS 链路，并通过 Kibana 检索分析；OpenTelemetry 负责采集 trace/span 链路数据，经 Collector 上报 Jaeger，由 Jaeger 展示跨服务调用和异步消息处理的耗时链路。三类数据通过 traceId、deviceId、alarmId 等字段关联，形成“指标发现、链路定位、日志定因”的可观测闭环。**

本项目中的统一流程示例：

**场景：某基地设备异常后告警生成延迟**

1. **指标层发现问题**：Grafana 看板显示 B01 基地的"设备异常到告警生成"延迟从 3 秒升高到 2 分钟
2. **指标定位范围**：拆解各环节延迟，发现 `device.telemetry.standard` 的规则消费组 Lag 持续增长，接入服务写入 Kafka 正常
3. **链路追踪验证**：找到一条延迟告警的 traceId，查看 span 树确认主要耗时发生在 Kafka 等待消费和规则引擎处理阶段
4. **日志定位根因**：用 traceId 在 Elasticsearch 中检索规则服务日志，发现某次复杂规则版本发布后窗口规则计算耗时明显升高
5. **处置**：回滚该规则版本，并将复杂规则拆分为预聚合指标 + 简化判定，恢复规则消费能力

这个流程体现了三支柱关联的价值：指标发现 → 链路定位 → 日志定因，整个排障过程在 10 分钟内完成。

统一观测平台的集成设计，核心是打通三个系统之间的跳转入口：

| 入口 | 可跳转到 | 用途 |
| --- | --- | --- |
| Grafana 指标面板 | Kibana / Elasticsearch 日志（按服务名+时间范围） | 从异常指标直接看相关日志 |
| Kibana 日志视图 | Jaeger 链路（按 traceId） | 从错误日志直接看请求链路 |
| Jaeger 链路详情 | Kibana / Elasticsearch 日志（按 traceId） | 从异常 span 直接看详细日志 |
| 告警通知 | Grafana 面板 + 相关日志 | 值班人员从告警直接进入排障视图 |

#### 架构师决策点

我没有把指标、日志、链路追踪作为三个独立系统来建设。如果三者之间没有关联，运维人员需要在 Grafana、Kibana、Jaeger 三个系统之间反复切换，排障效率反而不如以前看单机日志。因此我要求三个系统之间必须打通关联：指标面板通过服务名、时间范围和 traceId 跳转到 Kibana / Elasticsearch，日志和链路通过 traceId 字段互相关联，告警通知中附带 Grafana 面板链接和关键日志摘要，让值班人员可以一键进入排障视图。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。由于平台面临链路跨边缘和中心、服务调用复杂、消息积压难定位、告警噪声多和生产问题复盘困难等问题。围绕可观测性设计，我从指标、日志、链路追踪、业务监控、告警收敛和排障闭环几个方面进行架构设计，重点保障设备上报、规则判定、告警生成和工单派发等核心链路可监测、可定位、可恢复。经实践验证，该方案较好支撑了平台运行保障和持续优化。本文将结合该项目，论述我在可观测性设计中的思路和实施过程。

### 正文

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目难点不只是功能实现，还包括跨边缘和中心的链路定位、消息积压发现、故障影响范围判断和运行经验沉淀等问题。因此，在架构设计中需要围绕可观测性，在监控覆盖、资源消耗和排障效率之间取得平衡。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前运维闭环并保留后续扩展空间。

可观测性设计不是系统上线后补几张监控图表，而是要让设备数据、服务调用、消息积压和业务处置过程都能被追踪、解释和复盘。本项目链路跨越边缘节点、MQTT、Kafka、规则服务、告警服务和工单服务，异常可能发生在现场网络、中心服务、消息队列或下游消费环节。如果缺少统一可观测体系，排障只能依赖人工逐个系统猜测。因此，我从指标、日志、链路追踪和告警治理四个方面建立定位闭环。

首先，在指标体系上，我按基础设施、中间件、服务和业务四层设计监控。基础设施层采集 Kubernetes 节点、Pod、CPU、内存、磁盘和网络指标；中间件层采集 MQTT 连接数、Kafka Lag、Redis 内存、数据库连接和主从状态；服务层采集接口 QPS、错误率、P99 延迟、线程池和连接池使用率；业务层采集边缘节点在线率、数据上报成功率、告警生成延迟、工单创建成功率和工单闭环时长。业务指标尤其重要，因为 CPU 正常并不代表设备数据链路正常，只有业务指标才能反映平台是否真正服务生产运维。

其次，在日志设计上，我要求各服务输出结构化日志，并统一携带 traceId、baseId、edgeId、deviceId、alarmId 和 workorderId 等字段。边缘节点日志重点记录协议采集、缓存写入、MQTT 上报、断网补传和配置版本；中心服务日志重点记录接入校验、Kafka 投递、规则判定、告警生成和工单创建；平台日志进入 Elasticsearch 或日志平台，支持按业务对象检索。通过结构化日志，运维人员可以从一台设备、一个告警或一个工单出发，还原相关服务处理过程。

再次，在链路追踪方面，我通过 OpenTelemetry 统一传递 traceId。边缘节点在 MQTT payload 中携带 traceId 或业务追踪字段，中心接入服务写入 Kafka 时将 traceId 放入消息 Header，下游服务消费 Kafka 时恢复上下文，并在调用工单、通知等服务时继续传递。Jaeger 用于展示一次设备异常从边缘采集、中心接入、Kafka 排队、规则计算、告警生成到工单创建的完整耗时。这样，当告警生成延迟升高时，可以判断耗时发生在网络、Kafka 排队、规则计算还是数据库写入阶段。

在告警治理方面，我没有把所有异常都直接推给值班人员，而是按业务影响和根因关系进行收敛。边缘节点离线、同基地大量设备离线、Kafka Lag 升高和告警生成延迟上升之间存在因果关系，如果逐条告警会形成告警风暴。因此，我按基地、边缘节点、服务和时间窗口聚合告警，并在通知中附带影响范围、关键指标、日志摘要和面板链接。对于重复告警，采用抑制和升级策略；对于持续未恢复的异常，自动升级等级并触发工单。

我还将可观测性纳入发布和质量改进。每次生产发布后，流水线自动观察核心指标，包括接口错误率、P99 延迟、Kafka Lag、告警生成延迟和工单创建成功率，异常时触发回滚或人工确认。生产故障复盘时，必须判断是否缺少指标、日志字段或链路追踪点，并补充到监控体系中。这样，可观测性不是一次性建设，而是随系统演进持续完善。

该方案的取舍是，指标采集、日志收集和链路追踪会占用资源。如果采集粒度过细，会增加网络和存储压力；如果采集过粗，又无法定位问题。因此我按重要性分级采集：核心业务指标高频采集，普通资源指标中等频率采集，DEBUG 日志默认不采集，只有在问题排查时临时开启。通过采集分级和日志保留策略，控制可观测体系本身的成本。

### 结论

“智能设备运维平台”于2026年1月完成三期交付并全面上线。运行实践表明，平台在多基地、多设备、边缘协同的生产环境下总体稳定，关键设备非计划停机率下降约18%，运维响应效率和集团统一管理能力明显提升，基本达成了由“事后抢修”向“预防性维护”转型的建设目标。

从本次可观测性设计看，我没有把它作为监控工具建设处理，而是围绕故障可发现、链路可定位和问题可复盘这一主线，在指标、日志、链路追踪、告警收敛和发布观测等方面建立可落地的架构能力。实施过程中也存在一些取舍：可观测体系提升了排障效率，但也带来了采集成本、存储成本和告警规则维护成本；后续还需要结合生产运行数据，在根因分析、告警降噪和运行知识沉淀方面持续改进。

回顾项目全过程，作为系统架构师，我进一步认识到，可观测性的价值不在于监控面板数量，而在于能否贯穿真实业务链路并指导恢复动作。只有把可观测性落实为可发现、可定位、可复盘、可改进的工程能力，才能真正支撑平台长期稳定运行和持续发展。
