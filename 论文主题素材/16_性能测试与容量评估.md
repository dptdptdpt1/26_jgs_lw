项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

性能测试与容量评估解决的核心问题是：系统在真实业务压力下是否能稳定承载，以及瓶颈出现在哪里。它不是简单地“跑一下压测工具”，而是围绕业务负载建模、指标目标、测试环境、监控定位、容量推算和优化复测形成闭环。

这一技术方向通常包含：

- 性能目标定义：吞吐量、响应时间、错误率、资源水位、队列积压。
- 测试场景设计：基准测试、峰值测试、突发测试、稳定性测试、恢复补传测试。
- 压测数据准备：设备仿真、历史数据回放、脱敏数据构造。
- 瓶颈定位：入口层、消息队列、业务服务、数据库、缓存和网络链路。
- 容量规划：节点规格、实例数量、扩容阈值、预留冗余和成本取舍。

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 软件系统的性能测试技术（2025.11 真题）
- 负载均衡技术（2019、2025.05 真题）
- 秒杀场景及其技术解决方案（2025.11 真题，可迁移为设备高峰上报）
- 高并发系统设计
- 性能优化与容量规划
- 云原生系统弹性伸缩

### 1.3 从项目角度看

本项目覆盖 3 个生产基地、900 余台关键设备、24 台边缘节点。设备数据具有持续上报、局部突发、断点补传和早班集中开机等特点。中心侧还要同时支撑实时监控、告警判定、工单联动、驾驶舱查询和统计分析。如果只按平均流量估算容量，系统在换班、故障恢复、网络抖动后补传等场景下容易出现接入阻塞、Kafka 积压、告警延迟和查询变慢。因此，我将性能测试作为上线风险控制的一部分，用测试结果反推服务实例数、队列分区、数据库写入能力和扩容阈值。

## 2. 技术分析

### 2.1 技术点一：性能目标与指标体系

#### 技术解释

性能测试首先要定义目标，否则测试结果无法判断好坏。指标不能只看接口平均响应时间，还要结合业务链路定义端到端指标、系统资源指标和异常指标。

#### 项目中的具体场景

本项目的关键性能指标如下：

| 指标类型 | 指标 | 项目口径 |
| --- | --- | --- |
| 接入吞吐 | 每秒遥测数据接入量 | 覆盖 900 余台设备的持续上报和局部突发 |
| 链路延迟 | 数据上报到监控可见的延迟 | 常态下保持秒级可见 |
| 告警延迟 | 数据触发规则到告警生成的延迟 | 高优先级告警优先处理 |
| 队列水位 | Kafka Lag、消费速率 | 积压可观测、可恢复 |
| 查询性能 | 看板和报表响应时间 | 高频看板优先保障，复杂报表错峰执行 |
| 稳定性 | 长时间运行错误率和资源水位 | 服务无持续内存增长，资源不过早打满 |

#### 架构师决策点

我没有只用接口响应时间作为性能指标。原因是：本项目是事件驱动链路，用户真正关心的是设备数据多久能被看到、告警多久能生成、积压多久能恢复。接口响应时间只能反映入口局部性能，不能说明消息队列、规则引擎和存储链路是否健康。因此，我把“端到端延迟 + 队列积压 + 资源水位 + 业务效果”作为联合指标。

### 2.2 技术点二：测试场景建模

#### 技术解释

测试场景建模是把业务运行规律转化为可执行的压测模型。常见模型包括基准负载、峰值负载、突发负载、长稳负载和故障恢复负载。

#### 项目中的具体场景

本项目设计了五类性能测试场景：

| 测试场景 | 目的 | 项目示例 |
| --- | --- | --- |
| 基准测试 | 验证常态负载能力 | 900 余台设备按正常频率上报 |
| 峰值测试 | 验证高峰承载能力 | 早班开机后设备集中上线 |
| 突发测试 | 验证短时间冲击能力 | 某基地设备异常导致告警密集生成 |
| 补传测试 | 验证恢复能力 | 边缘节点断网后恢复，批量补传缓存数据 |
| 长稳测试 | 验证持续运行能力 | 连续运行 24 到 72 小时，观察资源水位和积压趋势 |

#### 架构师决策点

我没有只做峰值压测。原因是：峰值压测能说明系统能否扛住瞬时压力，但不能发现长时间运行后的资源泄漏、队列慢性积压和数据库写入抖动。对设备运维平台来说，稳定运行比单次峰值更重要。因此，测试计划同时覆盖峰值、补传和长稳场景。

### 2.3 技术点三：压测链路与数据准备

#### 技术解释

性能测试要尽量贴近真实链路。只压单个接口容易得到漂亮但无意义的数据。压测数据也要模拟真实设备、测点类型、数据质量和异常分布。

#### 项目中的具体场景

压测链路按项目主链路展开：

```text
设备仿真器 -> MQTT 接入 -> 中心接入服务 -> Kafka -> 规则引擎 -> 告警服务 -> 工单服务 -> 看板查询
```

数据准备包括：

- 按基地、产线、设备、测点生成设备标识和 Topic。
- 按温度、振动、电流、状态量等类型生成不同频率的数据。
- 模拟断网、乱序、重复上报、异常值和恢复补传。
- 使用脱敏历史数据回放验证报表和趋势分析性能。

#### 架构师决策点

我没有直接用随机数生成所有压测数据。原因是：完全随机的数据无法反映设备运行规律，也无法触发真实的规则判定和告警分布。压测数据既要有规模，也要有业务含义。只有这样，才能验证规则引擎、告警服务、工单服务和报表查询在真实负载下的表现。

### 2.4 技术点四：容量评估与扩容策略

#### 技术解释

容量评估是根据测试结果推算生产环境需要多少资源，并明确扩容条件。容量不是一次性算完，而是随着设备规模、测点数量和分析需求持续调整。

#### 项目中的具体场景

本项目按关键链路分别评估容量：

| 层次 | 容量关注点 | 扩容方式 |
| --- | --- | --- |
| 边缘节点 | 本地缓存、协议采集线程、断网保留时间 | 按产线和设备密度增加边缘节点 |
| 接入服务 | MQTT 连接数、写入吞吐、CPU 水位 | 横向扩容实例 |
| Kafka | Topic 分区、Broker 磁盘、消费 Lag | 增加分区和 Broker |
| 规则引擎 | 规则数量、窗口计算、消费速率 | 增加消费实例，按测点分区 |
| 时序库 | 写入吞吐、压缩、保留周期 | 分区、冷热分层、批量写入 |
| 看板查询 | 高频指标查询、聚合计算 | 缓存、预聚合、读写分离 |

扩容阈值不只看 CPU，还包括队列积压、写入延迟、查询响应时间和错误率。例如当 Kafka Lag 持续增长且消费服务 CPU 接近水位时，优先增加消费实例；如果消费实例增加后 Lag 仍不下降，再检查规则计算复杂度和数据库写入能力。

#### 架构师决策点

我没有把所有服务都按最大峰值预留固定资源。原因是：设备数据长期运行，资源成本必须可控。我的策略是：核心接入链路预留冗余，分析和报表链路通过异步化、缓存和错峰调度降低峰值压力；云原生环境下结合监控指标做弹性扩容。这样可以在可靠性和成本之间取得平衡。

### 2.5 技术点五：瓶颈定位与优化闭环

#### 技术解释

性能测试的价值不在于产出一次测试报告，而在于发现瓶颈、改进架构、复测验证。瓶颈定位通常依赖指标、日志和链路追踪联合分析。

#### 项目中的具体场景

压测中常见瓶颈及处理方式：

| 瓶颈位置 | 表现 | 优化措施 |
| --- | --- | --- |
| 接入服务 | MQTT 连接抖动、写入失败 | 连接池调优、批量写入、实例扩容 |
| Kafka | Lag 持续上升、Broker 磁盘压力高 | 增加分区、调整保留策略、扩容 Broker |
| 规则引擎 | 告警延迟升高 | 优化规则表达式、按测点分区消费、拆分复杂规则 |
| 数据库 | 写入延迟和查询延迟互相影响 | 批量写入、冷热分层、读写隔离、预聚合 |
| 看板 | 查询慢、并发访问时抖动 | 缓存高频指标、限制复杂查询、增加只读副本 |

闭环流程如下：

```text
定义目标 -> 设计场景 -> 执行压测 -> 采集指标 -> 定位瓶颈 -> 架构或参数优化 -> 复测验证 -> 固化容量基线
```

#### 架构师决策点

我没有把性能问题简单交给开发人员“优化代码”。原因是：性能瓶颈往往跨越接入、消息、计算、存储和查询多个层次，单点优化不一定有效。作为系统架构师，我重点关注链路级瓶颈和架构级取舍，例如是否需要异步削峰、是否需要拆分消费组、是否需要冷热分层、是否需要调整服务部署边界。

## 3. 论文主体内容

在本项目中，我把性能测试与容量评估作为上线风险控制和架构验证的重要环节。平台覆盖 3 个生产基地、900 余台关键设备和 24 台边缘节点，数据具有持续上报、局部突发、断点补传和早班集中上线等特点。如果只按照平均流量估算容量，系统在网络恢复补传、设备异常集中告警或报表高峰查询时，容易出现接入阻塞、消息积压、告警延迟和看板响应变慢。因此，我没有把性能测试理解为发布前的一次性压测，而是围绕业务链路建立性能目标、测试场景、监控定位和容量规划的闭环。

首先，我定义了面向业务链路的性能指标体系。传统接口压测往往关注平均响应时间和每秒请求数，但本项目采用事件驱动架构，入口接口性能并不能完全代表系统性能。因此，我将指标拆分为接入吞吐、端到端链路延迟、告警生成延迟、Kafka 消费积压、数据库写入延迟、看板查询响应时间和服务资源水位等维度。这样做的好处是，压测结果可以直接映射到用户体验和运维效果，例如设备数据是否能秒级可见、关键告警是否能及时生成、补传数据是否能在可接受时间内消化。

其次，我按真实业务规律设计压测场景，而不是只做单一峰值测试。测试场景包括常态负载、早班集中开机、单基地异常告警突发、边缘节点断网后的批量补传，以及连续 24 到 72 小时的稳定性测试。压测链路尽量覆盖完整主链路：设备仿真器通过 MQTT 上报数据，经中心接入服务写入 Kafka，再由规则引擎、告警服务、工单服务和看板查询共同承载压力。压测数据也不是完全随机生成，而是按基地、产线、设备、测点类型和异常比例构造，保证能够触发真实规则和查询模式。

再次，我根据压测结果进行分层容量评估。边缘层重点评估本地缓存、断网保留时间和协议采集线程；接入层重点评估连接数、写入吞吐和实例数；消息层重点评估 Topic 分区、Broker 磁盘和消费 Lag；计算层重点评估规则数量、窗口计算和消费速率；存储层重点评估时序数据写入、冷热分层和高频查询。对于核心接入和告警链路，我保留较高冗余；对于统计分析和复杂报表，我通过异步处理、预聚合、缓存和错峰调度降低峰值压力。这样既保证关键链路稳定，又避免所有服务都按最大峰值过度配置。

最后，我建立了性能优化闭环。每轮压测后，通过 Prometheus 指标、集中日志和链路追踪定位瓶颈。如果 Kafka Lag 持续增长，就先判断是分区不足、消费实例不足还是下游写入慢；如果看板查询变慢，就区分是数据库聚合成本高、缓存命中率低还是并发查询过多。针对不同瓶颈分别采取增加分区、扩容消费实例、批量写入、冷热分层、读写隔离和预聚合等措施，并通过复测验证优化效果。通过这一过程，项目在全面上线前形成了容量基线和扩容策略，为 2026 年 1 月三期全面上线提供了明确依据。
