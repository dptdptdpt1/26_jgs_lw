# 技术五：持续交付与自动化运维


## 1. 技术定位

### 1.1 从技术角度看

自动化运维解决的核心问题是：把高频、重复、规则明确的运维操作从人工执行转变为系统自动执行，降低人为失误风险，提升运维效率。

自动化运维通常覆盖：

- 持续集成与持续交付（CI/CD）
- 自动化部署与发布策略
- 自动化测试（单元测试、集成测试、冒烟测试）
- 自动化巡检与健康检查
- 自愈与弹性伸缩
- 自动化故障响应与预案执行

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 自动化运维及其应用
- 云上自动化运维及其应用（2024.05 真题）
- 持续交付与 DevOps
- 软件维护与架构演进
- 软件测试方法及应用（2025.05 真题）

### 1.3 从项目角度看

本项目分 3 期交付，18 个月内从零建设到全面上线，至今持续优化维护。项目涉及 22 人团队协作、多个服务并行开发、3 个基地分期上线。如果发布靠手动、巡检靠人工、故障靠经验，项目的交付效率和运行稳定性都无法保证。

## 2. 技术分析

### 2.1 技术点一：CI/CD 流水线

#### 技术解释

CI/CD 是自动化的基础。CI（持续集成）确保每次代码提交都经过自动构建和测试；CD（持续交付）确保通过测试的版本可以自动部署到目标环境。

#### 项目中的具体场景

本项目的 CI/CD 流水线设计：

```
代码提交 → 代码扫描（SonarQube）→ 单元测试 → 构建镜像 → 推送镜像仓库 → 部署到测试环境
→ 集成测试 → 人工审批 → 部署到预发布环境 → 冒烟测试 → 部署到生产环境（灰度）
→ 生产环境指标校验 → 全量发布或回滚
```

每个阶段的关键设计：

| 阶段 | 工具/方式 | 自动化内容 | 失败处理 |
| --- | --- | --- | --- |
| 代码扫描 | SonarQube | 检查代码规范、安全漏洞、重复率 | 阻断流水线，不允许合并 |
| 单元测试 | JUnit/Pytest | 核心业务逻辑的自动验证 | 阻断流水线 |
| 镜像构建 | Docker | 构建不可变镜像，打版本标签 | 自动重试一次，仍失败则阻断 |
| 集成测试 | 自动化测试框架 | 服务间接口联调验证 | 阻断流水线 |
| 人工审批 | 流水线暂停 | 运维或架构师确认后继续 | 超时自动取消 |
| 灰度发布 | K8s 滚动更新 | 先更新 1 个副本，观察指标 | 指标异常自动回滚 |
| 指标校验 | Prometheus API | 发布后 5 分钟内检查错误率和延迟 | 超过阈值自动回滚 |

#### 架构师决策点

我没有让开发人员直接在服务器上手动部署。原因是：一、手动部署不可重复，不同人的操作可能不同；二、手动部署没有审计记录，出问题难以追溯；三、分期交付期间频繁发布，手动操作效率太低。通过 CI/CD 流水线，每次发布都有完整的构建记录、测试结果和部署日志，出问题可以快速定位到是哪个版本引入的。

### 2.2 技术点二：灰度发布与回滚策略

#### 技术解释

灰度发布是指新版本先在小范围内验证，确认无问题后再全量发布。它解决的核心问题是：新版本如果存在缺陷，如何控制影响范围。

#### 项目中的具体场景

本项目中的灰度发布策略按场景分两种：

**常规更新（功能迭代、Bug 修复）**：滚动更新

```
全量 5 个副本 → 更新 1 个副本 → 观察 5 分钟 → 指标正常 → 更新剩余副本
                                        → 指标异常 → 回滚该副本
```

**重大版本（架构变更、数据库迁移）**：分基地灰度

```
选择 1 个基地试点 → 部署新版本 → 观察 1-2 天 → 确认稳定 → 逐基地推广
                              → 发现问题 → 回滚该基地，排查后重试
```

回滚机制设计：

| 场景 | 回滚方式 | 恢复时间 |
| --- | --- | --- |
| 容器部署异常 | K8s 自动回滚到上一个 ReplicaSet | 秒级 |
| 发布后指标异常 | 流水线自动触发回滚脚本 | 分钟级 |
| 数据库 Schema 变更 | 执行预定义的回滚 SQL | 分钟级 |
| 分基地灰度失败 | 回滚该基地的部署配置 | 分钟级 |

#### 架构师决策点

我没有采用蓝绿部署。原因是本项目的服务数量和流量规模不需要维护两套完整环境，滚动更新 + 分基地灰度已经足够。同时，蓝绿部署需要双倍资源，对于 3 个基地的部署环境来说成本过高。滚动更新可以在不停机的情况下逐步替换实例，分基地灰度可以在真实流量下验证新版本，两者组合既保证了安全性又控制了成本。

### 2.3 技术点三：自动化巡检与健康检查

#### 技术解释

自动化巡检是指系统按预定义的检查项和频率，自动检查各组件的健康状态，替代人工逐台登录查看。

#### 项目中的具体场景

本项目中的自动化巡检分为三个层次：

**基础设施层巡检**（每 5 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| 边缘节点在线 | Ping + MQTT 心跳 | 连续 3 次失败触发 P1 告警 |
| 中心服务存活 | K8s 健康检查接口 | 自动重启 Pod |
| 数据库主从状态 | 连接主从实例查询状态 | 主从切换异常触发 P0 告警 |
| Redis 哨兵状态 | 查询 Sentinel 状态 | 主节点不可达触发 P0 告警 |
| 磁盘使用率 | SSH 执行 df 命令 | 超过 80% 触发 P2 告警 |

**中间件层巡检**（每 10 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| Kafka 消费组 Lag | Prometheus 指标查询 | Lag > 10000 持续 3 次触发 P1 |
| MQTT 连接数 | Prometheus 指标查询 | 连接数骤降 50% 触发 P1 |
| Elasticsearch 集群状态 | API 查询集群 health | 状态为 yellow 触发 P2，red 触发 P0 |

**业务层巡检**（每 30 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| 设备在线率 | 统计各基地在线设备占比 | 低于 95% 触发 P1 |
| 数据上报成功率 | 比对预期上报量和实际接收量 | 低于 90% 触发 P1 |
| 告警处理时效 | 统计未处理告警的积压数量 | 超过 50 条未处理触发 P2 |

巡检结果自动汇总为巡检报告，每日发送给运维团队。

#### 架构师决策点

我没有让巡检脚本直接 SSH 到各服务器执行命令。原因是：一、SSH 方式不安全，需要管理大量密钥；二、SSH 方式和应用层解耦，应用健康但 SSH 不可达时会误报；三、无法利用 K8s 的自愈能力。因此我采用分层方式：K8s 层面通过 Liveness Probe 和 Readiness Probe 自动检测和重启；中间件和业务层面通过 Prometheus 指标和 API 接口检测；只有边缘节点因为不在 K8s 集群内，才通过 MQTT 心跳和网络探测检测。

同时，我必须考虑监控体系本身的资源消耗。心跳、指标采集、日志收集都会占用网络带宽、计算资源和存储资源。以边缘节点心跳为例，我对比了三种频率：10 秒心跳能快速发现异常，但 24 台节点每天产生约 8.6 万条心跳消息，MQTT Broker 压力大；60 秒心跳资源消耗小，但异常发现延迟 1 分钟，对生产影响大；30 秒心跳是平衡点，既能过滤大部分短暂断连，资源消耗也可接受。Prometheus 指标采集也按变化速度分级：服务存活状态 15 秒采集一次，CPU/内存 30 秒一次，业务指标 60 秒一次。日志采集按级别分级：ERROR 实时采集并告警，WARN 实时采集汇总告警，INFO 采样采集（每分钟 1 条），DEBUG 不采集。监控体系资源消耗约占系统总资源的 10%，这个投入是值得的，因为没有监控就无法发现和定位问题。

### 2.4 技术点四：自愈与弹性伸缩

#### 技术解释

自愈是指系统在检测到异常后自动执行修复动作，不依赖人工干预。弹性伸缩是指系统根据负载自动调整资源实例数量。

#### 项目中的具体场景

本项目中的自愈设计：

| 异常场景 | 检测方式 | 自动修复动作 |
| --- | --- | --- |
| 中心服务 Pod 崩溃 | K8s Liveness Probe 失败 | 自动重启 Pod |
| 边缘采集线程异常退出 | 边缘节点健康检测模块 | 自动重启采集线程并记录日志 |
| MQTT 连接断开 | 边缘节点连接状态检测 | 自动重连，3 次重连失败切换本地规则模式 |
| Kafka 消费组 Lag 持续升高 | Kafka Exporter / Prometheus 指标 | 自动扩容消费组实例（KEDA 或 Prometheus Adapter + HPA） |
| 服务响应时间 P99 超标 | Prometheus 指标告警 | 自动扩容服务副本（HPA） |

弹性伸缩配置（以规则引擎服务为例）：

这里需要区分 HPA 和 KEDA 的使用边界。HPA 适合常驻在线服务，依据 CPU、内存、接口延迟或 QPS 等指标调整副本数；KEDA 适合事件驱动任务，依据 Kafka Lag、队列长度、Cron 或 HTTP 事件触发扩缩容，并可在空闲时缩容到 0。KEDA 不是替代 HPA，而是把外部事件源指标转换为 Kubernetes 可伸缩指标，并创建或驱动 HPA 执行副本调整。因此，监控、告警、工单等在线服务主要使用 HPA，Kafka 消费、定时统计、低频回调等任务优先使用 KEDA。

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rule-engine-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rule-engine
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: kafka_consumer_lag
      target:
        type: AverageValue
        averageValue: "5000"
```

#### 架构师决策点

我没有让所有异常都自动修复。原因是：一、有些异常自动修复可能扩大影响（如数据库主从切换后如果应用连接池未更新，自动重启服务可能导致大量连接失败）；二、有些异常需要人工判断根因后再修复（如数据一致性问题）。因此我把自愈分为两类：基础设施层自愈（Pod 重启、线程重启、连接重连）全自动执行；业务层自愈（消费组扩容、服务扩容）自动执行但需要监控确认；数据层自愈（数据库故障切换）半自动，系统检测到故障后自动切换，但需要人工确认数据一致性。

### 2.5 技术点五：自动化故障响应与预案执行

#### 技术解释

自动化故障响应是指当特定故障模式被识别后，系统自动执行预定义的处置预案，而不是等人工判断后再行动。

#### 项目中的具体场景

本项目中的预案设计：

| 故障模式 | 识别条件 | 预案动作 | 执行方式 |
| --- | --- | --- | --- |
| 单基地网络中断 | 该基地所有边缘节点同时离线 | 切换到备用网络通道 + 通知基地运维 | 半自动（确认后执行） |
| Kafka 集群 Broker 宕机 | Broker 数量 < 集群副本数 | 自动调整分区 Leader + 通知中间件运维 | 全自动 |
| 短信通道限流 | 通知服务连续收到 rate limit 错误 | 切换备用短信通道 | 全自动 |
| 磁盘即将满 | 磁盘使用率 > 90% | 自动清理过期日志和临时文件 | 全自动 |
| 数据库连接池耗尽 | 连接池使用率 > 95% | 自动重启服务释放连接 + 通知运维 | 半自动 |

预案执行日志：每次预案执行都记录触发条件、执行动作、执行结果和执行时间，便于事后复盘和预案优化。

#### 架构师决策点

我没有把所有故障响应都设为全自动。原因是：一、有些故障的判断条件可能有误（如"所有边缘节点同时离线"可能是监控系统自身异常而非网络中断），全自动执行可能造成误操作；二、有些故障的修复动作有副作用（如重启服务会中断正在处理的请求），需要人工评估影响范围。因此我采用"全自动 + 半自动"混合策略：影响范围小、修复动作安全的故障全自动处理；影响范围大、修复有副作用的故障先通知人工确认再执行。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。本文结合该项目建设实践，首先简要概述平台建设背景和总体架构特点，随后围绕持续交付与自动化运维，阐述我如何从流水线、环境标准化、灰度发布、自动化巡检、故障预案和运行反馈几个方面开展架构设计与实施，并分析相关技术选型、实施效果和架构取舍。

### 正文

#### 项目背景

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前建设目标并预留后续演进空间。

#### 过渡内容

持续交付与自动化运维不是把部署脚本自动执行一遍，而是要控制多服务、多环境和多批次上线过程中的质量风险。本项目 18 个月内分三期建设，设备接入、告警、工单和分析能力不断迭代。如果仍依赖人工打包、手工上传和临时检查，环境差异、版本不可追溯、回滚困难和巡检遗漏都会放大。因此，我将持续交付作为研发交付底座，将自动化运维作为运行保障手段，二者共同支撑平台持续演进。

#### 主体内容

首先，我建立标准化流水线。代码提交后，合并门禁执行代码扫描、单元测试和契约测试；发布分支合并后，流水线构建容器镜像，生成明确版本号和 Git commit 标识，并推送到私有镜像仓库；部署到测试和预发布环境后，执行集成测试、端到端回归和数据库脚本验证；生产发布前，检查性能基线、回滚方案、监控告警和灰度计划。通过流水线，构建、测试、部署和审批过程都有记录，出现问题时可以追溯到具体版本、提交和执行人。

其次，我做了环境标准化设计。所有核心服务以容器镜像交付，同一镜像在测试、预发布和生产环境运行，环境差异通过 ConfigMap、Secret 和配置中心注入。数据库迁移脚本纳入版本管理，禁止生产环境手工修改表结构；Kafka Topic、Redis 配置、网关路由和告警阈值都通过配置模板和审批流程管理。这样可以避免“开发环境能跑、测试环境报错、生产环境再修”的问题，也能减少人员差异带来的不可重复发布。

再次，我将灰度发布作为控制生产风险的关键机制。常规服务采用 Kubernetes 滚动更新，先替换少量副本并观察接口错误率、P99 延迟、Kafka Lag 和告警生成延迟；重大规则调整或核心链路改造采用分基地灰度，先选择一个基地试运行，再逐步推广到其他基地。API 网关负责管理类请求的路由和限流，Kafka 消费链路则通过消费者实例和消费组控制发布节奏。发布后如果核心指标异常，流水线支持快速回滚到上一版本，数据库变更则要求提前设计可回退脚本或兼容字段策略。

在自动化运维方面，我围绕“发现、判断、处置、复盘”建立机制。基础巡检覆盖 Kubernetes Pod 状态、节点资源、数据库连接、Redis 内存、Kafka Lag、MQTT Broker 连接数和边缘节点在线率；业务巡检覆盖数据上报成功率、告警生成延迟、工单创建成功率和工单闭环时长。巡检结果进入 Prometheus 和告警平台，常见异常触发预案。例如非核心实例异常重启、磁盘空间接近阈值、Kafka 消费积压和短信通道异常，可以由自动化脚本或半自动流程处理；涉及设备安全、数据库主从切换和大范围网络异常的场景，则必须人工确认后执行。

我还将运行反馈纳入持续改进。每次生产故障、发布回滚或人工补偿都形成复盘记录，判断是否需要补充监控指标、优化发布门禁、增加自动化预案或调整架构设计。例如某次规则服务发布后消费耗时升高，复盘后不仅回滚规则版本，还增加了规则执行耗时指标和发布前的规则性能测试。这样，运维不再是被动处理故障，而是不断反哺测试、发布和架构演进。

该方案的取舍是，自动化程度越高，对流程规范、脚本可靠性和权限控制要求越高。为避免自动化误操作，我将预案分为全自动、半自动和人工三类，并要求所有自动动作可审计、可回滚、可评估。对于生产设备相关动作，坚持人工确认优先；对于平台运行层面的低风险重复动作，则逐步自动化。

#### 论文结论

“智能设备运维平台”于2026年1月完成三期交付并全面上线。运行实践表明，平台在多基地、多设备、边缘协同的生产环境下总体稳定，关键设备非计划停机率下降约18%，运维响应效率和集团统一管理能力明显提升，基本达成了由“事后抢修”向“预防性维护”转型的建设目标。

从本次持续交付与自动化运维设计看，我没有把它作为部署脚本处理，而是围绕可重复交付、可控发布和持续运行这一主线，在流水线、环境标准化、灰度发布、自动化巡检和故障预案等方面建立可落地的架构能力。实施过程中也存在一些取舍：自动化提升了效率和稳定性，但也带来了流程维护、权限控制和预案可靠性要求；后续还需要结合生产运行数据，在智能巡检、故障演练和自动化预案评估方面持续改进。

回顾项目全过程，作为系统架构师，我进一步认识到，持续交付和自动化运维不是运维阶段的附属工作，而是架构可演进能力的重要组成部分。只有把交付和运维落实为可追溯、可回滚、可持续优化的工程体系，才能真正支撑平台长期稳定运行和持续发展。
