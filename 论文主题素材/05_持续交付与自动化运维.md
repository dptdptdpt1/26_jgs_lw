# 技术五：持续交付与自动化运维

## 过渡段（可直接写入正文）

持续交付与自动化运维不是把部署脚本自动执行一遍，而是要控制多服务、多环境和多批次上线过程中的质量风险。本项目周期18个月、团队22人、采用3期交付，设备接入、告警、工单和分析能力不断迭代，如果仍依赖人工部署和临时检查，环境差异、回滚困难和发布影响面都会放大。因此，我围绕流水线、环境标准化、灰度发布、自动化巡检和运行反馈设计交付体系。

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

## 1. 技术定位

### 1.1 从技术角度看

自动化运维解决的核心问题是：把高频、重复、规则明确的运维操作从人工执行转变为系统自动执行，降低人为失误风险，提升运维效率。

自动化运维通常覆盖：

- 持续集成与持续交付（CI/CD）
- 自动化部署与发布策略
- 自动化测试（单元测试、集成测试、冒烟测试）
- 自动化巡检与健康检查
- 自愈与弹性伸缩
- 自动化故障响应与预案执行

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 自动化运维及其应用
- 云上自动化运维及其应用（2024.05 真题）
- 持续交付与 DevOps
- 软件维护与架构演进
- 软件测试方法及应用（2025.05 真题）

### 1.3 从项目角度看

本项目分 3 期交付，18 个月内从零建设到全面上线，至今持续优化维护。项目涉及 22 人团队协作、多个服务并行开发、3 个基地分期上线。如果发布靠手动、巡检靠人工、故障靠经验，项目的交付效率和运行稳定性都无法保证。

## 2. 技术分析

### 2.1 技术点一：CI/CD 流水线

#### 技术解释

CI/CD 是自动化的基础。CI（持续集成）确保每次代码提交都经过自动构建和测试；CD（持续交付）确保通过测试的版本可以自动部署到目标环境。

#### 项目中的具体场景

本项目的 CI/CD 流水线设计：

```
代码提交 → 代码扫描（SonarQube）→ 单元测试 → 构建镜像 → 推送镜像仓库 → 部署到测试环境
→ 集成测试 → 人工审批 → 部署到预发布环境 → 冒烟测试 → 部署到生产环境（灰度）
→ 生产环境指标校验 → 全量发布或回滚
```

每个阶段的关键设计：

| 阶段 | 工具/方式 | 自动化内容 | 失败处理 |
| --- | --- | --- | --- |
| 代码扫描 | SonarQube | 检查代码规范、安全漏洞、重复率 | 阻断流水线，不允许合并 |
| 单元测试 | JUnit/Pytest | 核心业务逻辑的自动验证 | 阻断流水线 |
| 镜像构建 | Docker | 构建不可变镜像，打版本标签 | 自动重试一次，仍失败则阻断 |
| 集成测试 | 自动化测试框架 | 服务间接口联调验证 | 阻断流水线 |
| 人工审批 | 流水线暂停 | 运维或架构师确认后继续 | 超时自动取消 |
| 灰度发布 | K8s 滚动更新 | 先更新 1 个副本，观察指标 | 指标异常自动回滚 |
| 指标校验 | Prometheus API | 发布后 5 分钟内检查错误率和延迟 | 超过阈值自动回滚 |

#### 架构师决策点

我没有让开发人员直接在服务器上手动部署。原因是：一、手动部署不可重复，不同人的操作可能不同；二、手动部署没有审计记录，出问题难以追溯；三、分期交付期间频繁发布，手动操作效率太低。通过 CI/CD 流水线，每次发布都有完整的构建记录、测试结果和部署日志，出问题可以快速定位到是哪个版本引入的。

### 2.2 技术点二：灰度发布与回滚策略

#### 技术解释

灰度发布是指新版本先在小范围内验证，确认无问题后再全量发布。它解决的核心问题是：新版本如果存在缺陷，如何控制影响范围。

#### 项目中的具体场景

本项目中的灰度发布策略按场景分两种：

**常规更新（功能迭代、Bug 修复）**：滚动更新

```
全量 5 个副本 → 更新 1 个副本 → 观察 5 分钟 → 指标正常 → 更新剩余副本
                                        → 指标异常 → 回滚该副本
```

**重大版本（架构变更、数据库迁移）**：分基地灰度

```
选择 1 个基地试点 → 部署新版本 → 观察 1-2 天 → 确认稳定 → 逐基地推广
                              → 发现问题 → 回滚该基地，排查后重试
```

回滚机制设计：

| 场景 | 回滚方式 | 恢复时间 |
| --- | --- | --- |
| 容器部署异常 | K8s 自动回滚到上一个 ReplicaSet | 秒级 |
| 发布后指标异常 | 流水线自动触发回滚脚本 | 分钟级 |
| 数据库 Schema 变更 | 执行预定义的回滚 SQL | 分钟级 |
| 分基地灰度失败 | 回滚该基地的部署配置 | 分钟级 |

#### 架构师决策点

我没有采用蓝绿部署。原因是本项目的服务数量和流量规模不需要维护两套完整环境，滚动更新 + 分基地灰度已经足够。同时，蓝绿部署需要双倍资源，对于 3 个基地的部署环境来说成本过高。滚动更新可以在不停机的情况下逐步替换实例，分基地灰度可以在真实流量下验证新版本，两者组合既保证了安全性又控制了成本。

### 2.3 技术点三：自动化巡检与健康检查

#### 技术解释

自动化巡检是指系统按预定义的检查项和频率，自动检查各组件的健康状态，替代人工逐台登录查看。

#### 项目中的具体场景

本项目中的自动化巡检分为三个层次：

**基础设施层巡检**（每 5 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| 边缘节点在线 | Ping + MQTT 心跳 | 连续 3 次失败触发 P1 告警 |
| 中心服务存活 | K8s 健康检查接口 | 自动重启 Pod |
| 数据库主从状态 | 连接主从实例查询状态 | 主从切换异常触发 P0 告警 |
| Redis 哨兵状态 | 查询 Sentinel 状态 | 主节点不可达触发 P0 告警 |
| 磁盘使用率 | SSH 执行 df 命令 | 超过 80% 触发 P2 告警 |

**中间件层巡检**（每 10 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| Kafka 消费组 Lag | Prometheus 指标查询 | Lag > 10000 持续 3 次触发 P1 |
| MQTT 连接数 | Prometheus 指标查询 | 连接数骤降 50% 触发 P1 |
| Elasticsearch 集群状态 | API 查询集群 health | 状态为 yellow 触发 P2，red 触发 P0 |

**业务层巡检**（每 30 分钟）：

| 检查项 | 检查方式 | 异常处理 |
| --- | --- | --- |
| 设备在线率 | 统计各基地在线设备占比 | 低于 95% 触发 P1 |
| 数据上报成功率 | 比对预期上报量和实际接收量 | 低于 90% 触发 P1 |
| 告警处理时效 | 统计未处理告警的积压数量 | 超过 50 条未处理触发 P2 |

巡检结果自动汇总为巡检报告，每日发送给运维团队。

#### 架构师决策点

我没有让巡检脚本直接 SSH 到各服务器执行命令。原因是：一、SSH 方式不安全，需要管理大量密钥；二、SSH 方式和应用层解耦，应用健康但 SSH 不可达时会误报；三、无法利用 K8s 的自愈能力。因此我采用分层方式：K8s 层面通过 Liveness Probe 和 Readiness Probe 自动检测和重启；中间件和业务层面通过 Prometheus 指标和 API 接口检测；只有边缘节点因为不在 K8s 集群内，才通过 MQTT 心跳和网络探测检测。

同时，我必须考虑监控体系本身的资源消耗。心跳、指标采集、日志收集都会占用网络带宽、计算资源和存储资源。以边缘节点心跳为例，我对比了三种频率：10 秒心跳能快速发现异常，但 24 台节点每天产生约 8.6 万条心跳消息，MQTT Broker 压力大；60 秒心跳资源消耗小，但异常发现延迟 1 分钟，对生产影响大；30 秒心跳是平衡点，既能过滤大部分短暂断连，资源消耗也可接受。Prometheus 指标采集也按变化速度分级：服务存活状态 15 秒采集一次，CPU/内存 30 秒一次，业务指标 60 秒一次。日志采集按级别分级：ERROR 实时采集并告警，WARN 实时采集汇总告警，INFO 采样采集（每分钟 1 条），DEBUG 不采集。监控体系资源消耗约占系统总资源的 10%，这个投入是值得的，因为没有监控就无法发现和定位问题。

### 2.4 技术点四：自愈与弹性伸缩

#### 技术解释

自愈是指系统在检测到异常后自动执行修复动作，不依赖人工干预。弹性伸缩是指系统根据负载自动调整资源实例数量。

#### 项目中的具体场景

本项目中的自愈设计：

| 异常场景 | 检测方式 | 自动修复动作 |
| --- | --- | --- |
| 中心服务 Pod 崩溃 | K8s Liveness Probe 失败 | 自动重启 Pod |
| 边缘采集线程异常退出 | 边缘节点健康检测模块 | 自动重启采集线程并记录日志 |
| MQTT 连接断开 | 边缘节点连接状态检测 | 自动重连，3 次重连失败切换本地规则模式 |
| Kafka 消费组 Lag 持续升高 | Kafka Exporter / Prometheus 指标 | 自动扩容消费组实例（KEDA 或 Prometheus Adapter + HPA） |
| 服务响应时间 P99 超标 | Prometheus 指标告警 | 自动扩容服务副本（HPA） |

弹性伸缩配置（以规则引擎服务为例）：

这里需要区分 HPA 和 KEDA 的使用边界。HPA 适合常驻在线服务，依据 CPU、内存、接口延迟或 QPS 等指标调整副本数；KEDA 适合事件驱动任务，依据 Kafka Lag、队列长度、Cron 或 HTTP 事件触发扩缩容，并可在空闲时缩容到 0。KEDA 不是替代 HPA，而是把外部事件源指标转换为 Kubernetes 可伸缩指标，并创建或驱动 HPA 执行副本调整。因此，监控、告警、工单等在线服务主要使用 HPA，Kafka 消费、定时统计、低频回调等任务优先使用 KEDA。

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: rule-engine-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: rule-engine
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
  - type: Pods
    pods:
      metric:
        name: kafka_consumer_lag
      target:
        type: AverageValue
        averageValue: "5000"
```

#### 架构师决策点

我没有让所有异常都自动修复。原因是：一、有些异常自动修复可能扩大影响（如数据库主从切换后如果应用连接池未更新，自动重启服务可能导致大量连接失败）；二、有些异常需要人工判断根因后再修复（如数据一致性问题）。因此我把自愈分为两类：基础设施层自愈（Pod 重启、线程重启、连接重连）全自动执行；业务层自愈（消费组扩容、服务扩容）自动执行但需要监控确认；数据层自愈（数据库故障切换）半自动，系统检测到故障后自动切换，但需要人工确认数据一致性。

### 2.5 技术点五：自动化故障响应与预案执行

#### 技术解释

自动化故障响应是指当特定故障模式被识别后，系统自动执行预定义的处置预案，而不是等人工判断后再行动。

#### 项目中的具体场景

本项目中的预案设计：

| 故障模式 | 识别条件 | 预案动作 | 执行方式 |
| --- | --- | --- | --- |
| 单基地网络中断 | 该基地所有边缘节点同时离线 | 切换到备用网络通道 + 通知基地运维 | 半自动（确认后执行） |
| Kafka 集群 Broker 宕机 | Broker 数量 < 集群副本数 | 自动调整分区 Leader + 通知中间件运维 | 全自动 |
| 短信通道限流 | 通知服务连续收到 rate limit 错误 | 切换备用短信通道 | 全自动 |
| 磁盘即将满 | 磁盘使用率 > 90% | 自动清理过期日志和临时文件 | 全自动 |
| 数据库连接池耗尽 | 连接池使用率 > 95% | 自动重启服务释放连接 + 通知运维 | 半自动 |

预案执行日志：每次预案执行都记录触发条件、执行动作、执行结果和执行时间，便于事后复盘和预案优化。

#### 架构师决策点

我没有把所有故障响应都设为全自动。原因是：一、有些故障的判断条件可能有误（如"所有边缘节点同时离线"可能是监控系统自身异常而非网络中断），全自动执行可能造成误操作；二、有些故障的修复动作有副作用（如重启服务会中断正在处理的请求），需要人工评估影响范围。因此我采用"全自动 + 半自动"混合策略：影响范围小、修复动作安全的故障全自动处理；影响范围大、修复有副作用的故障先通知人工确认再执行。

## 3. 论文主体内容（按细分主题选用）

### 3.1 CI/CD 与持续交付主体

在本项目中，【**CI/CD 与持续交付**】不是简单的自动构建部署，而是保障 3 期交付、22 人协作、3 个基地分期上线的工程基础设施。项目初期，发布流程是开发人员在本地打包，通过 SCP 上传到服务器，手动重启服务。这种做法导致三个问题：一是环境不一致，开发环境能跑但测试环境报错，测试环境能跑但生产环境报错，排查这类问题平均耗时半天；二是发布不可重复，不同人打包的结果可能不同，同一个代码版本打包两次可能产生不同镜像；三是没有审计记录，出问题后无法追溯是哪个版本、谁在什么时间发布的。

因此我建立了完整的【**CI/CD 流水线**】。代码提交后自动触发四个阶段：第一阶段是代码质量检查，SonarQube 扫描代码规范、安全漏洞和重复率，不通过不允许合并；第二阶段是单元测试，核心业务逻辑的测试用例自动执行，覆盖率低于阈值阻断流水线；第三阶段是镜像构建，使用 Docker 构建不可变镜像，打上 Git commit hash 作为版本标签，确保同一代码永远产生同一镜像；第四阶段是自动部署到测试环境，执行集成测试验证服务间接口联调。

流水线的关键设计是【**分层门禁**】。代码扫描和单元测试作为合并门禁，执行时间控制在 5 分钟内，确保快速反馈；集成测试作为发布门禁，在 release 分支合并时触发，执行时间 30 分钟内；性能基线验证作为上线门禁，在生产发布前执行。人工审批卡点设置在部署到预发布环境之前，运维或架构师确认后才继续。这样既保证了自动化效率，又保留了关键节点的人工把控。

容器化交付是 CI/CD 的基础。所有服务统一打包为 Docker 镜像，开发、测试和生产使用同一镜像，通过环境变量区分配置。这消除了"本地能跑、线上不行"的问题。镜像推送到 Harbor 私有仓库后，通过 Helm Chart 定义部署配置，不同环境使用不同的 values 文件。每次发布都有完整的构建记录、测试结果、镜像版本和部署日志，出问题可以快速定位到是哪个版本引入的。

项目效果方面，CI/CD 流水线将发布周期从手动操作的 2-3 天缩短到 30 分钟，其中代码扫描 2 分钟、单元测试 3 分钟、镜像构建 5 分钟、集成测试 20 分钟。二期和三期累计发布 150 多次，未出现因环境不一致或打包差异导致的线上问题。CI/CD 不仅提升了交付效率，更重要的是建立了团队对发布过程的信心，发布从"紧张的大事"变成"日常的小事"。

### 3.2 灰度发布与回滚策略主体

在本项目中，【**灰度发布与回滚策略**】不是可选的高级功能，而是控制发布风险的必要手段。平台涉及设备接入、实时监控、告警生成、工单流转等核心业务，如果新版本存在缺陷，全量发布后影响范围是 3 个基地、900 余台设备、24 小时生产运行。因此必须通过灰度发布控制影响范围，通过快速回滚缩短故障恢复时间。

本项目根据变更风险程度采用两种灰度策略。常规更新（功能迭代、Bug 修复）采用滚动更新：全量 5 个副本，先更新 1 个副本，观察 5 分钟，指标正常后更新剩余副本，指标异常则回滚该副本。重大版本（架构变更、数据库迁移、协议调整）采用分基地灰度：选择 1 个基地试点，部署新版本后观察 1-2 天，确认稳定后逐基地推广，发现问题则回滚该基地。

滚动更新的关键是【**指标校验**】。发布后 5 分钟内，流水线自动调用 Prometheus API 检查四类指标：错误率（HTTP 5xx 比例）、延迟（P99 响应时间）、Kafka Lag（消费积压）和设备在线率。每类指标都有阈值，超过阈值自动触发回滚。例如错误率阈值是 1%，如果发布后 5 分钟内错误率超过 1%，流水线自动执行 `kubectl rollout undo` 回滚到上一个版本。回滚是秒级的，因为 K8s 保留了上一个 ReplicaSet，回滚只是把流量切回去。

分基地灰度的关键是试点基地的选择。我选择 B 基地作为试点，原因是 B 基地设备数量适中（约 300 台），生产节奏稳定，运维人员配合度高。试点期间重点观察三个维度：技术维度（服务稳定性、资源使用、错误日志）、业务维度（告警准确性、工单流转、数据完整性）、运维维度（部署过程、回滚验证、监控告警）。试点通过后，再按 B 基地 → A 基地 → C 基地的顺序推广，每个基地间隔 3-5 天。

项目二期发生过一次灰度发布拦截问题的案例。工单服务新增了自动派单功能，滚动更新第 1 个副本后，指标校验发现工单创建接口 P99 延迟从 200ms 升到 2 秒，原因是自动派单逻辑查询人员数据库时没有走缓存，全表扫描导致数据库 CPU 飙升。流水线自动回滚，开发人员修复缓存后重新发布。如果没有灰度发布，这个缺陷会导致 3 个基地的工单服务全部变慢，影响整个运维流程。

项目效果方面，滚动更新 + 分基地灰度的组合策略，让发布风险可控。二期和三期累计发布 150 多次，其中 3 次被灰度机制拦截（错误率超标 1 次、延迟超标 2 次），避免了全量发布后的故障。回滚操作累计执行 5 次，平均恢复时间 2 分钟。灰度发布不是为了"不发布"，而是为了"敢发布"——因为知道有问题能快速回滚，团队才敢频繁发布、快速迭代。

### 3.3 自动化巡检与健康检查主体

在本项目中，【**自动化巡检**】不是锦上添花，而是替代人工逐台登录查看的必要能力。项目涉及 24 台边缘节点、10 多个中心服务、Kafka 集群、MQTT Broker、Redis、Elasticsearch 等组件，如果每天人工巡检一轮，至少需要 2 小时，而且人工巡检有三个问题：一是容易遗漏，24 台节点逐台检查，疲劳后容易跳过；二是标准不统一，不同人检查的深度和判断标准不同；三是无法实时，人工巡检是一天一次，中间发生的异常可能要等到下一次巡检才发现。

因此我建立了【**三层自动化巡检体系**】。基础设施层每 5 分钟巡检一次，覆盖边缘节点在线状态、中心服务存活、数据库主从状态、Redis 哨兵状态和磁盘使用率。中间件层每 10 分钟巡检一次，覆盖 Kafka 消费组 Lag、MQTT 连接数、Elasticsearch 集群状态。业务层每 30 分钟巡检一次，覆盖设备在线率、数据上报成功率、告警处理时效。

边缘节点巡检是本项目的特殊挑战。边缘节点部署在 3 个生产基地，不在 K8s 集群内，无法通过 K8s 健康检查检测。我采用 MQTT 心跳机制：边缘节点每 30 秒发送一次心跳消息到 MQTT Broker，中心服务订阅心跳 topic，连续 3 次未收到心跳则判定节点离线，触发 P1 告警。这种机制比 Ping 探测更可靠，因为 Ping 只能检测网络连通性，MQTT 心跳能检测边缘节点的采集程序是否正常运行。

巡检结果分级告警是另一个关键设计。不是所有异常都需要立即处理，我按影响程度分为四级：P0（核心业务中断，如数据库主节点宕机）立即电话通知；P1（业务降级，如边缘节点离线、Kafka Lag 持续升高）立即企微通知；P2（潜在风险，如磁盘使用率超过 80%、告警积压超过 50 条）工作时间通知；P3（信息类，如非核心服务重启）仅记录日志。告警升级机制：P1 告警如果 15 分钟内未确认，自动升级为 P0 电话通知。

巡检报告是巡检体系的闭环。每天早上 8 点自动生成巡检报告，包含过去 24 小时的异常事件、处理结果、趋势分析和建议。报告发送给运维团队和架构师，作为日常运维和架构优化的输入。例如报告连续一周显示某基地边缘节点在凌晨 1 点频繁离线，排查发现是现场 4G 基站定时维护，调整心跳超时时间后解决了误报。

项目效果方面，自动化巡检替代了每日 2 小时的人工检查，异常发现时间从"下一次巡检"缩短到"5 分钟内"。上线一年内，巡检系统累计发现并告警 200 多次异常，其中 P0 级 5 次（数据库主从切换、MQTT Broker 宕机等），P1 级 30 多次（边缘节点离线、Kafka Lag 升高等），大部分在人工介入前已被自愈机制处理。自动化巡检的价值不仅在于效率提升，更在于建立了 7x24 小时的持续监控能力，这是人工巡检无法实现的。

### 3.4 自愈与弹性伸缩主体

在本项目中，【**自愈与弹性伸缩**】不是替代人工运维，而是处理高频、低风险、可自动修复的异常，让运维人员聚焦于复杂问题。平台运行中，最常见的异常是 Pod 崩溃、采集线程退出、MQTT 连接断开、Kafka Lag 升高，这些异常占日常告警的 80% 以上。如果每次都等人工处理，运维人员会被大量简单问题淹没，真正需要关注的复杂问题反而被延误。

因此我按自愈的确定性程度分三层设计。第一层是基础设施自愈，完全自动执行：Pod 崩溃时 K8s Liveness Probe 检测失败后自动重启，边缘采集线程异常退出时守护进程自动重启，MQTT 连接断开时自动重连（3 次重连失败则切换本地规则模式）。这类自愈确定性高、副作用小，不需要人工确认。第二层是业务自愈，自动执行但需要监控确认：Kafka 消费组 Lag 持续升高时自动扩容消费实例，服务响应时间超标时自动扩容服务副本。这类自愈虽然自动执行，但扩容可能带来资源成本增加，需要监控确认是否合理。第三层是数据层自愈，半自动执行：数据库主从切换时系统自动完成切换，但需要人工确认数据一致性，检查是否有未同步的事务。

【**弹性伸缩**】是自愈的重要组成部分。本项目按服务特性分别使用 HPA 和 KEDA。在线服务（监控、告警、工单等）使用 HPA，基于 CPU、内存或自定义指标（如接口延迟）自动扩缩容。事件驱动任务（Kafka 消费、定时统计等）使用 KEDA，基于 Kafka Lag、Cron 表达式等事件源触发扩缩容，空闲时可缩容到 0 节省资源。

以规则引擎服务为例，HPA 配置如下：最小副本数 3，最大副本数 10，CPU 阈值 70%，Kafka Lag 阈值 5000。当 CPU 超过 70% 或 Kafka Lag 超过 5000 时自动扩容，当负载降低后自动缩容。扩容决策时间约 30 秒（指标采集 + 决策），Pod 启动时间约 60 秒（镜像拉取 + 应用启动），从触发扩容到新 Pod 接受流量约 2 分钟。

项目二期发生过一次自愈机制发挥作用的案例。凌晨 2 点，B 基地 MQTT Broker 因内存溢出宕机，24 台边缘节点全部断连。监控系统 30 秒内检测到 MQTT 连接数骤降，触发 P0 告警并自动重启 Broker Pod。Broker 重启后，边缘节点自动重连，整个过程 3 分钟内恢复。如果等人工处理，从接到告警到登录服务器、排查问题、重启服务，至少需要 30 分钟，期间 300 台设备的数据采集全部中断。

项目效果方面，自愈机制处理了 80% 的日常异常，运维人员处理的告警从每天 20 多次降到 4-5 次。弹性伸缩让资源使用更合理：早班开机高峰时自动扩容，夜间低谷时自动缩容，资源成本降低约 30%。自愈和弹性伸缩的价值不仅在于减少人工干预，更在于让系统具备了"自己照顾自己"的能力，运维人员可以聚焦于架构优化和复杂问题处理。

### 3.5 自动化故障响应与预案执行主体

在本项目中，【**自动化故障响应与预案执行**】不是让系统自己修一切，而是对已知故障模式建立预定义的处置预案，在故障发生时快速响应、减少损失。平台运行中，有些故障模式反复出现：短信通道限流、磁盘即将满、Kafka Broker 宕机、单基地网络中断。如果每次都要人工判断、人工执行修复，响应时间长、执行容易出错，而且不同人的处理方式可能不同。

因此我建立了【**故障预案库**】。每个预案包含四个要素：故障模式（什么情况）、识别条件（怎么判断）、预案动作（做什么）和执行方式（全自动还是半自动）。根据故障的判断确定性和修复副作用，我将预案分为两类：全自动预案和半自动预案。

全自动预案适用于判断条件明确、修复动作安全的故障。短信通道限流时，通知服务检测到连续 rate limit 错误，自动切换到备用短信通道，整个过程 10 秒内完成，用户无感知。磁盘使用率超过 90% 时，自动清理过期日志和临时文件，保留最近 7 天的日志，清理过程不影响正常服务。Kafka 集群 Broker 宕机时，自动调整分区 Leader 选举策略，确保剩余 Broker 能继续提供服务。

半自动预案适用于判断条件可能有误、修复动作有副作用的故障。单基地网络中断时，系统检测到该基地所有边缘节点同时离线，自动发送告警通知运维人员，运维人员确认后才执行切换备用网络通道的操作。原因是"所有边缘节点同时离线"可能是监控系统自身异常而非网络中断，全自动切换可能造成误操作。数据库连接池耗尽时，系统检测到连接池使用率超过 95%，自动发送告警并建议重启服务，运维人员确认后执行。原因是重启服务会中断正在处理的请求，需要评估影响范围。

预案执行的关键是日志记录和复盘优化。每次预案执行都记录四个信息：触发条件（什么时间、什么指标达到什么阈值）、执行动作（执行了什么命令或脚本）、执行结果（成功还是失败、耗时多久）和后续影响（执行后指标是否恢复、是否有副作用）。这些日志用于事后复盘，分析预案是否有效、识别条件是否准确、执行动作是否合适。

项目上线一年内，预案执行 80 多次。其中全自动预案执行 60 多次：短信通道切换 15 次、磁盘清理 20 次、Kafka Leader 调整 5 次、Pod 重启 20 多次。半自动预案执行 20 多次：网络中断切换 3 次、数据库连接池重启 5 次、其他复杂故障 12 次。预案执行成功率 95%，5 次失败是因为预案脚本未覆盖新的故障变种，失败后补充预案脚本并复盘优化。

预案的持续优化是闭环的关键。每次预案执行后，运维团队会复盘三个问题：识别条件是否准确（有没有误触发或漏触发）、执行动作是否有效（故障是否恢复、是否有副作用）、是否有更好的处理方式。例如，磁盘清理预案最初是清理所有超过 7 天的日志，但有一次清理了审计日志导致合规检查失败，复盘后调整为只清理应用日志，审计日志保留 30 天。预案不是写完就结束，而是需要根据实际运行情况持续迭代优化。

项目效果方面，自动化故障响应将平均故障恢复时间（MTTR）从人工处理的 30 分钟缩短到自动预案的 3 分钟。预案库积累了 20 多个故障模式的处置方案，成为团队的知识资产，新运维人员可以通过预案库快速了解常见故障的处理方式。自动化故障响应的核心价值不在于替代人工，而在于把"人记住的经验"变成"系统执行的预案"，让故障处置标准化、可重复、可追溯。
