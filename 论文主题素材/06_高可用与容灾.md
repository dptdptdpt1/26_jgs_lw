# 技术六：高可用与容灾


## 1. 技术定位

### 1.1 从技术角度看

高可用与容灾解决的是“系统在异常情况下如何持续提供服务”的问题。它不是单一组件的稳定性，而是入口、服务、缓存、数据库、边缘节点、备份恢复和运维监控的全链路保障能力。

这一技术方向通常包含：

- 入口高可用
- 服务多副本部署
- 缓存与数据库高可用
- 边缘侧容错
- 备份恢复
- 可观测性与演练机制

### 1.2 从考题角度看

这个技术方向适合以下题目：

- 高可用架构设计
- 容灾设计
- 软件可靠性设计
- 稳定性工程设计
- 系统演进设计

如果题目考“高可用”“可靠性”“容灾”，这一主题本身就足以展开成一篇论文主体。

### 1.3 从项目角度看

在本项目中，平台一旦中断，影响的不是单一功能，而是整条设备运维主链路：

- 设备状态无法及时接入
- 告警无法及时识别
- 工单无法及时派发与处理
- 管理层无法获取运行态势

同时，项目采用分 3 期交付，后续还要持续优化，这意味着平台不仅要“运行起来”，还要“能够不停地升级和扩展”。因此，高可用与容灾在本项目中属于底线能力，而不是锦上添花。

## 2. 技术分析

### 2.1 技术点一：入口高可用

#### 技术解释

入口高可用解决的是“用户和边缘节点如何稳定进入平台”的问题，通常通过多入口节点、虚拟地址和反向代理集群完成。

#### 项目中的使用场景

本项目中，边缘节点上报请求和用户访问请求都要先经过统一入口。若入口层只有单节点，一旦故障，整个平台就会整体不可用。因此需要在入口层通过：

- `Nginx`
- `Keepalived`
- `VIP`

实现访问入口高可用。

典型链路可写为：

`边缘节点/WEB端 -> VIP -> Nginx/Keepalived -> API 网关`

#### 为什么这样贴合项目

因为本项目同时有设备接入流量和人员访问流量，入口层是所有业务的共同前提。

### 2.2 技术点二：服务多副本部署

#### 技术解释

服务多副本部署用于避免单个业务实例故障导致核心能力中断。

#### 项目中的使用场景

本项目中的监控、告警、工单、权限等核心服务，都不应以单实例方式运行，而应通过：

- `Kubernetes`
- 多副本服务部署

方式运行，保证某个实例故障时流量可切换到其他健康实例。

#### 为什么这样贴合项目

因为监控、告警和工单都属于核心链路，任一单点故障都可能直接影响运维闭环。

### 2.3 技术点三：缓存与数据库高可用

#### 技术解释

平台服务稳定，不仅取决于应用实例，还取决于缓存与数据库是否具备故障切换能力。

#### 项目中的使用场景

本项目中，可采用以下方式提升数据层可靠性：

- 缓存层采用 `Redis Sentinel`
- 数据库层采用 `MySQL 主从` 或 `MGR`

这样做可以在单节点故障时维持核心数据读写能力。

#### 为什么这样贴合项目

因为工单、告警、权限、设备档案等核心数据都依赖数据库和缓存，一旦数据层不可用，应用层多副本也没有意义。

### 2.4 技术点四：边缘侧容错

#### 技术解释

边缘侧容错解决的是“中心平台异常或网络抖动时，现场数据如何不丢”的问题。

#### 项目中的使用场景

本项目中，边缘节点具备本地缓存和恢复后补传能力。当中心平台入口临时不可用或链路波动时，边缘节点仍可先保存关键遥测数据，待恢复后补传，避免采集链路完全中断。

#### 为什么这样贴合项目

工业现场与中心平台之间的网络不可能始终稳定，边缘容错是平台真实可用的重要保障。

### 2.5 技术点五：可观测性与备份恢复

#### 技术解释

高可用不只是架构设计，还必须通过监控、日志、备份和演练机制持续验证。

#### 项目中的使用场景

本项目中，需要至少补齐以下能力：

- `Prometheus + Grafana` 监控关键指标
- 核心服务、缓存、数据库的统一日志与告警
- 数据备份与恢复流程
- 分阶段容灾演练
- 灰度发布与回滚预案

#### 为什么这样贴合项目

因为项目是分期交付并持续优化的，若没有监控、备份和演练，所谓“高可用”就只停留在设计图层面。

## 论文示例

### 摘要

2024年7月，我作为系统架构师参与并主导某汽车零部件集团“智能设备运维平台”总体架构设计。平台面向集团3个生产基地、900余台关键设备和24台边缘节点，建设设备接入、实时监控、异常告警、工单闭环和统计分析等能力，支撑设备运维由“事后抢修”向“预防性维护”转型。项目周期18个月，团队22人，采用3期交付方式，于2026年1月全面上线。本文结合该项目建设实践，首先简要描述高可用与容灾的概念，随后围绕高可用与容灾，阐述我如何从入口冗余、服务多副本、数据高可用、边缘自治、故障切换和可观测运维几个方面开展架构设计与实施，并分析相关技术选型、实施效果和架构取舍。

### 正文

#### 项目背景

随着制造业数字化转型推进，设备运维已从故障后抢修转向统一管控、过程可视、协同处置和持续优化。传统分散管理方式，难以满足跨基地、多设备、长周期运行下的稳定性和响应效率要求。我所在企业是一家汽车零部件集团，下辖3个生产基地，拥有关键设备900余台，并部署24台边缘节点。建设前，各基地数据分散，告警口径不一，工单处置缺少闭环，集团难以及时掌握设备状态和沉淀运维经验。为此，公司建设“智能设备运维平台”，打通设备接入、实时监控、规则判定、告警生成、工单联动、处置闭环和统计分析等主链路。项目于2024年7月启动，周期18个月，团队22人，采用3期交付，并于2026年1月全面上线。我作为系统架构师，负责总体架构设计和核心质量属性把控，围绕“端边云协同、分层解耦、事件驱动、持续演进”建立架构基线，支撑当前建设目标并预留后续演进空间。

#### 过渡内容

高可用与容灾不是简单多买几台服务器，而是要让系统在局部故障、网络波动和组件异常时仍能优先保障核心业务。本项目的核心链路包括设备数据上报、监控状态刷新、规则判定、告警生成和工单派发。任何一个环节中断，都可能影响设备异常发现和运维响应。因此，我将高可用设计分为入口层、服务层、数据层、边缘层和运维层，形成分层防护和快速恢复能力。

#### 主体内容

首先，在入口层，我将管理类 HTTP 请求和高频设备遥测请求分开治理。Web 端、移动端和边缘节点管理接口通过统一域名、VIP、Nginx 和 API 网关进入平台，由网关完成鉴权、路由、限流和访问审计；高频遥测数据则通过 MQTT Broker 和中心接入服务进入 Kafka，不与管理类请求挤在同一个入口。Nginx、API 网关和 MQTT Broker 都采用多实例部署，并通过健康检查自动摘除异常节点。这样，即使某个入口实例异常，其他实例仍能继续承接流量。

其次，在服务层，核心业务服务全部运行在 Kubernetes 集群中，采用多副本部署和滚动发布。设备接入、监控、告警、工单、权限和分析服务通过 Deployment 管理副本，通过 Service 和 CoreDNS 提供服务发现。Readiness Probe 用于判断实例是否可以接收流量，Liveness Probe 用于发现进程卡死并触发重启。对于接入和告警这类关键服务，配置 HPA 或基于 Kafka Lag 的弹性扩容，避免早班开机、断网补传或告警集中爆发时处理能力不足。对于报表分析等非核心链路，则通过限流和错峰计算避免影响实时链路。

再次，在数据层，我按不同数据特性设计高可用策略。MySQL 采用主从或高可用集群承载设备档案、告警记录、工单状态和权限数据，并设置备份与恢复演练；Redis 采用 Sentinel 或集群模式支撑热点状态和配置缓存；Kafka 通过多 Broker、副本机制和消费组位点管理保证消息可持续消费。对于告警和工单这类关键事件，采用 Outbox、幂等、重试和死信队列，避免数据库写入成功但事件丢失，或消息重复导致工单重复创建。

在边缘层，我特别考虑现场网络不稳定问题。边缘节点负责协议适配、数据标准化、本地缓存和断点续传。采集到的数据先写入本地 SQLite Outbox，再通过 MQTT 上报中心；网络中断时数据在本地保留，网络恢复后按 localSeq 和事件时间补传，中心接入服务通过幂等键去重。安全类和状态类规则可在边缘本地执行，保证现场基础响应不完全依赖中心平台；复杂关联规则仍由中心执行，避免边缘节点过度膨胀。这样，基地网络短时异常不会直接造成数据丢失。

在容灾和运维层，我建立了故障检测、切换和复盘机制。Prometheus 采集基础设施、Kubernetes、MQTT、Kafka、数据库和业务指标，重点关注边缘节点在线率、数据上报成功率、Kafka Lag、告警生成延迟、接口错误率和工单创建成功率。常见故障有明确预案，例如 Pod 异常重启、Kafka 消费积压、Redis 主从切换、数据库只读异常和边缘节点离线。对低风险平台故障可以自动或半自动处理，对涉及生产设备和数据一致性的故障必须人工确认。故障恢复后进行复盘，补充监控、测试和预案。

该方案的取舍在于，高可用会带来资源成本和运维复杂度。并非所有模块都需要同等级别保障，因此我按业务影响分级：设备接入、监控和告警属于高优先级链路，要求多副本、快速恢复和高频监控；分析报表可接受延迟和降级；后台管理功能在异常时可以短暂不可用。通过分级保障，既控制成本，又保护核心业务。

#### 论文结论

“智能设备运维平台”于2026年1月完成三期交付并全面上线。运行实践表明，平台在多基地、多设备、边缘协同的生产环境下总体稳定，关键设备非计划停机率下降约18%，运维响应效率和集团统一管理能力明显提升，基本达成了由“事后抢修”向“预防性维护”转型的建设目标。

从本次高可用与容灾设计看，我重点围绕服务多副本、故障隔离、边缘缓存补传、数据备份和恢复演练进行了落地，使平台在边缘弱网、服务实例异常和核心数据恢复中具备了更好的持续服务、数据可靠和恢复可控能力。同时，项目后续仍有两个值得持续优化的方向：一是告警处置知识库和AI分析模块还需要结合真实维修过程继续沉淀。例如早班开机后，某条产线设备可能连续出现温度升高、振动波动和重复告警。对于这类场景，系统目前可以基于历史告警、维修记录和知识库推荐相似案例、处置步骤和可能原因；但当故障同时受设备老化、工况变化和维护不及时等因素影响时，仍需要结合专家反馈持续优化规则和分析模型。二是内网环境下的部署分发方式还可以继续优化。由于生产网络与外部网络隔离，当前版本发布主要采用离线镜像包方式，由流水线完成构建和扫描后导出镜像tar文件，再上传到各环境服务器或内网节点进行导入部署。该方式满足了安全隔离和上线可控要求，但在多服务版本联动、回滚效率和跨基地同步发布方面仍有提升空间。后续可逐步建设内网私有镜像仓库、自动化镜像同步和发布编排能力，在不降低安全边界的前提下提升交付效率。

回顾项目全过程，作为系统架构师，我进一步认识到，高可用与容灾不能停留在简单堆叠冗余资源，也不能脱离业务场景追求复杂方案，而应从问题识别出发，在业务目标、团队能力、运行成本和演进空间之间取得平衡。只有把高可用与容灾落实为可验证、可治理、可演进的工程能力，才能真正支撑平台长期稳定运行和持续发展。
