# 技术二：数据架构与大数据处理（收敛版）

## 过渡段（可直接写入正文）

大数据架构在本项目中不是越重越好，而是要用适度的架构层次承接设备高频数据和运维分析需求。平台既要让最新状态、短时趋势和告警判断保持低延迟，也要把历史测点、告警、工单和处置结果沉淀下来，支撑统计分析和后续预测性维护。因此，我没有一次性铺开复杂大数据平台，而是围绕Kafka、Flink、热数据服务层和湖仓明细层，形成实时链路稳定、历史数据可查、指标口径可治理的收敛方案。

项目固定背景统一参考 [项目固定背景.md](/Users/duanpeitong/Desktop/work/study/26_jgs_lw/项目固定背景.md)。

本文件用于替代原 06 文件中偏重技术栈罗列的写法。它保留大数据架构的层次感，但控制组件数量，适合在论文中写成“架构师根据业务访问模式做取舍”，而不是写成大数据组件清单。

## 1. 设计定位

### 1.1 本项目为什么需要大数据架构

本项目服务于 3 个生产基地、900 余台设备和 24 台边缘节点。设备持续产生状态、测点、告警和工单过程数据。按每台设备约 30 个测点、平均 5 秒采集一次估算，平台每秒约产生 5400 个数据点，日增量接近 90GB。

这些数据有三类典型访问模式：

| 场景 | 关注点 | 时效要求 | 典型数据 |
| --- | --- | --- | --- |
| 实时监控 | 当前状态、近期趋势、异常发现 | 秒级 | 最新状态、近几分钟曲线 |
| 运维闭环 | 告警、工单、处置过程追踪 | 秒级到分钟级 | 告警事件、工单状态 |
| 管理分析 | 可用率、故障率、MTTR、基地对比 | 分钟级到小时级 | 日报、月报、趋势指标 |

因此，本项目的数据架构不能只选一个数据库解决所有问题，也不需要建设过重的大数据平台。合理的目标是：实时链路低延迟，历史数据可沉淀，指标口径可统一，查询服务不互相干扰。

### 1.2 设计原则

我会把本项目的大数据架构控制在五条原则内：

- 数据先分层，再选技术组件。
- 实时链路优先保障监控和告警，不被报表分析拖慢。
- 热数据服务面向用户正在等待的查询，湖仓面向长期沉淀和离线分析。
- 指标统一在平台侧计算，各基地不各算各的。
- 组件数量可控，能用一类组件解决的场景不拆成多套系统。

## 2. 推荐总体架构

### 2.1 架构概括

推荐架构可以概括为：

```text
边缘节点
-> MQTT Broker
-> 中心接入服务
-> Kafka 数据总线
-> Flink 实时处理
-> 热数据服务层 + 湖仓明细层
-> 离线指标计算
-> 驾驶舱 / 监控 / 告警 / 分析应用
```

更适合论文中的一句话表达：

> 我采用“Kafka 数据总线 + Flink 实时处理 + 湖仓沉淀 + 热数据服务”的收敛式大数据架构，支撑设备数据的实时监控、告警识别、长期分析和统一指标治理。

### 2.2 组件控制

组件不宜过多。建议主线只保留下面几类：

| 层次 | 推荐组件 | 职责 |
| --- | --- | --- |
| 接入缓冲 | Kafka | 承接中心接入服务写入的数据，支撑削峰、解耦和回放 |
| 实时处理 | Flink | 数据清洗、去重、质量标记、窗口聚合、复杂事件识别 |
| 热数据服务 | Redis + 时序/OLAP 存储 | Redis 存最新状态和热点指标，时序/OLAP 存近期趋势和交互分析 |
| 湖仓沉淀 | HDFS 或 MinIO + Iceberg | 保存 ODS 原始数据和 DWD 明细数据，支撑长期存储、回放和离线分析 |
| 离线计算 | Spark 或 Flink SQL | 计算 DWS/ADS 指标，如可用率、故障率、MTTR |
| 业务数据 | MySQL | 保存设备主数据、告警、工单、权限和驾驶舱结果表 |

其中，时序/OLAP 存储不要再拆得太细。论文中可以写成“时序分析库或 OLAP 明细库”，不必同时展开 InfluxDB、HBase、Elasticsearch、Doris、ClickHouse。真实工程中可以根据团队经验选择 ClickHouse、Doris 或 InfluxDB 之一。

## 3. 数据分层设计

### 3.1 四层数据模型

数据分层比组件名称更重要。本项目可以采用 ODS、DWD、DWS、ADS 四层。

| 层级 | 存放内容 | 核心价值 |
| --- | --- | --- |
| ODS 原始层 | Kafka raw topic 归档的原始报文 | 保留事实，支持回放和问题复盘 |
| DWD 明细层 | 清洗后的设备状态、测点、告警、工单明细 | 统一格式、去重、质量标记、关联主数据 |
| DWS 汇总层 | 按设备、基地、班组、日期聚合的通用指标 | 统一指标口径，避免多处重复计算 |
| ADS 应用层 | 驾驶舱、报表、预测性维护特征数据 | 面向页面和模型直接消费 |

### 3.2 项目中的典型链路

设备遥测数据链路：

```text
边缘节点原始报文
-> Kafka raw
-> Flink 清洗、去重、测点映射、质量标记
-> Kafka clean
-> Redis 更新最新状态
-> 时序/OLAP 存储近期趋势
-> Iceberg DWD 沉淀明细
```

告警与工单分析链路：

```text
告警事件 / 工单事件
-> Kafka event topic
-> Flink 或业务服务处理实时状态
-> MySQL 保存业务状态
-> Iceberg DWD 保存明细
-> 离线计算 DWS 指标
-> ADS 输出 MTTR、闭环率、及时率
```

这样设计后，实时监控、告警闭环和管理分析使用同一批底层数据，但走不同查询路径，不互相阻塞。

## 4. 实时链路设计

### 4.1 Flink 的职责

Flink 不需要承担所有大数据任务，但在本项目中它应作为实时数据处理主线。

主要职责包括：

- 从 Kafka raw topic 消费边缘上报数据。
- 根据设备主数据和测点模型做标准化。
- 处理边缘补传、MQTT 重投导致的重复数据。
- 对异常值、缺失值、时间乱序打质量标记。
- 输出 clean topic，供监控、规则、分析消费。
- 对近期窗口做聚合，如 1 分钟平均温度、5 分钟振动峰值。
- 对复杂事件进行识别，如连续温升叠加振动异常。

这样写的好处是主线清楚：Flink 是实时清洗和实时计算入口，不再额外强调 Kafka Streams、HBase 等多个并列组件。

### 4.2 实时链路的取舍

实时链路不追求把所有指标都实时算完。设备最新状态、窗口趋势和关键告警需要实时；设备可用率、故障率、MTTR、基地月度对比不需要秒级计算，可以放到离线链路。

这个取舍适合论文表达：

> 我没有将所有分析任务都放入实时链路，而是把设备状态刷新、告警判定和短窗口聚合作为实时任务，将可用率、故障率、MTTR 等长周期指标放入离线链路，避免复杂统计任务影响监控和告警响应。

## 5. 存储与查询设计

### 5.1 热数据服务层

热数据服务层只解决用户正在等待的查询。

| 数据 | 存储建议 | 查询场景 |
| --- | --- | --- |
| 最新设备状态 | Redis | 监控大屏实时刷新、设备详情当前状态 |
| 近期趋势数据 | 时序/OLAP 存储 | 近 1 小时、近 24 小时曲线 |
| 驾驶舱热点指标 | Redis 或 MySQL 缓存表 | 首页指标、基地概览 |

这层数据可以有保留周期，例如 30 天原始趋势、180 天降采样趋势。它不承担长期历史沉淀。

### 5.2 湖仓沉淀层

长期数据放入湖仓，而不是继续压在实时库里。

推荐口径：

```text
HDFS/MinIO + Iceberg
```

其中 HDFS 或 MinIO 负责低成本存储，Iceberg 负责表格式、Schema 演进、增量读取和时间旅行。

湖仓层存两类数据：

- ODS：原始报文，保留数据源事实。
- DWD：清洗后的明细数据，作为离线指标和历史分析基础。

论文中不用把 Iceberg 的每个机制展开，只抓三点即可：

- Schema 演进：新增测点时不重写历史数据。
- 增量读取：离线计算只处理新增数据，降低计算成本。
- 时间旅行：指标异常时可以回放历史版本，支持复盘。

### 5.3 业务查询与分析查询分离

MySQL 仍然保存业务事实，如设备档案、工单状态、告警记录、权限数据。大数据架构不应替代业务数据库。

更合理的分工是：

- MySQL 负责业务状态和事务一致性。
- Kafka/Flink 负责事件流转和实时处理。
- 湖仓负责历史明细和离线分析。
- Redis/时序或 OLAP 存储负责低延迟查询。

### 5.4 算存分离与弹性分析

算存分离不是本项目的主线，但可以作为数据架构的演进点写入论文。它的核心思想是：历史数据统一沉淀在湖仓存储层，计算资源按任务类型独立扩缩容，避免存储扩容和计算扩容互相绑定。

在本项目中，ODS 原始数据和 DWD 明细数据可以统一保存在 HDFS 或 MinIO 上，并通过 Iceberg 管理表结构、快照和增量读取。Flink、Spark 或 SQL 查询引擎按需读取同一份湖仓数据：实时任务关注新增数据和短窗口计算，离线任务关注日级、月级指标汇总，临时分析任务则按需拉起计算资源。这样，历史数据不需要为不同计算引擎重复存储，计算能力也可以根据早晚高峰、日报计算和临时分析压力独立调整。

写作时要注意，算存分离不要写成另起一套架构。它更适合作为湖仓设计的取舍点：存储层保持稳定、低成本和可追溯，计算层按场景弹性使用，支撑平台后续接入更多设备和分析任务。

## 6. 离线指标与数据治理

### 6.1 统一指标口径

本项目最值得写的不是用了多少大数据组件，而是通过平台统一计算指标，解决多基地口径不一致问题。

核心指标建议统一放在 DWS 层：

| 指标 | 计算口径 | 数据来源 |
| --- | --- | --- |
| 设备可用率 | 实际运行时间 / 计划运行时间 | 设备状态明细 |
| 故障率 | 故障次数 / 运行时间 | 告警 + 设备状态 |
| MTTR | 故障修复总时长 / 故障次数 | 告警 + 工单 |
| 工单及时率 | SLA 内关闭工单 / 总工单 | 工单明细 |
| 告警闭环率 | 已关联工单并关闭的告警 / 总告警 | 告警 + 工单 |

各基地和总部都消费 DWS/ADS 输出的统一结果，避免同一指标在不同报表中含义不同。

### 6.2 数据质量治理

数据质量治理要和项目问题绑定。

| 问题 | 项目来源 | 治理方式 |
| --- | --- | --- |
| 重复数据 | MQTT 重投、边缘补传 | 按 edgeId、deviceId、metricCode、timestamp 幂等去重 |
| 时间乱序 | 弱网、断网补传 | 同时保留 eventTime、receiveTime，乱序数据打标 |
| 测点口径变化 | 现场改造、配置变更 | 每条数据携带 configVersion |
| 缺失数据 | 设备断连、采集失败 | 质量标记为 missing，分析时不直接当作 0 |
| 异常值 | 传感器异常、协议解析错误 | 标记 out_of_range，进入隔离队列复核 |

质量标记应进入 DWD 明细层，后续实时告警、离线分析和历史复盘都可以识别数据是否可信。

## 7. 架构取舍

### 7.1 不采用过重技术栈

本项目设备规模是 900 余台，不是百万级设备接入平台。因此不应把 HBase、InfluxDB、Elasticsearch、ClickHouse、Doris、Hive 全部放成同等核心组件。

更稳妥的做法是：

- 实时处理统一靠 Flink。
- 热查询选择 Redis + 一类时序或 OLAP 存储。
- 长期沉淀统一靠 Iceberg 湖仓。
- 日志全文检索归到可观测性体系，不作为大数据主链路重点。

### 7.2 不让大数据架构侵入业务事务

工单创建、告警确认、权限变更仍然由业务服务和 MySQL 承担。大数据架构通过事件订阅沉淀明细和计算指标，不直接替代业务事务。

这样可以避免为了分析方便而破坏业务系统的事务边界。

### 7.3 预留演进空间

后续如果接入更多基地或预测性维护能力增强，可以逐步演进：

- 增加 Kafka 分区和 Flink 并行度。
- 扩大湖仓存储容量。
- 引入更强的 OLAP 引擎支撑自助分析。
- 通过算存分离让离线计算、临时分析和模型特征计算按需扩缩容。
- 在 ADS 层沉淀设备健康评分和模型特征。

这属于持续演进，不需要在一期就把所有大数据能力一次性铺开。

## 8. 可写入论文的主体内容

在本项目中，【**数据架构设计**】不是简单选择某个数据库，而是围绕设备运维数据的实时处理、长期沉淀和统一分析进行系统设计。平台覆盖 3 个生产基地、900 余台设备和 24 台边缘节点，设备状态、测点值、告警事件和工单过程数据持续产生。按每台设备约 30 个测点、平均 5 秒采集一次估算，中心侧每秒约接收 5400 个数据点，日增量接近 90GB。实时监控要求秒级刷新，异常告警要求及时识别，集团驾驶舱和趋势分析又要求长周期聚合。如果把所有数据都放在同一种存储中，高频写入、实时查询和复杂统计会互相干扰；如果为每类需求单独建设一套链路，又会造成数据孤岛和口径不一致。因此，我采用“Kafka 数据总线、Flink 实时处理、湖仓长期沉淀、热数据服务低延迟查询”的收敛式大数据架构。

首先，在【**数据分层模型**】上，我将数据划分为 ODS、DWD、DWS 和 ADS 四层。ODS 层保存边缘节点上报的原始报文，不做业务转换，用于回放和问题复盘；DWD 层保存清洗后的设备状态、测点、告警和工单明细，统一设备编码、测点编码、时间戳、质量标记和配置版本；DWS 层按设备、基地、班组和日期聚合通用指标，如设备可用率、故障率、MTTR 和告警闭环率；ADS 层面向驾驶舱、报表和预测性维护输出最终结果。这样设计后，原始事实、标准明细、通用指标和应用结果各有边界，上游协议变化不会直接冲击驾驶舱指标，管理层看到的跨基地指标也来自同一套计算口径。

其次，在【**数据接入与实时处理**】上，边缘节点通过 MQTT 将设备数据上报到中心接入服务，中心接入服务只做节点身份校验、基础格式校验、幂等键补充和路由分发，然后将数据写入 Kafka 原始主题。Kafka 承担平台内部数据总线职责，使监控、告警、分析等链路可以独立消费同一批数据。Flink 从 Kafka 原始主题消费数据，完成去重、测点映射、单位转换、时间校正和质量标记，再输出到清洗后的主题。监控服务和规则引擎只消费清洗后的数据，避免在原始数据上重复处理协议差异，也避免因边缘补传、MQTT 重投或测点配置变更导致规则误判。

在实时链路中，我没有把所有计算都交给业务服务同步完成。设备最新状态、短窗口聚合和复杂事件识别由 Flink 实时处理：最新状态用于监控大屏刷新，短窗口聚合用于展示温度、振动、电流等近期趋势，复杂事件识别用于判断“连续温升叠加振动异常”这类故障前兆。规则引擎生成告警事件后，再通过 Kafka 驱动通知、工单和分析链路。这样，设备接入、监控刷新和告警识别不会被报表统计或工单后续处理阻塞，平台在早班开机、边缘补传和告警集中爆发时仍能优先保障主链路。

再次，在【**冷热分层存储**】上，我没有让实时库承担长期历史分析，也没有把湖仓用于用户正在等待的实时查询。对于设备最新状态、基地概览和驾驶舱热点指标，写入 Redis 或 MySQL 缓存表，支撑页面快速刷新；对于近 30 天到 180 天的趋势曲线，写入一类时序或 OLAP 存储，支撑设备详情、告警上下文和基地趋势查询；对于原始报文和清洗后的明细数据，则写入 HDFS 或 MinIO 上的 Iceberg 表，形成 ODS 和 DWD 层，用于长期保留、历史回放和离线分析。热数据服务层解决“用户马上要看”的问题，湖仓层解决“数据长期可管、可算、可追溯”的问题，二者职责清晰。

在【**流批协同计算**】上，我按时效要求拆分任务。设备最新状态、短窗口趋势和关键告警属于实时任务，由 Flink 在秒级链路中处理；设备可用率、故障率、MTTR、工单及时率、告警闭环率等长周期指标由离线任务每日汇总，写入 DWS 和 ADS 层，再供驾驶舱和报表使用。这样做的原因是，长周期指标往往需要关联设备状态、告警明细、工单明细和设备主数据，如果强行放进实时链路，会增加状态管理和跨表关联复杂度，也会占用告警判定所需的计算资源。通过流批协同，平台既能看见当前状态，也能稳定沉淀长期指标。

在【**数据治理**】方面，我重点解决多基地口径一致和数据质量可追溯问题。平台统一定义设备可用率、故障率、平均修复时间、告警闭环率等核心指标，并在 DWS 层集中计算，各基地和总部消费同一份结果，避免各基地自行统计造成横向对比失真。对于边缘补传、MQTT 重投、设备断连、测点变更和异常值等问题，Flink 在 DWD 层为每条数据打上质量标记，并保留 edgeId、configVersion、eventTime、receiveTime 等元数据。比如某设备在断网后补传历史数据，系统既可以按事件时间还原设备状态，也能通过接收时间识别补传延迟；某测点配置调整后，后续分析可以按 configVersion 区分不同口径，避免把口径变化误判为设备异常。

为了支撑问题复盘，我还设计了从应用结果到原始数据的追溯链路。当某个基地月度可用率突然下降时，架构上可以从 ADS 驾驶舱指标追溯到 DWS 汇总结果，再下钻到 DWD 层的设备状态明细、告警明细和工单明细，必要时回到 ODS 原始报文查看边缘节点当时上报的真实内容。Iceberg 的表格式能力用于管理历史快照、Schema 演进和增量读取，既支持新增测点后的结构变化，也支持离线任务只处理新增数据，降低每日计算成本。这种追溯能力使数据架构不只是服务查询，也服务故障定位、指标审计和后续算法建模。

从项目效果看，这种架构既没有过度堆叠大数据组件，也能支撑平台的实时监控、告警联动和长期分析。Kafka 和 Flink 保障了设备数据主链路的实时处理能力，Redis 和时序/OLAP 存储保障了用户交互查询体验，Iceberg 湖仓保障了长期数据沉淀、口径治理和历史回放能力。同时，湖仓层也为后续算存分离预留了基础，历史数据统一沉淀，计算资源可以按日报计算、临时分析和模型训练等不同负载独立扩缩容。我的体会是，大数据架构的关键不在于技术栈越多越好，而在于根据访问模式划清边界：实时数据走实时链路，历史数据进湖仓，核心指标统一计算，质量问题可追溯。这样平台才能在设备规模扩大和预测性维护能力演进时保持可扩展、可治理和可持续优化。

## 9. 考场快速组织方式

遇到“大数据架构 / 数据架构 / 湖仓 / 实时分析”类题目，可以按下面顺序写：

```text
项目数据规模和访问差异
-> 为什么不能单一数据库承载
-> Kafka + Flink 实时链路
-> 热数据服务层和湖仓沉淀层
-> 离线指标与数据治理
-> 效果与取舍
```

如果题目偏 Lambda 架构，就放大“Flink 实时 + 离线计算”。

如果题目偏数据湖仓，就放大“ODS/DWD/DWS/ADS + Iceberg + 指标治理”。

如果题目偏数据治理，就放大“统一指标口径、质量标记、血缘追溯”。

如果题目偏算存分离，就放大“湖仓统一存储 + 计算引擎按需扩缩容 + 避免重复存储”。
